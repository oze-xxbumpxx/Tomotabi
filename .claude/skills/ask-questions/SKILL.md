# 問いを出すスキル

AI に要件定義書を「書かせる」と、決まっていないことを決まったこととして書いてしまう。
そこで、書く前に AI が「問い」を出し、ユーザーが答えてから書く。
問いを全部出すと 50 問を超えて人が読めなくなるので、札を付けて絞る。

元にした考え方: 食べログの「AI に問わせる要件定義」（https://tech-blog.tabelog.com/entry/ai-requirements-definition-with-questions）。

## いつ使うか

- L2 / L3 の要件定義書・設計書を書く前（`create-requirements-document` / `create-design-document` の手順から呼ぶ）。
- L0 / L1 では使わない。迷ったら自分で決めて、報告に一行書く。ユーザーに聞くのは AGENTS.md のゲートに当たるものだけ。

## 進め方

1. 正本（基本設計・詳細設計・`docs/design/handoff-v3/`）と既存のコード・文書を読む。問いの根拠はここから取る。
2. 調べる観点は工程ごとのチェックリストを使う。要件定義は [create-requirements-document/checklist.md](../create-requirements-document/checklist.md)。
3. 決まっていないこと・正本どうしで食い違うことを、全部「問い」として書き出す。この段階では数を絞らない。
4. 各問いに 2 つの札を付ける（下の「札の付け方」）。
5. **今の工程** かつ **優先度: 高** の問いだけをユーザーに出す。目安は 10 問以内。超えたら優先度の付け方を見直す。
6. それ以外の問いは、成果物の「未決事項」に札つきで残す。後の工程で、その工程の問いとして出し直す。
7. 答えを成果物の「決めたこと（問いと答え）」に記録してから、本文を書く。

## 札の付け方

| 札     | 値                        | 決め方                                                                                                         |
| ------ | ------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 工程   | 要件 / 設計 / 実装 / 運用 | 何を決める段階の問いか。「画面に何を出すか」は要件、「どの表に持つか」は設計、「どの関数に置くか」は実装       |
| 優先度 | 高 / 中 / 低              | 高: 答えが無いと今の工程を書けない。中: 今の工程で決めたいが、仮置きで先に進める。低: 後の工程で決めれば足りる |

コードを読めば答えが出る問い（既存の書き方に合わせる、ファイルの置き場所など）は、問いにしない。自分で決めて「決めたこと」に根拠と一緒に書く。

## 問いの書き方

3 つを守る。

- 具体的に問う。「通知はどうしますか」ではなく「精算の確認を相手が完了したとき、立て替えた側に通知を送るか」。
- なぜ今決める必要があるかを書く。根拠は正本の箇所・コードの `path:line`・既存の決定（ADR）で示す。
- 選択肢を用意し、AI の推奨を 1 つ選ぶ。最後の選択肢は必ず「その他（自由に書く）」にする。

ひな形は [template.md](template.md)。

## ユーザーへの出し方

- メインの会話で、番号つきの一覧として出す。Subagent はユーザーに直接聞けないので、問いを Orchestrator に返す。
- ユーザーは「1A 2B 3C」のように記号で答える。推奨どおりでよいなら「全部推奨」でよい。
- 答えが「その他」や質問返しのときは、その問いだけをやりとりして決める。
- 問いの番号は答え合わせのための仮の番号。報告や文書では番号だけで指さず、問いの中身で書く（AGENTS.md）。

## 記録

成果物（要件定義書・設計書）の「決めたこと（問いと答え）」に、問いごとに 1 行残す。

| 問い | 答え | 推奨と同じか | 理由（ユーザーが言ったときだけ） |
| ---- | ---- | ------------ | -------------------------------- |

「推奨と同じか」を残すのは、AI の推奨が外れやすい種類の問いを後で見つけるため。
外れた問いは、チェックリストに観点を足すか、正本に書かれていない前提（二人の使い方・お金の感覚など）を `docs/glossary.md` や正本の補足に足す材料にする。

## 調べている途中で既存の不具合を見つけたとき

勝手に直さない。問いとは別に、次の 3 つを書いて報告する。直すかどうかはユーザーが決める（Issue にするかも含む）。

- 何が起きるか
- どの条件で起きるか（`path:line`）
- 直し方の選択肢と推奨

## 禁止

- 決まっていないことを、問いにせず本文に決定として書く。
- 札を付けずに全部の問いをユーザーに出す。
- 選択肢・推奨・根拠のない問い。
