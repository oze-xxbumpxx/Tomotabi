# 要件定義の調べる観点

要件定義書を書く前に、この観点で「決まっていないこと」を探し、[ask-questions](../ask-questions/SKILL.md)の問いにする。
全部の観点に問いを作る必要はない。正本や既存の決定で答えが出ているものは、根拠を書いて飛ばす。

Tomotabiは二人で使う旅行アプリなので、立場は「作った側・相手側」「お金を立て替えた側・受け取る側」で分けて考える。
エンジニアの目だけで見ると、相手側の画面・旅行中の電波・あとから見返すときの観点が抜けやすい。

## 1. なぜ作るか（要求）

- この機能が無いと、二人は今どう困っているか。正本のどこに書いてあるか。
- 今回の段階でどこまで作り、どこを次の段階に回すか（画面だけ・APIだけ・ふつうの流れだけ、など）。
- 正本の案から変えたい値はあるか（上限・件数・期間など）。変えるなら理由。

## 2. 何が変わるか（使い方）

立場ごとに、操作の前後で何が見え、何ができるかを追う。

| 立場                           | 見る観点                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------------ |
| 操作した人                     | 操作のあと、画面に何が出るか。間違えたとき戻せるか（取りやめ・取り消し）             |
| 相手                           | 相手の操作をいつ・どこで知るか。同時に同じものを触ったら（競合）                     |
| お金を立て替えた人・受け取る人 | 金額・端数・残額の見え方。受け渡しの確認のあとに支払いが増えたり取り消されたりしたら |
| 旅行中の人                     | 電波が弱い・切れたときに保存できるか（結果不明・同じ要求で確かめる）                 |
| 旅行が終わったあとの人         | 記録を見返したとき、取り消した記録や誰が何をしたかが分かるか                         |
| 運用する人（自分）             | 二人から「おかしい」と言われたとき、どの記録で原因を追えるか                         |

- 既存の機能（旅行・予定・支払い・精算など）のうち、この変更で振る舞いが変わるものはどれか。`path`で挙げる。
- 個人情報（名前・メール・位置）を新しく持つか、見せる範囲が変わるか。

## 3. 何を作るか（要件）

- 機能: 入力・出力・状態の移り方。状態ごとに、できる操作とできない操作。
- 異常系: 権限がない、相手が先に変えた、二重に送った、途中で失敗した、ときの振る舞い。
- 境界: 0・空・上限・下限・日付の切り替わり・旅行の開始前と終了後。
- 性能・保存: 件数の上限、旅行中のオフライン、再読み込みしたときに残すもの。
- 受け入れ条件: 自動の試験で確かめるもの、手で確かめるもの、E2Eに足すもの。

## このチェックリストの育て方

設計・実装・レビューの段階で「要件定義のときに聞いておけばよかった」問いが出たら、その観点をここに1行足す。
`ask-questions`の記録で「推奨と同じか」が「違う」だった問いも、足す候補にする。
