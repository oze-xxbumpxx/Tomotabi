# 判断を1枚の画面にまとめる

候補が複数ある設計と、不具合の原因調べは、チャットに文章を重ねない。3列の1枚にまとめ、人が1問ずつ選ぶ。

見た目の参照は[reference.png](reference.png)。同じフォルダの[example.tsx](example.tsx)は、その見た目を1ファイルで再現した見本である。見本の上部にある「見本データ」の帯、割合、経過、工程の分数、不具合の筋書きは作り物なので、本番の画面に写さない。

## いつ使うか

- 置き場所、文言、画面の流れ、データの持ち方など、候補が2つ以上ある設計の判断。
- 不具合について、原因の候補と直し方を、根拠と一緒に並べるとき。
- 使わないとき。コードを読めば答えが1つに決まる修正。候補の無い作業。

L2 / L3の論点の記録と確認のページは`ask-questions`の仕事である。この画面は、持ち主が見て選ぶための成果物で、記録の代わりにしない。実装は、持ち主が選んだあとに`develop-feature`で進める。このスキルの中でアプリのコードは変えない。

## 出すもの

claude.aiのArtifactとして、1ファイルのReactを出す。

- `export default`のコンポーネントが1つ。ファイルは分けない。同じファイルの補助コンポーネントは、exportしなければ使ってよい。
- importは`react`だけ。アイコンのパッケージは足さない。図はSVGで描く。
- 見た目はTailwindのクラス。色と余白は下のトークンに合わせ、新しい色を足さない。
- 画面の文言は日本語。専門用語は、何をするかを先に書いてから名前を出す。
- 子エージェントは作らない。このセッションがこのスキルを読んで、成果物を出す。
- 見本ファイルにある「設計の見本 / 不具合の見本」の切り替えは、見本を両方載せるためだけにある。本番は、頼まれた方を1枚出す。

## 手順

1. 関係するコードを開く。開いていないファイルの中身は書かない。パスを記憶で作らない。
2. 問いを分ける。中央は1つ。残りは左のインボックスに置く。
3. 選択肢は2つか3つ。各カードに、1行の説明、トレードオフ1行、小さな見本を書く。
4. 推奨は1つまで。理由を1行書く。理由が無いときは札を付けない。
5. 右に根拠を置く。数と事例は、開いたコード、実行した結果、持ち主の言葉だけにする。
6. 下の点検を満たしてから出す。
7. チャットには、ページのURLと、中央にある問いの1文だけを添える。

## 3列

全体は横並び。左がインボックス、中央がいまの問い、右が根拠。背景はグレー、各列は白い角丸の面。幅の目安は左280px、右320px、中央が残り。

### 左（インボックス）

見出しは「インボックス」。参照画像の「離席」スイッチは、見た目だけ置いてよい。スイッチはローカルの表示で、判断を変えない。離席の機能は作らない。

タブは3つ。

- 次にやること
- いまの作業（件数）。件数は、そのタブに出している項目の数にする。
- 終わったこと

項目は3つのまとまりに分ける。空のまとまりは見出しを出さない。

- あなたの番。人が選ぶか、人が手を動かすまで進まないもの。
- 動いている。人を待たずに進んでいるもの。
- 止まっている。手を止めて待っているもの。

各項目に、次を出す。

- タイトル
- 「いま：工程名」。工程が複数あるときだけ「（n/m）」を付ける。工程の数を水増ししない。時刻が分かっているときだけ経過を書く。分からない経過は空欄にする。
- 問いなら`Q1`と問いの1行。人が手を動かす作業なら`T1`と「あなたがやること」。

中央に出している項目は、左で選択中だと分かる見た目にする。

### 中央

上に、すでに決めたことを小さい行で置く。行頭は緑のチェック。決めたことが無ければ、この行は出さない。

その下に、問いのIDと、どの項目の問いかを小さく書く。見出しは問いの1文。閉じる操作は、その問いの中身を畳むだけで、左の項目は残す。

本文は2〜3文。何が起きているか、誰が困っているか。

その下に、考えることを2〜3個置く。

選択肢はA、B、Cのカード。2つか3つにし、4つ目は別の問いに分ける。各カードに次を書く。

- 1行の説明
- トレードオフを1行
- 小さな見本。画面の略図、関係の図、コードの差分のいずれか。材料が無いカードは「図なし」と書き、空の枠を埋めない。
- 推奨は1枚。理由は札の近くに1行。理由が書けない推奨は出さない。

推奨は勧めであり、決定ではない。ラジオは、人がいま指しているカードである。推奨の札とは別に動く。初期値は推奨のカードでよい。

一番下に「メモや質問を書く」入力を置く。メモは決定ではない。

中央の問いは1つ。ほかの問いは左に並べ、選ばれるまで開かない。

### 右（根拠）

見出しは「根拠」。番号付きで、次の3つまで。無い節は作らない。

1. 何が問題か。開いたログやコードから数が取れているときだけ、小さな図を付ける。数の出所（ファイル、コマンドの結果、持ち主の言葉）を1行で書く。数が無いときは「データなし」とし、割合の図は描かない。
2. 選択肢の比較。中央のカードと対応する短い比較。
3. 見た実物。このリポジトリか、持ち主が示した範囲で確かめたものだけ。確かめていない事例は「未確認」。URLは作らない。

## 不具合のとき

原因と直し方は、別の問いにする。中央に同時に出さない。

- 一方の見出しは「原因はどれか」。もう一方は「どう直すか」。直し方は、原因が決まるまで左の「次にやること」に置いてよい。
- 右の列は、設計の3節の代わりに次を置く。再現手順。実際の結果と、期待する結果。ログと数（無ければ「データなし」）。
- 各カードに、設計の項目に加えて「確かめ方」と「影響範囲」を書く。影響範囲は、触るファイルと画面の名前。範囲が分からないときは「未確認」。
- コードを読んで分かった分岐と、それが今回の原因であることは、分けて書く。仮説には「未確認」を付ける。読んだコードと矛盾する断定はしない。

## 守ること

- 普通の言葉を先に書く。ファイル名や関数名は、そのあとバッククォートで添える。
- 画面の中央は問い1つ。ほかの問いは左に待つ。
- 推奨には理由を1行書く。決めるのは人。推奨を決定と書かない。
- 数字、事例、URLは、出所があるものだけ書く。数の出所が無いときは「データなし」。確かめていない事例は「未確認」。
- 選択肢は、コードの話なら、開いた実在のコンポーネントとファイルパスに結びつける。
- example.tsxの帯、割合（70%と30%）、経過（3分前など）、見本の不具合は作り物である。本番に写さない。本番の成果物に「見本データ」の帯は付けない。

## 出す前の点検

成果物を出す直前に、次を全部見る。1つでも欠けたら直してから出す。点検の文章はチャットに長く書かない。

- 中央の問いは1つか。ほかの問いは左にあるか。
- 推奨に、1行の理由があるか。決定済みと書いていないか。
- 作った数字、事例、URLが無いか。無いものは「データなし」か「未確認」か。
- コードの選択肢が、開いた実在のファイル名に結びついているか。
- example.tsxの見本（割合、経過、見本の不具合）を写していないか。
- 専門用語の前に、普通の言葉があるか。
- 色が上のトークンから外れていないか。
