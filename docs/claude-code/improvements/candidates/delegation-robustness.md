## 観測した事象

`robustness`は語彙の表に無いまま使われ、中身がばらばらだった。同じ原因でまとまるのは次の2つで、残りは1件ずつ。

### 事象1: 外部から来る配列・たどるループに上限が無い（3件）

- #78（PR #79）: `cause`をたどる2つのループに深さの上限が無い（nit）。
- #110（PR #112）: 了承の一覧に件数の上限と重複の拒否が無い（nit）。
- #125（PR #127）: 了承の配列に件数の上限が無い（nit）。

### 事象2: 失敗のあとに古いETagのまま送り直す（2件。閾値の下）

- #80（PR #84）: 期間の422のあと、取り直す前の再保存の`If-Match`が古い。
- #85（PR #87）: 拒否のあとも確定ボタンが押せて同じ古いETagで送る。428の「最新を取り直す」が失敗しても古いETagのまま編集に戻る。

### 1件ずつのもの

DBのエラーの扱い（#117の`lock_timeout`のSQLSTATEの誤り（must）と同時の一意違反で500（must）、ROLLBACKに失敗した接続をプールへ戻す）、利用者が分からないあいだの送信（#118・#119）、TRUNCATEを止めるトリガー（#109）、保留の保持期間（#111）、kindを見ずに拾う（#123）、`details`の欄の設定漏れ（#125 must）、同じ接続への`Promise.all`（#148）。

- **発生回数**: 事象1は異なる委譲で3件。事象2は2件。#128以降の12委譲では#148の1件（nit）だけ。
- **原因仮説**: 事象1は、設計書・試験計画に上限の数が書かれていないとき、Devinは入力の大きさを考えない。正常系の試験だけでは見つからない。
- **改善案**: 事象1だけを`devin-workflow` §2に1行足す。どの委譲にも効く予防なので「既知の指摘」の表には置かない。事象2と1件ずつのものは昇格しない（事象2はあと1件で見直す）。あわせて、語彙の表に`robustness`の定義を足し、事象2のように同じ原因で数えられるようにする。
- **変更対象**: Skill（`.agents/skills/devin-workflow/SKILL.md` §2）、語彙（`delegations/README.md`）
- **想定される副作用**: 上限の数をDevinが勝手に決めると、承認した設計に無い拒否が入る（PR #173のCodexの指摘）。設計書に数が無ければ実装せず、PRの説明に挙げる形にした（数はユーザーが決める）。
- **評価方法**: 昇格後の3委譲で、外部の配列・ループの上限の指摘が0件か（`summary`の`robustness`の中身を見る）。
- **昇格判定**: 事象1は昇格条件を満たす（異なるIssueで3件）。ほかは昇格しない。
