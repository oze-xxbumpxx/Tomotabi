## 観測した事象

### 事象1: 試験が、順番や値が運で決まるところを確定させずに確かめている

- **種類**: レビュー指摘
- **観測した事象**:
  - #117（PR #120。支払いのAPI）: 別の旅行への同時送信の実DB試験が、負ける側がロック待ちに入ったのを確かめずに勝つ側を送っていた。先に受領を読めば一意違反の経路を通らずに409で通ってしまう。
  - #125（PR #127。精算のAPI）: ロック待ちの数え方が行を絞っておらず、別の試験の待ちも数えてしまう。
  - #211（PR #214。購読の実DB試験）: 試験で作るVAPIDの秘密鍵が約256回に1回31バイトになり、まとめて409で落ちていた。最初のPRは原因を取り違えていた。
- **発生回数**: 異なる委譲で3件（#117・#125・#211）。どれもマージ前か、マージ後の追いかけのIssueで直った。
- **原因仮説**: 3件とも、試験が通ったことだけを見て、毎回同じ経路を通るかを確かめていない。#117・#125は並行の順番（ロック待ちに入ったか）、#211は乱数の値（鍵の長さ）が運で決まる。
  Devinは試験を1回か数回流して通れば完了とみなし、通った経路が狙った経路かを確かめる手順を持っていない。
- **改善案**: `.agents/skills/devin-workflow/SKILL.md`の「2. 実装」に1行足す。
  並行の順番や乱数に頼る試験は、待ちに入ったこと（ロック待ちの行を、その試験の行だけに絞って数える）や値の形（長さ・範囲）を確定させてから確かめる。
  どの委譲にも効く予防なので`devin-workflow`に置き、`review-devin-pr`の「既知の指摘」の表には書かない。
- **別案と比べた理由**:
  - 「既知の指摘」の表にAPIの実DB試験の行を足す → 3件のうち#211は並行ではなく乱数の話で、領域で絞ると漏れる。
  - 試験をくり返し流す（例: 20回）ことを完了条件にする → 256回に1回の失敗は20回では見つからず、CIの時間も増える。
- **変更対象**: Skill（`devin-workflow`）。採るかはユーザーが決める
- **想定される副作用**: 並行・乱数を使う試験で、確かめる手順が1つ増える
- **評価方法**: 適用後の委譲で`test-flakiness`の指摘が出るかを見る
- **昇格判定**: 閾値に到達（3件）。backlogにproposalで載せる
