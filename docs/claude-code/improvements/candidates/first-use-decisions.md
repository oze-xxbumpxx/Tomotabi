## 観測した事象

### 事象1: 触るファイルで分けた3つのタスクは、並行で進めても衝突しなかった

- **種類**: 成功手順
- **観測した事象**: 3つのタスクを、触るファイルが重ならないように分け、専用のクローン1つずつで同時に動かした（クローンごとのロックは#293）。3つとも`globals.css`を触る見込みだったが、関係する規則のそばに足すよう計画に書き、マージで衝突は出なかった。#301と#303はround 0でマージ可、#302はround 1でマージ可になった
- **発生回数**: このタスクで1回（3本）
- **原因仮説**: 計画の「分け方」の表に、タスクごとの主に触るファイルを書いたので、Devinが範囲の外に出なかった
- **改善案**: 並行で渡すときは、計画にタスクごとの主に触るファイルを書く。今の`create-implementation-plan`の「分け方」で足りるので、手順は変えない
- **昇格判定**: Memory留め（次の並行の委譲でも衝突が出ないかを見る）

### 事象2: 計画で指定した部品の置き場所が、lintの決まりに当たった

- **種類**: 設計の誤り
- **観測した事象**: 計画で、「（相手）」の部品`PartnerTag`を`features/trips`に置き、精算の受け渡しのカード（`features/settlement`）からも使うよう指定した。機能どうしを直接つながない決まり（`boundaries/no-cross-feature`）に当たり、#302のCIのlintが落ちた。レビューで`shared/ui`へ移すよう指摘し、Devinが直した。Devinは、Issueの指定と決まりが両立しないとコミットの説明に書いていた
- **発生回数**: 1回
- **原因仮説**: 設計と計画を書くとき、使う側（3つの画面）の置き場所を見たが、部品を置く場所から読めるかをlintの決まりで確かめなかった
- **改善案**: 2つ以上の機能（`features/*`）から使う部品は`shared/`に置く、と計画を書くときに確かめる。1回だけなので、手順にはまだ足さない
- **昇格判定**: Memory留め（同じ誤りが2回目なら`create-implementation-plan`に1行足す）

### 事象3: 試験計画に、名前が空の相手の場合が無かった

- **種類**: 要件見落とし
- **観測した事象**: 試験計画は「参加者の一覧が取れない」場合だけを書いていた。参加者の一覧に居ても表示名が空のときに「相手（相手）」と出る場合が漏れていて、round 0のレビューで見つけた
- **発生回数**: 1回
- **原因仮説**: 表示名の決まり（`displayNameOf`は空なら「相手」を返す）を、取得の失敗と同じものと見ていた
- **改善案**: 名前を出す直しでは、`displayNameOf`が「相手」を返す条件（一覧に無い・表示名が空）をすべて試験の観点に書く。1回なので手順は変えない
- **昇格判定**: Memory留め

### 事象4: 結合検証環境のデータが足りず、3か所を見られなかった

- **種類**: 検証の不足
- **観測した事象**: 取り消した支払いが環境のどの旅行にも無く、履歴の取り消しの行を見られなかった。福岡旅行は精算が0円で、ホームと精算の受け渡しのカードの「（相手）」も見られなかった。明るい画面も見ていない。共有の点検用のデータを変えないよう、自分で支払いを取り消すのはやめた
- **発生回数**: 1回
- **原因仮説**: 試験計画の「結合検証環境で見て確かめること」に、見るために要るデータ（取り消した支払い・受け渡しがある旅行）を書いていなかった
- **改善案**: 結合検証環境で見る項目には、要るデータと、無いときに誰が作るかを書く。残りの3か所は`logs/2026-10-27.md`の次回やることに入れた
- **昇格判定**: Memory留め

### 事象5: 推奨と違う答えが1問あった

- **種類**: ユーザーの判断
- **観測した事象**: 精算の画面の「支払いを記録」で、推奨の「出さない」ではなく「枠だけの小さなボタン」が選ばれた。理由は聞いていない
- **発生回数**: 1回
- **原因仮説**: 推奨は精算の画面の主な操作を1つにすることを優先したが、記録し忘れに気づいた場所からすぐ記録できることの重みを低く見ていたかもしれない（推測）
- **改善案**: 主な操作を消す案を推奨するときは、消したときにほかの画面へ移る手間の重みを、選択肢の欠点に具体的に書く
- **昇格判定**: Memory留め
