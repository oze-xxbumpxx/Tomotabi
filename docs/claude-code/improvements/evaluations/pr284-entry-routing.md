## 結果

### 速さと量は前後でほとんど同じ

途中終了の4回を除いた各版18回の合計は次のとおり。

| 指標     | before | after | 差   |
| -------- | ------ | ----- | ---- |
| 時間     | 673秒  | 729秒 | +8%  |
| 費用     | $7.44  | $7.65 | +3%  |
| トークン | 5.37M  | 5.76M | +7%  |
| ターン数 | 140    | 159   | +14% |

afterで増えた分は、L2/L3の依頼（3〜5）で`develop-feature`、`classify-change`、`ask-questions`を読む分だと読める。依頼4と5の2回目は、afterだけ40〜60秒かかった。各版2回ずつなので、この差が揺れの範囲を超えているかは分からない。

### どちらの版も子エージェントを起動しなかった

40回のどれでも、`Agent`ツールは一度も呼ばれていない。beforeの設計では、L2/L3はorchestratorから設計役へ渡す決まりだった。しかし実際には、メインのセッションが自分で問いを出して止まっていた。PR #284は、実際の動きを文書の側に合わせた変更と言える。記事が挙げる「受け渡しのたびに中身が薄くなる」問題は、この計測の範囲では起きていなかった。

### afterでは入口のスキルが読まれた

| 依頼                      | before                                          | after                                                                                                                 |
| ------------------------- | ----------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 3〜5（L2/L3の追加・変更） | スキルを読まずに問いを出した（6回）             | 6回とも`develop-feature`をSkillで読んだ。`classify-change`をReadで開いたのは5回。`ask-questions`まで開いたのは2回だけ |
| 7（内部の関数分割）       | `classify-change`を読み、L1と判定して書き換えた | `develop-feature`、`classify-change`、`implement-change`を読み、L1と判定して書き換えた                                |
| 9（DevinのPR）            | 2回とも`review-devin-pr`                        | 2回とも`review-devin-pr`                                                                                              |

依頼3〜5では、どの回も承認前にアプリのコードを変えていない。afterで`ask-questions`を開かなかった4回も、問いは出していた。ただ、この4回は問いの形（工程と優先度の札、推奨、選択肢）がスキルの手順どおりかを確かめていない。

### 両方の版で同じだったこと

- 依頼2と8（調べるだけ）は、ファイルを変えていない。依頼8はどちらの版も`Explore`を使わず、自分で`Grep`して2ターンで終えた。
- 依頼6（READMEだけ）は`README.md`だけを直し、検証役を起動していない。beforeの1回は日次ログにも追記した。
- 依頼7は、両方の版ともL1と判定して`apps/api`の2ファイルを書き換えた。確認一覧の期待は「L2なら設計から」で、L1と判定するのも決まりの範囲に入る。この依頼文では、L1かL2かの判断を評価できない。

## 総合判定

- **判定**: 入口の確認では採用してよい。作業全体の効果は未判定（証拠不足）
- **理由**: 入口の確認で比べられた指標に、悪化したものは無い。時間・費用・トークンの差は3〜8%で、各版2回では揺れと区別できない。設計承認より後の工程は、[確認一覧の「成果物まで確かめる比較」](../../../../.claude/evals/folded-loop-checklist.md#成果物まで確かめる比較)を、人が承認を出す形で回すまで判断しない。

次に回すときに直すことが3つある。

1. 依頼1には直す画面と文言、依頼7には対象の関数とL2と判定させたい理由を書く。L1かL2かの判断と、`implement-change`まで届くかを測れるようにするため。
2. 依頼9は`gh pr view`と`gh pr diff`を許可する。依頼10は、pushできるコミットがある一時リポジトリで回す。
3. 回数を各版3回以上にし、使用量に余裕のある時間に回す。
