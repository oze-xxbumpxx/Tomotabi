# 論点の記録: 結合検証環境

- 機能名: integration-env
- 確認のページ: https://claude.ai/artifact/Fk5mC9LbL7Gp6eP1qUj481
- 進み具合: docs/discussions/integration-env.progress.json

## 背景

アプリの機能は通知まででそろった。次は、本番と同じVercel・Neonの上に、架空のデータを入れた検証用の環境を作り、手元では確かめられないことを確かめる。確かめるのは、画面からAPIへの転送とCookie、Googleログインと二人の制限、Neonへの接続と休止からの復帰、実際の端末での通知、無料枠の使い方。ここで見つかった問題を、公開準備の前に直す。

## 前提

- 構成は設計資料（詳細設計08「Vercel＋Neonのデプロイと無料枠運用」）のとおり、Vercel Hobby（画面とAPIの2プロジェクト）とNeon Free（検証用のプロジェクト）。2026-10-12にユーザーがCloudflareと比べてこの構成を選んだ。
- 費用はかけない。無料枠を超えそうなら、課金ではなく検証を止める（詳細設計08の2節）。
- アカウントの作成、管理画面での設定、秘密情報（DBの接続URL、Better Authの鍵、Googleのsecret、VAPIDの秘密鍵）の登録は、ユーザーが行う。Claude Codeは秘密情報の値を見ない。Claude Codeは手順書と、アプリ側の作り（NestJSのVercelの入口、通知の送信の`waitUntil`など）を用意する。
- 検証用の環境には架空のデータだけを入れる。本番のデータや実際の金銭の受け渡しは使わない。
- Vercel Hobbyは個人の非商用の利用に限る。二人で使う今の用途は当てはまる。

### Vercelの実行場所とNeonの地域をどこにするか

<!-- id: regions -->

- 工程: 要件
- 種類: 設計
- 優先度: 高
- 状態: 決定
- なぜ今: Neonのプロジェクトを作るときに地域を決め、あとから変えられない。ユーザーは、Vercel＋Neonの別のアプリで、シンガポールのときに毎回の操作の描画が遅れたことがある（2026-10-12）。
- 根拠: 詳細設計08の3節の初期配置案は、Vercelをsin1、NeonをAWS Singapore（ap-southeast-1）にそろえ、国内からの速さは実機で測るとしている。Neonの地域に東京は無い（2026-10-12に公式の地域の一覧で確かめた）。Vercelの関数は、設定しなければアメリカ東部（iad1）で動く。Tomotabiの保存は1回の操作でDBに何度も問い合わせるので、関数とDBを離すと遅くなる。
- 選択肢:
  - A) 検証用の環境はシンガポールで作り、遅れを距離・Neonの休止・関数の起動に分けて測ってから、本番の地域を決める。距離が原因なら、本番を作る前に、東京の地域があるPostgreSQLのサービスへの変更をADRで検討する
    - 利点: 原因を確かめてから決められ、検証用のDBは架空のデータなので作り直しても困らない
    - 欠点: 本番の地域が決まるのが、測ったあとになる
  - B) 最初から、東京の地域があるPostgreSQLのサービスに変える
    - 利点: 距離が原因なら、最初から速い
    - 欠点: DBのサービスを変えるADRと設計資料の見直しが先に入り、休止や起動が原因なら直らない
  - C) 関数だけ東京にし、Neonはシンガポールのまま
    - 利点: 設定だけで済む
    - 欠点: DBへの問い合わせのたびに東京とシンガポールを往復し、かえって遅くなる
- 推奨: A（遅れの原因を分けて測ってから決められる）
- 決定: A
- 推奨と同じか: 同じ
- 理由: 別のアプリでは、毎回の操作が遅かった（2026-10-12）
- 選ばなかった理由: B（原因を確かめる前にDBのサービスを変えることになり、休止や起動が原因なら直らないため）。C（DBへの問い合わせのたびに往復が増え、かえって遅くなるため）
- 前の決定: 仮決定のA（設計資料の初期案どおり、どちらもシンガポール）
- 反映先: docs/requirements/integration-env.md
- 決めた日: 2026-10-12

### 検証が終わったあと、検証用の環境を残すか

<!-- id: keep-test-env -->

- 工程: 運用
- 種類: 設計
- 優先度: 中
- 状態: 仮決定
- なぜ今: 公開後の変更をどこで確かめるかと、無料枠の使い方が変わる。
- 根拠: 詳細設計08の3節は「固定の結合検証環境」を、本番と並べて置くとしている。
- 選択肢:
  - A) 残す。必要なときだけデプロイして使う
    - 利点: 公開後の変更も、本番の前に同じ環境で確かめられる
    - 欠点: 使っていなくても、プロジェクトとDBの枠を1組分持ち続ける
  - B) 確かめ終わったら消す
    - 利点: 枠を本番だけに使える
    - 欠点: 次に確かめたいとき、作り直す手間がある
- 推奨: A（設計資料のとおり固定で置き、使わないあいだは止めておけば無料枠をほとんど使わない）

### 公開前の確認（OPS-01〜18）のうち、この段階でどれを確かめるか

<!-- id: ops-scope -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- なぜ今: この段階の完了の条件が決まる。
- 根拠: 詳細設計10は、この段階を「架空データでCookie・認可・Push・端末復帰を実検証。無料枠消費を測定」、公開準備を「OPS-01〜18を実行し根拠を記録」としている（`運用設定と公開チェック.md`の3節）。
- 選択肢:
  - A) 環境で初めて確かめられるもの（転送・Cookie・キャッシュ・Googleと二人の制限・DBの接続と休止・同時操作・実行ロール・通知・実機の画面・利用量。OPS-03〜11・17・18）をこの段階で、残り（プランと課金の制御・環境の分離・公開の順番・dumpと復元・巻き戻し・完全停止・秘密とログ）を公開準備で
    - 利点: この段階では環境の動きに集中でき、本番の準備に関わるものは本番の環境で確かめられる
    - 欠点: 公開準備の確認が多く残る
  - B) OPS-01〜18を全部この段階で確かめる
    - 利点: 公開準備が軽くなる
    - 欠点: 本番の環境が無いと確かめられない項目（本番への公開の順番など）まで、検証用の環境で代わりに確かめることになる
- 推奨: A（設計資料の段階の分け方どおりで、本番に関わる確認を本番の環境で行える）
