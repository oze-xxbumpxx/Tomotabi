# 論点の記録: ToDoのカテゴリ分けと予定との関連付け

- 機能名: todo-organize
- 確認のページ: https://claude.ai/artifact/RkrTGDx64nX4sjzjk8zJAT
- 進み具合: docs/discussions/todo-organize.progress.json

## 背景

ToDoを項目ごとに分け、予定に関連付けたい、とユーザーから要望があった（2026-11-14）。今のToDoは名前とメモだけを持ち、予定とつながるのは「予定にする」で完了にしたときに限られる。機能を増やした案をイメージ図（https://claude.ai/artifact/LRsVh7g3KmuPN4bfVNtXrE ）で出し、ユーザーが図と画面の言葉を採用した（2026-11-14）。この記録では、図だけでは決まらない決まりを決める。

## 前提

- イメージ図の採用で決まったこと。二人が名前を付けて作るカテゴリでToDoを分ける。ToDoに担当（自分・相手・未定）と期限（日付）を付けられる。リストを「自分の担当」「期限が近い」で絞れる。
- 未完了のToDoも、しおりの予定1つと関連付けられる。1つの予定には複数のToDoを関連付けられる。
- 予定の詳細に「関連するToDo」の欄を出し、その場で完了にでき、ToDoを追加できる。
- リストはカテゴリごとの欄にし、欄の中は未完了を上、完了を下に並べる。今の「まだのもの」「済んだもの」の2つの欄はやめる。
- 画面の言葉はイメージ図のとおり（カテゴリ・関連する予定・関連するToDo・期限・担当・未定）。
- 2026-11-08に対象外とした「期日・担当者・種類の分類」（docs/requirements/trip-todo.md「対象外」）を、この機能で対象に入れる。
- 変更レベルはL3。カテゴリの表とAPIを新しく作り、ToDoの表に列を足すため。

## 論点

### 完了の印を外したとき、予定との関連付けを残すか

<!-- id: reopen-keeps-plan -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 今は外すと予定とのつながりも消す（docs/requirements/trip-todo.md F-12）。未完了でも関連付けられるようにするので、この決まりを変えるかを決めないと、完了の付け外しの要件を書けない。
- 根拠: `apps/api/src/modules/planning/domain/todo.ts:66`（`reopen`が`planId`をnullにする）。
- 選択肢:
  - A) 残す。関連付けは、自分で外すまで変わらない
    - 利点: 押し間違えて完了にしたあと戻しても、関連付けをやり直さずに済む
    - 欠点: 今の決まり（F-12）を変える
  - B) 今のまま消す
    - 利点: 今の決まりを変えない
    - 欠点: 未完了でも関連付けられるのに、完了を外すと消えるので、決まりが食い違う
- 推奨: A（関連付けと完了を別のものとして扱えば、二人が覚える決まりが1つで済む）

### 「新しく予定を作る」でToDoから予定を作ったとき、そのToDoを完了にするか

<!-- id: plan-from-todo-completes -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 今は予定を保存するとToDoを完了にする（F-10）。関連付けが完了と別になるので、予定を作っただけで完了にするかを決めないと、予定を作る流れの要件を書けない。
- 根拠: docs/requirements/trip-todo.md F-10、`apps/api/src/modules/planning/usecase/create-plan.usecase.ts`（予定の保存と同じ書き込みで完了にする）。
- 選択肢:
  - A) 今のまま完了にする
    - 利点: 「行きたい所を予定に入れた」ことが、完了の印でわかる
    - 欠点: 「切符を買う」のような用事は、予定を作っただけでは済んでいないのに完了になる
  - B) 完了にしない。作った予定と関連付けるだけにする
    - 利点: 完了は「実際に済んだ」の意味だけになり、予定の詳細の「関連するToDo」で残りを確かめられる
    - 欠点: 今の決まり（F-10）を変える。予定に入れたToDoは自分で完了にする
- 推奨: B（関連付けが残るので、予定にしたことは行の「10/13 の予定」でわかる。完了は済んだときに付けるほうが意味がそろう）

### カテゴリを削除したとき、中のToDoをどうするか

<!-- id: category-delete -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 削除の決まりで、確かめの画面の文と、相手が同時に追加したときの扱いが変わる。
- 根拠: ToDoの削除は戻せない（F-08）。カテゴリには最大200件のToDoが入りうる（B-04）。
- 選択肢:
  - A) ToDoは残し、「未分類」に移す
    - 利点: カテゴリを消してもToDoが無くならない
    - 欠点: 未分類の欄が要る
  - B) 中のToDoも一緒に削除する
    - 利点: 使い終わった「持ち物」をまとめて消せる
    - 欠点: 1回の押し間違いで、相手が書いたToDoまで消える
  - C) 空のカテゴリだけ削除できる
    - 利点: 決まりが一番少ない
    - 欠点: 消す前に、中のToDoを1件ずつ移すか消すことになる
- 推奨: A（戻せない削除でToDoが巻き込まれない。まとめて消したくなったら、あとで足せる）

### 旅行を作ったとき、カテゴリを最初から用意しておくか

<!-- id: category-initial -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 最初の画面の見え方と、今ある旅行のToDoをどの欄に出すかが変わる。
- 根拠: 今ある旅行のToDoにはカテゴリが無い。イメージ図の「出発前の準備・行きたい所・持ち物」は例として描いた。
- 選択肢:
  - A) 用意しない。カテゴリの無いToDoは「未分類」の欄に出し、二人が要るカテゴリを作る
    - 利点: 今ある旅行のToDoがそのまま見え、使わないカテゴリが並ばない
    - 欠点: 最初はカテゴリが1つも無く、分け方を自分で考える
  - B) 「出発前の準備・行きたい所・持ち物」の3つを最初から入れておく（名前の変更・削除はできる）
    - 利点: 開いてすぐ分けて書ける
    - 欠点: 今ある旅行にも足す移し替えが要り、使わない欄が出る
- 推奨: A（今ある旅行をそのまま扱え、カテゴリを使わない人の画面は今と変わらない）

### カテゴリやToDoの並び順を、自分で変えられるようにするか

<!-- id: reorder -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 並べ替えを入れると、順番を持つ列と、二人が同時に並べ替えたときの決まりが要り、作る量が変わる。
- 根拠: 2026-11-08に並べ替えは対象外と決めた（docs/discussions/trip-todo.md「リストの並び順を自分で変えられるようにするか」）。カテゴリが増えると、作った順のままでは上に置きたいものを選べない。
- 選択肢:
  - A) どちらも作った順のまま
    - 利点: 作る量が一番少ない
    - 欠点: 「出発前の準備」を一番上に置きたくても、作り直すしかない
  - B) カテゴリだけ並べ替えられる。ToDoは追加した順
    - 利点: 欄の順は選べて、ToDoの順番の決まりは増えない
    - 欠点: カテゴリの順番の保存と、同時に変えたときの決まりが要る
  - C) カテゴリもToDoも並べ替えられる
    - 利点: 大事なToDoを上に置ける
    - 欠点: 作る量が一番多い。期限と担当で絞れるので、使う場面は少ない（推測）
- 推奨: B（カテゴリは数個なので順を選びたくなる。ToDoは期限と絞り込みで探せる）

### 期限が近づいたとき、担当の人に通知を送るか

<!-- id: due-notify -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 通知を送るなら、決まった時刻に動く処理が要り、作る範囲が大きく変わる。
- 根拠: ToDoでは通知を送らないと決めている（F-15）。今の通知は、相手の操作をきっかけに送るものだけ。
- 選択肢:
  - A) 送らない。リストとホームの画面の印（「10/5まで」「あと3日」）だけにする
    - 利点: 今の通知のしくみに手を入れずに済む
    - 欠点: アプリを開かないと期限に気づかない
  - B) 期限の前の日に、担当の人へ通知を送る
    - 利点: 開かなくても気づける
    - 欠点: 時刻で動く処理を新しく作る。今のアプリには無い
- 推奨: A（まず画面の印で使い、気づけなくて困ったら通知を足す）

### 担当を付けた・変えたとき、相手に通知を送るか

<!-- id: assign-notify -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- なぜ今: ToDoの通知を送らない決まり（F-15）を続けるかを書くため。

    - 欠点: 通知の種類が増える
- 推奨: A（二人で話して決めることが多く、今の決まりを変えるほどの理由がまだ無い）

### 関連付けた予定を取りやめたとき、ToDoをどうするか

<!-- id: cancelled-plan -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- なぜ今: 取りやめた予定の表示を要件に書くため。
- 根拠: 今は「取りやめた予定」と出し、ToDoは変えない（F-12・F-16）。
- 選択肢:
  - A) 今と同じ。ToDoは変えず、行に「取りやめた予定」と出す
    - 利点: 予定の取りやめがToDoを書き換えない
    - 欠点: 関連付けは自分で外す
  - B) 関連付けを自動で外す
    - 利点: 取りやめた予定が行に残らない
    - 欠点: 取りやめを戻しても関連付けは戻らない
- 推奨: A（今の決まりのままで、取りやめを戻したときも関連付けが残る）

### 「期限が近い」を、何日前からにするか

<!-- id: due-soon-days -->

- 工程: 要件
- 種類: 画面
- 優先度: 中
- 状態: 仮決定
- なぜ今: 絞り込みと「あと3日」の印を出す条件を書くため。
- 根拠: イメージ図の「あと3日」。
- 選択肢:
  - A) 期限まで3日以内と、期限を過ぎた未完了のToDo
    - 利点: 週末に準備する用事を前もって拾える
    - 欠点: 3日が合わない旅行もある
  - B) 7日以内
    - 利点: 早めに気づける
    - 欠点: 出発の前は、ほとんどのToDoが当てはまる
- 推奨: A（イメージ図のとおり。使ってみて合わなければ日数だけ変えられる）

### カテゴリの数と名前の長さの上限を、いくつにするか

<!-- id: category-limits -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- なぜ今: 境界の条件を書くため。
- 根拠: ToDoは名前100字・1つの旅行に200件（B-02・B-04）。
- 選択肢:
  - A) 1つの旅行に20個まで、名前は30字まで
    - 利点: 画面の1行に収まり、数も足りる
    - 欠点: 30字を超える名前は付けられない
  - B) 上限を決めない
    - 利点: 決まりが無い
    - 欠点: 一覧の大きさが決まらず、画面が崩れる名前を防げない
- 推奨: A（二人の旅行で20個を超えることは考えにくい）
