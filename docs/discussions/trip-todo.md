# 論点の記録: 旅行でしたいことのToDoリスト

- 機能名: trip-todo
- 確認のページ: https://claude.ai/artifact/FDP4ztTqcaucUUKriM78Ty
- 進み具合: docs/discussions/trip-todo.progress.json
- v3の版: 9db5634a

## 背景

旅行ごとに「したいこと」をToDoリストにまとめたい、とユーザーから要望があった（2026-11-08）。今のアプリには、日付の決まった予定（しおり）と、支払い・達成・予約の記録しかない。日付の決まっていない「やりたいこと」を置く場所は無い。この記録では、リストに何を書くか、予定とどうつなぐか、どの画面から開くかを決める。

## 前提

- 使うのは本人とパートナーの二人だけ。旅行の参加者はこの二人で固定（v3の画面一式の概要）。
- 予定には日付が必須（`apps/api/src/infrastructure/database/schema/planning.ts:111`）。種類は場所・食べ処・買い物・宿・移動の5つ（`apps/api/src/modules/planning/domain/plan-kind.ts:1`）。
- 下のタブはホーム・しおり・履歴・精算の4つと「支払いを記録」（`apps/web/src/features/trips/ui/trip-tab-bar.tsx:25`）。v3にToDoの画面は無い。
- 設計資料は「持ち物」を後で扱う領域として残している（詳細設計「実装順序」）。中身の仕様はまだ無い。
- 新しい表・API・画面が要るので、変更の大きさはL3とする。

## 論点

### リストに書くのは、どんな「したいこと」か

<!-- id: todo-scope -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 書くものによって、予定とのつなぎ方・項目・置き場所が変わる。
- 根拠: 要望は「旅行でしたいことをToDoリストでまとめたい」。行きたい場所のような旅先でしたいことと、宿の予約やパスポートの準備のような出発前の用事の、どちらとも読める。
- 選択肢:
  - A) 旅先でしたいこと（行きたい場所・食べたいもの・買いたいもの・体験）だけ
    - 利点: 予定の候補として扱え、予定への移し方を素直に決められる
    - 欠点: 出発前の用事は別の場所に書くことになる
  - B) 出発前の準備の用事（予約する・両替する・荷造りする）だけ
    - 利点: 完了の印を付ける使い方がはっきりする
    - 欠点: 「したいこと」という言葉から離れる
  - C) どちらも区別せず、一つのリストに書く
    - 利点: 何でも書けて、使う人が迷わない
    - 欠点: 予定に移せるものと移せないものが混ざり、画面の説明が要る
- 推奨: C（二人で使う小さなリストなので、書くものを分けるより、何でも書けるほうが使い始めやすい。予定に移すかどうかは項目ごとに選べばよい）

### したいことを、日付を決めて予定に移せるようにするか

<!-- id: todo-to-plan -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 08
- なぜ今: 移せるなら、予定の追加の画面と予定の作りに手が入り、作る量が大きく変わる。
- 根拠: 予定は日付が必須で、日付の決まらないものは今は置けない（`planning.ts:111`）。
- 選択肢:
  - A) 移せない。ToDoリストは予定と別のもの
    - 利点: 予定のしくみに手を入れず、早く作れる
    - 欠点: 予定にするときは、同じ名前をもう一度打つ
  - B) 「予定にする」を押すと、名前を入れた状態で予定の追加の画面を開く。保存したらToDoに完了の印を付ける
    - 利点: 打ち直しが要らず、どのしたいことを予定にしたかがわかる
    - 欠点: 予定の追加の画面に、ToDoから来たときの流れを足す
  - C) Bに加えて、予定とToDoを結び付け、予定を取りやめたらToDoを未完了に戻す
    - 利点: 予定とToDoの状態がずれない
    - 欠点: 結び付きの持ち方と戻すときの決まりが要り、作る量が一番多い
- 推奨: B（打ち直しを省けて、予定のしくみは名前を受け取るだけで済む。取りやめたあとの戻し方は、使ってみて困ったら足せる）

### ToDoリストをどこから開くか

<!-- id: todo-entry -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 08, v3 03
- なぜ今: 下のタブはv3で4つと決まっている。置き場所で、ほかの画面の作りを変えるかが決まる。
- 根拠: `trip-tab-bar.tsx:25`。v3にToDoの画面は無い。
- 選択肢:
  - A) 下のタブに「ToDo」を足して5つにする
    - 利点: どの画面からも一度で開ける
    - 欠点: v3のタブ構成から外れ、タブ1つあたりの幅が狭くなる
  - B) しおりの画面の上に「したいこと」への入口を置き、リストは別の画面にする
    - 利点: 予定と並べて見られ、予定に移す流れと近い。タブは変えない
    - 欠点: ホームからは2回押す
  - C) ホームに「したいこと」の欄（未完了の数件と「すべて見る」）を置き、リストは別の画面にする
    - 利点: 旅行を開いてすぐ目に入る
    - 欠点: ホームの欄が増え、今日の予定や最近の記録が下に押される
- 推奨: B（タブを変えずに済み、日付を決めて予定に移すときにしおりと行き来しやすい）

### 二人のどちらが追加・完了したかを残し、相手に通知するか

<!-- id: todo-notify -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 高
- 状態: 回答待ち
- なぜ今: 通知を送るなら通知の種類を足し、通知の設定の画面にも項目が増える。
- 根拠: 達成・予約・支払いは、記録すると相手に通知が届く（`apps/api/src/modules/notification/`）。
- 選択肢:
  - A) 誰が追加・完了したかは残して画面に出す。通知は送らない
    - 利点: 相手の端末を鳴らしすぎない。作る量が少ない
    - 欠点: 相手が足したことに、リストを開くまで気づかない
  - B) 追加と完了のたびに相手に通知する
    - 利点: 相手の動きにすぐ気づける
    - 欠点: 旅行前にまとめて書くと通知が続けて届く
  - C) 誰がしたかも残さず、通知もしない
    - 利点: 一番単純
    - 欠点: どちらが書いたかがわからない
- 推奨: A（旅行前にまとめて書く使い方では、通知が続くとうるさい。誰が書いたかは画面で足りる）

### 一つのしたいことに、名前のほかに何を書けるか

<!-- id: todo-fields -->

- 工程: 要件
- 種類: 画面
- 優先度: 中
- 状態: 仮決定
- なぜ今: 項目によって、追加の画面の大きさと表の列が決まる。
- 根拠: 予定は名前・種類・日付・時刻・メモを持つ（`planning.ts:109`）。
- 選択肢:
  - A) 名前だけ（最大100字）
    - 利点: 一行で素早く足せる
    - 欠点: 補足を書けない
  - B) 名前とメモ
    - 利点: お店のURLや理由を残せる
    - 欠点: 追加の画面が一行では済まない
  - C) 名前・メモ・種類（予定と同じ5つ）
    - 利点: 予定に移すときに種類も引き継げる
    - 欠点: 種類に当てはまらない用事（両替など）で迷う
- 推奨: B（名前は一行で足せるようにし、メモは開いたときだけ書く。種類は予定に移すときに選べば足りる）

### リストの並び順を自分で変えられるようにするか

<!-- id: todo-order -->

- 工程: 要件
- 種類: 画面
- 優先度: 中
- 状態: 仮決定
- なぜ今: 並べ替えを入れると、順番の持ち方と同時に並べ替えたときの決まりが要る。
- 根拠: 予定は日付と時刻で並ぶ。並べ替えの操作はアプリにまだ無い。
- 選択肢:
  - A) 並べ替えなし。未完了を上、完了を下にし、それぞれ足した順
    - 利点: 作りが単純で、二人が同時に触っても順番がずれない
    - 欠点: 大事なものを上に置けない
  - B) 長押しで動かして並べ替えられる
    - 利点: 大事なものを上に置ける
    - 欠点: 二人が同時に並べ替えたときの決まりと、スマートフォンでのドラッグの操作が要る
- 推奨: A（まず単純に作り、困ったら並べ替えを足す）

### 完了したもの・要らなくなったものをどう扱うか

<!-- id: todo-delete -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- なぜ今: 消せるかどうかで、間違えて消したときの戻し方が変わる。
- 根拠: 予定は消さずに「取りやめ」にする（`planning.ts:114`）。
- 選択肢:
  - A) 完了の印は付け外しでき、要らなくなったものは確認のうえ削除できる
    - 利点: リストが散らからない
    - 欠点: 消したものは戻せない
  - B) 予定と同じく、削除せず「取りやめ」にして薄く表示する
    - 利点: 間違えても戻せる
    - 欠点: リストに要らないものが残る
- 推奨: A（ToDoはお金の記録と違い、消しても精算などに響かない。確認を挟めば足りる）

### 旅行が終わったあともリストを編集できるか

<!-- id: todo-after-finish -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 低
- 状態: 後の工程へ
- なぜ今: 旅行の終了後に何を止めるかは、ほかの記録の決まりとそろえる必要がある。
- 根拠: 旅行には手動の開始・終了がある（v3 16〜18）。

### ToDoの表をどのモジュールに置くか

<!-- id: todo-module -->

- 工程: 設計
- 種類: 設計
- 優先度: 中
- 状態: 後の工程へ
- なぜ今: 予定のモジュール（planning）に置くか、新しいモジュールにするかで、予定に移す流れの作りが変わる。
- 根拠: `apps/api/src/modules/`の6区分。
