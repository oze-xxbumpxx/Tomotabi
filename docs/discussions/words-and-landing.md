# 論点の記録: 画面の言葉をそろえ、旅行を開いたときの画面と受け渡しの確認のボタンを直す

- 機能名: words-and-landing
- 確認のページ: https://claude.ai/artifact/Tj3kxZGbxceys6xXP65vtW
- 進み具合: docs/discussions/words-and-landing.progress.json
- v3の版: 9db5634a

## 背景

初めて使った人のレビューで、同じものを画面ごとに別の言葉で呼んでいると指摘された（#249）。予定の詳細のボタンは「予約済みを記録」なのに、バッジと記録の絞り込みは「予約」になっている。下のタブの「しおり」と「記録」の違いも、名前だけでは伝わらない。旅行を開くと、今日の様子がわかるホームではなく、しおりの画面が開く。精算の主ボタン「受け渡しを確認する」については、押すと何が起きて戻せるのかがわからないという指摘があった（#248）。この記録では、言葉と開く画面を決める。決めた言葉は、後で直す予定の詳細のボタン（#252）と、細かい点のまとめ（#253）でも使う。

## 前提

- 画面の上では、すでに「予定」とだけ書いている。「プラン」と出している画面は無い（`apps/web/src`を検索して確かめた）。URLの`/plans`は変えない。
- 精算の主ボタンを押すと、その時点の対象と金額を固定した「受け渡しの確認」が作られ、その画面に進む（`apps/web/src/screens/settlement/settlement-screen.tsx:61`）。この時点では、まだ何も精算として記録されない。精算として記録されるのは、確認の画面で「受け渡し完了を記録」を押したときになる。このボタンには、押す前の確認がすでにある（「このアプリは送金を行いません」と書いてある）。
- 旅行を開く入口は3か所ある。旅行一覧の行（`trip-row.tsx:19`）、旅行を作った直後（`trip-new-screen.tsx:72`）、支払いを保存した直後（`payment-form-screen.tsx:246`）。3か所とも、今はしおりを開く。

## 論点

### 旅行を開いたときに、最初にどの画面を出すか

<!-- id: landing-screen -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 03, v3 08
- なぜ今: 旅行一覧の行と旅行を作った直後の行き先が、これで決まる。下のタブの並びも、最初の画面に合わせて見直すことになる。
- 根拠: #249。設計資料には、旅行を開いたときにどの画面を出すかが書かれていない。v3の画面一式は、ホーム（03）をタブの先頭に置いている。
- 選択肢:
  - A) ホームを出す。しおりは、日程を見たいときにタブから開く
    - 利点: 今日の予定と精算の額がすぐに見え、タブの先頭とも合う
    - 欠点: 旅行を作った直後に予定を足したい人は、タブを1回押す手間が増える
  - B) 今のまま、しおりを出す
    - 利点: 作り直しが要らず、予定を足す画面にすぐ届く
    - 欠点: 予定がまだ少ないうちは、ほとんど空の画面が開く
  - C) 旅行一覧からはホーム、旅行を作った直後はしおりを出す
    - 利点: 作った直後は予定を足し、2回目からは今日の様子を見る、という使い方に合う
    - 欠点: 入口ごとに開く画面が変わり、決まりが1つ増える
- 推奨: C（作った直後は予定がまだ0件なので、ホームを出しても見るものが無い。2回目からはホームが役に立つ）

### 予定の詳細のボタンと、バッジ・絞り込みの言葉を、どちらにそろえるか

<!-- id: reserve-achieve-words -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 09, v3 10
- なぜ今: 予定の詳細のボタン（#252）と、記録の一覧の言葉が、ここで決まる。
- 根拠: ボタンは「予約済みを記録」「達成を記録」（`plan-detail-screen.tsx:419`・`:432`）。記録の絞り込みは「予約」「達成」（`record-filters.tsx:29`・`:34`）。v3の09は、予約の行を「予約済み」と書いている。
- 選択肢:
  - A) ボタンを「予約を記録」にする。バッジと絞り込みは「予約」「達成」のまま
    - 利点: ボタン・バッジ・絞り込みの3か所が同じ言葉になり、直す箇所はボタン1つで済む
    - 欠点: 「予約を記録」は、これから予約するように読める人もいる
  - B) バッジと絞り込みを「予約済み」にする。ボタンは「予約済みを記録」のまま
    - 利点: 済んだことの記録だと、はっきりわかる
    - 欠点: 絞り込みのボタンが長くなり、狭い画面で4つ並べにくい
- 推奨: A（「達成を記録」と同じ形になり、直すのはボタン1つで済む。予約が済んだことは、ボタンの下の一行の説明（#252で足す）で補う）

### 下のタブの「記録」を、何という名前にするか

<!-- id: records-tab-name -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 10
- なぜ今: タブの名前は、記録の一覧の見出しと、ホームの「記録一覧へ」のリンクにも使う。#253の細かい点の直しも、この名前に合わせる。
- 根拠: #249。「達成を記録」「支払いを記録」のようにボタンにも「記録」を使うので、タブの「記録」が何の一覧なのかが伝わりにくい。記録の一覧には、支払い・達成・予約・取り消しが並ぶ。
- 選択肢:
  - A) 「履歴」にする
    - 利点: 起きたことが新しい順に並ぶ画面だとわかり、ボタンの「記録」とぶつからない
    - 欠点: 支払いの一覧を探す人には、「履歴」の中に支払いがあると伝わりにくい
  - B) 「記録」のまま、記録の一覧の見出しの下に一行の説明を足す
    - 利点: 作り直しが少なく、v3の画面一式と同じ名前のまま
    - 欠点: タブだけを見たときの分かりにくさは残る
  - C) 「支払い・履歴」にする
    - 利点: 支払いの一覧への入口だとわかる
    - 欠点: 4つのタブの中で1つだけ長くなり、狭い画面で文字が詰まる
- 推奨: A（ボタンの「記録」とぶつからず、2文字のまま並べられる。支払いだけを見たいときのために、絞り込みの「支払い」はそのまま残す）

### 下のタブの「しおり」との違いを、どう伝えるか

<!-- id: itinerary-tab-hint -->

- 工程: 要件
- 種類: 画面
- 優先度: 中
- 状態: 仮決定
- 画面: v3 08
- なぜ今: 記録のタブの名前を変えると、しおりとの違いが変わる。2つまとめて決めたい。
- 根拠: #249。v3の画面一式は「しおり」を使っている。
- 選択肢:
  - A) 「しおり」のまま。名前は変えず、説明も足さない
    - 利点: 旅行の日程を「しおり」と呼ぶのは一般的で、記録のタブを「履歴」にすれば違いは伝わる
    - 欠点: 説明が無いので、初めての人は1回開いて確かめることになる
  - B) 「日程」にする
    - 利点: 何の画面かがすぐわかる
    - 欠点: v3の画面一式と設計資料の言葉が変わり、直す文書が増える
- 推奨: A（記録のタブを「履歴」にすれば、日程と起きたことの違いは名前で伝わる）

### 精算の主ボタン「受け渡しを確認する」の名前と、そばの一行の説明をどうするか

<!-- id: settle-button-words -->

- 工程: 要件
- 種類: 画面
- 優先度: 高
- 状態: 回答待ち
- 画面: v3 14, v3 14c
- なぜ今: 精算の画面とホームの精算の欄で、同じボタンを使っている。名前が決まらないと#248を直せない。
- 根拠: #248。押すと確認を作るだけで、精算として記録するのは確認の画面の「受け渡し完了を記録」（`settlement-preview-screen.tsx:265`）。v3の14は、主ボタンを「受け渡しの記録」から「受け渡しを確認する」に変えている。
- 選択肢:
  - A) 名前は「受け渡しの内容を確かめる」にする。説明は「金額を決めて確認の画面を開きます。まだ精算にはなりません。送金もしません。」にする
    - 利点: 押しても何も確定しないことが、名前と説明の両方でわかる
    - 欠点: ボタンの文字が長くなる（12字）
  - B) 名前は「受け渡しを確認する」のまま、同じ説明だけを足す
    - 利点: v3の画面一式と同じ名前のままで、直すのは説明の一行で済む
    - 欠点: 名前だけを読むと、相手に知らせるようにも読める
  - C) 名前を「受け渡しへ進む」にして、同じ説明を足す
    - 利点: 短く、次の画面に進むボタンだとわかる
    - 欠点: 何をする画面に進むのかは、説明を読まないとわからない
- 推奨: A（押し間違えを心配する人が、ボタンの名前だけで「まだ何も決まらない」とわかる）

### 精算の主ボタンを押す前に、確認を出すか

<!-- id: settle-button-confirm -->

- 工程: 要件
- 種類: アプリの決まり
- 優先度: 中
- 状態: 仮決定
- 画面: v3 14, v3 14d
- なぜ今: #248の改善案に「押す前に確認を出す」とある。出すなら、確認の言葉も決める。
- 根拠: 主ボタンを押しても確認が作られるだけで、精算は記録されない。精算として記録する「受け渡し完了を記録」には、押す前の確認がすでにある（v3の14d）。
- 選択肢:
  - A) 出さない。確定は次の画面の「受け渡し完了を記録」でする、と説明の一行に書く
    - 利点: 何も確定しない操作に確認を挟まずに済み、確認が2回続かない
    - 欠点: 押す前に、戻れるかどうかを確かめる場所が無い
  - B) 出す
    - 利点: 押す前に、まだ精算にならないことを読んでもらえる
    - 欠点: 確認の画面の「受け渡し完了を記録」でも確認が出るので、続けて2回聞くことになる
- 推奨: A（このボタンは何も確定しない。押した後の画面には「受け渡し完了を記録」の確認があるので、そこで止められる）
