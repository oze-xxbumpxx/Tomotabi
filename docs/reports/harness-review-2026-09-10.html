第 2 回分析（同日追記）
構成の整合性だけでなく実際にフックへ入力を流して挙動を実測した結果、追加で 22 件の改善点が見つかりました（第 8 章）。 特に重要なのは、開発方針（AI 駆動開発を主とする。AI が実装し、ユーザーは要件・設計判断・レビューを担う）がハーネスの入口文書に書かれておらず、ツールごとに振る舞いがぶれうること（E-1）、 git clean / git restore . / sequelize db:drop など作業・データを消す操作が安全フックを素通りすること（A-1〜A-3）、 スキルの補助ファイルを書くとフックがブロックすること（C-1）です。
一言でいうと
「守り（安全・状態）」は完成度が高いので触らず、「攻め（ワークフロー・改善）」は 今のプロジェクト段階に合わせて縮退・凍結し、スタック決定後に再有効化するのが最も費用対効果の高い改善です。 ハーネス自身の memory-policy.md が「改善＝追加ではない」「メタ作業の再増殖を監視する」と述べているとおり、 このレポートの提案も削る・凍結する・置き換えるが中心です。

4. 改善ポイント（重要度別）

高 今のセッションで既に誤動作・誤誘導している、または承認境界の穴になっているもの。 中 次のタスク着手前に直すと手戻りを防げるもの。 低 気づいたら直せばよいもの。

4.1 重要度：高

H-1高スクリプト・フックが Cookpit のモノレポ構成と pnpm に固定されている
現状
  • check-deliverables.mjs の isSourceFile() は packages/*/src/** と apps/web/src/** の .ts/.tsx のみを「ソース」と見なす。Tomotabi でどんな構成を選んでも、この形にしない限り PostToolUse の成果物チェックは一度も発火しない。
  • run-quality-gates.sh / detect-project-commands.sh は pnpm 固定・package.json 前提。特に harness ゲートは test:harness script が無いと SKIP になり、AGENTS.md が指示する node --test .claude/tests/*.test.mjs に落ちない。つまり「品質ゲートを回して」と頼むと、唯一実在するテストが unknown と報告される。
  • format-check は pnpm exec prettier 固定、テストは Vitest 前提のコメント。
なぜ問題か
「動いているが何も見ていない」フックは、守られていると思い込むのが最大のリスク。品質ゲートの結果も AGENTS.md の指示と矛盾する。
提案
  1. 監視対象ソースのパターンを設定ファイルへ外出しする（例：.claude/harness.json に sourceGlobs）。未設定なら「ソース判定不能」として沈黙ではなく 1 回だけ注意を出す。
  2. run-quality-gates.sh の harness ゲートを「test:harness script があればそれ、無ければ node --test .claude/tests/*.test.mjs」にフォールバックさせる。
  3. パッケージマネージャーは lockfile（pnpm-lock.yaml / package-lock.json / yarn.lock）から検出し、無ければ npm を既定にする。業務で使っている npm/Node の構成にもそのまま適合する。
対象
.claude/hooks/check-deliverables.mjs, .claude/scripts/run-quality-gates.sh, .claude/scripts/detect-project-commands.sh

4.2 重要度：中

M-1中current-feature の書き込み先が二重で、古い値が新しい値を隠す
現状
スキル・Agent は「.claude/state/current-feature に 1 行書く」と指示する（リポジトリ内・gitignore 済み・旧パス）。 一方フックは resolveReadablePath() で 永続領域 → 旧パス の順に読む。 永続領域（~/.local/state/tomotabi-harness/current-feature）に前タスクの値が残っていると、新しく書いた旧パスの値は無視される。
提案
harness-run.mjs に feature set <name> / feature clear / feature show を追加し、スキル・Agent の指示を「このコマンドを実行」に統一する。正典が 1 つになり、書き先の問題も消える。 ついでに close-session の完了条件に「feature をクリアしたか」を入れると取り残しが防げる。
対象
.claude/scripts/harness-run.mjs, classify-change / create-design-document / create-requirements-document / orchestrator.md / architecture-designer.md
M-2中model 検証が公式エイリアスをブロックする一方、ポリシーはエイリアス前提
現状
validate-agent-config.mjs は frontmatter の model が /^claude-(opus|sonnet|haiku|fable)-/ に一致しないとBLOCK（exit 2）する。 しかし Claude Code の subagent 定義で正規にサポートされる sonnet / opus / haiku / inherit はこの正規表現に当たらない。 orchestration-policy.md 自身も Explore を model: haiku、L3 を model: fable で起動すると書いており、エイリアス運用を前提にしている。
なぜ問題か
「モデルは frontmatter で固定せず inherit にして親の采配に任せる」というごく普通の変更が、ハーネスに拒否される。ブロック系フックの条件が厳しすぎると、結局 --no-verify 的な回避を招く。
提案
許容値を「claude-* の完全 ID」+「inherit | sonnet | opus | haiku | fable」にする。タイポ検出という本来の目的は保てる。併せて agent 定義の model をベンダーの具体的なモデル ID に固定するか、エイリアスにするかを orchestration-policy.md で 1 つに決める。
M-3中shouldEmitNotice() の重複実装と、コメントと実装の不一致
現状
同じ関数が check-deliverables.mjs と check-improvement-cycle.mjs に別々に存在する。 コメントは「警告セットが変化したか、クールダウンを過ぎたときだけ emit」と言うが、ハッシュ対象は feature のみで warnings 引数は未使用。 つまり 30 分以内に不足成果物が増えても再通知されない。
提案
.claude/lib/hook-notice.mjs に共通化し、ハッシュ対象を feature + warnings.join() にする。テストを 1 本追加（同一警告は抑制、警告が増えたら再通知）。
M-4中移植性：plugin がユーザーローカルの改変コピーに依存し、二重発火が未確認
現状
settings.json の enabledPlugins は *@cookpit-harness を有効化しているが、harness-setup.md によればその marketplace は ~/.local/share/cookpit-harness-claude/ の手修正コピーで「GitHub 更新に自動追随しない」。 別マシンや Cloud Agent 環境では解決できない。さらに同じフック群がプロジェクト内 settings.json にも直接登録されているため、plugin 側にもフック定義があれば同じフックが 2 回走る。 harness-setup.md 自身が「新しい対話セッションでのフック発火は未確認」と記録している。
提案
  1. まず 1 回、新セッションで record-activity.mjs の活動ログを見て、1 回の UserPromptSubmit に対し行が 1 本か 2 本かを確認する（二重発火の最も簡単な検出法）。
  2. 方針を決める：A プロジェクト内ファイルを正とし enabledPlugins を外す（現状の 79 ファイルが既にリポジトリ内にあるので自然）／B plugin を正としリポジトリ内の hooks・skills を削る。個人開発でリポジトリ完結を優先するなら A を推奨。
M-5中名前空間の解決がツールごとに手動で、package.json 不在時に孤児化する
現状
Claude Code は settings の env、Codex は毎回 HARNESS_NAMESPACE=tomotabi-harness を手で付ける。 付け忘れると resolveNamespace() は package.json を探すが Tomotabi には無く、既定の claude-harness に落ちる（警告は出るが記録は別ディレクトリへ孤児化）。
提案
解決順に「リポジトリ内マーカー（例 .claude/harness.json の namespace）」を package.json の前に挿入する。H-1 の sourceGlobs と同じファイルにまとめれば、ハーネスの「プロジェクト固有設定」が 1 箇所になる。AGENTS.md の Codex 向け手順から env の記述を消せる。

7. 学びのポイント（なぜそうなっているか・現場ではどう考えるか）

ハーネスは「足場」であり、建物より先に完成させるものではない
今回の最大の指摘（H-4）は、技術的な誤りではなく段階の不一致です。現場でも、CI・レビュー規約・ADR などの仕組みは 「チームがその痛みを一度経験してから」導入するほうが定着します。先に全部入れると、守れないルールが増え、ルール全体の信頼が下がります。 「今有効なもの」を短く宣言し、残りは条件付きで凍結する、というのは Feature Flag と同じ発想です。
fail-open と fail-closed を「関数単位」で決める
harness-paths.mjs は、記録のためのパス解決は失敗しても旧パスに落ちる（fail-open）、安全判定のためのパス解決は失敗したら例外で止める（fail-closed）と、 同じモジュール内で目的別に分けています。業務の Express / Node でも「ログ出力の失敗でリクエストを落とさない」「認可判定が不能なら拒否する」という同じ原則が使えます。 どちらに倒すかをコメントで明文化している点が、このコードの読みやすさの理由です。
「動いているが何も見ていない」チェックが最も危ない
H-1 の isSourceFile() は例外を出さず、単に false を返し続けます。テストも通ります。 現場ではこれを「サイレント・ノーオペ」と呼び、CI のテストが 0 件で緑になるのと同じ危険があります。 対策は「対象が 1 件も無いときは警告を 1 回出す」「対象パターンを設定に外出しし、設定が無いこと自体を検出する」の 2 つです。
ブロック系のルールは緩く、警告系は賢く
M-2（model のエイリアスをブロック）は、正しい入力を拒否するフックの典型です。exit 2 でブロックするルールは 「絶対に誤検知しない」ものだけにし、迷うものは additionalContext の警告に落とす。 guard-dangerous.mjs がその原則を守っているのに対し、validate-agent-config.mjs の model 判定だけがはみ出しています。 ESLint の error と warn の使い分けと同じです。
状態は「リポジトリの外」、設定は「リポジトリの中」
ハーネスは状態（activity-log 等）を ~/.local/state/ に置き、リポジトリ内フォールバックを trusted: false と扱います。 一方で M-5 が示すとおり、設定（namespace や監視対象パス）まで環境変数に頼ると、ツールが増えるたびに手動設定が増えます。 12-Factor の「設定は環境変数」はデプロイ環境ごとに変わるものの話で、プロジェクトで固定のものはリポジトリ内のファイルが正典です。 この区別は Docker / AWS の設定管理でも同じです。
承認境界を決めたら、その境界に機械検証を置く
改善サイクルは「構成変更の承認は PR レビューで」と決めています。であれば PR に node --test が走らないのは、 「レビュアーが目で 88 件のテスト結果を想像する」ことを求めているのと同じです。 人が判断すべきことだけを人に残す（Gate A / Gate B の思想）を、CI にも適用するのが M-6 です。

提案

- L2 / L3 では設計書（docs/designs/）をユーザーが承認してから実装に入る。L0 / L1 は承認なしで進める。
- 技術スタック・アーキテクチャなど ADR 級の決定は AI が候補と比較を示し、決定はユーザーが行う。
- main へ直接コミットしない。変更は作業ブランチ → PR。破壊的操作（履歴改変・データ削除・本番操作）は事前確認。
- 実装完了の報告には「何を・なぜそう設計したか・別解との比較」を含め、ユーザーが読んで学べる形にする。
あわせて classify-change の出力に「ユーザー承認: 必要 / 不要」を加えると、orchestrator がどこで止まるかが機械的に決まる。 現場での慣行: AI 駆動開発を採るチームでは、ゲート（設計承認・PR レビュー）を人が握り、その間は AI に任せる「人が判断点だけを持つ」運用が一般的。ゲートの位置を文書化しておくと、任せ過ぎと確認し過ぎの両方を防げる。

現状
implementer.md の完了報告は「変更ファイル・実行したテスト・残課題」が中心で、reviewer.md は「指摘数を増やさない」「nit は出さない」「人間が少ない判断で受容できる状態へ圧縮する」が原則。 いずれもマージ判断を速くする設計としては正しい。しかし AI 駆動開発でユーザーがスキルアップするには、AI が書いたコードの「なぜこの構成か」「別解は何で、なぜ採らなかったか」「現場ではどう書くか」を読める形で受け取る必要があり、それを出す役割がどこにも無い。
なぜ問題か
AI 駆動開発の弱点は、動くコードが増える速さに理解が追いつかず、レビューが「動いたから OK」になること。理解していないコードはレビューもデバッグもできないので、学習用の説明は品質のためにも必要になる。
提案
