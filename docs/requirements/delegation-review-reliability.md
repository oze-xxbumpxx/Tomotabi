# 要件定義: delegation-review-reliability

- task-id / 変更レベル: delegation-review-reliability / L3
- 作成日: 2026-10-09
- 状態: draft（設計PRの承認待ち。主要3方針はユーザー選択済み）

## 背景

ローカルとCloudで同じ範囲のIssueが作られ、Devinが重複して実装した。2026-10-09の調査では、直近12件のDevin作成PRのうちCodexの完了記録があったのは1件で、その対象コミットも最終headと異なっていた。根拠は[当日の調査ログ](../../logs/2026-10-09.md)。

## 目的

どの実行環境から依頼しても、同じ作業のIssueとDevin起動を重ねない。ユーザーがPRを開くと、最終版のClaude・CodexレビューとCIの状態を確かめられ、必要なレビューが揃うまで通常のマージを止める。

## ユーザー要求（原文の要約）

完全自動化より、共有された委譲状態とレビューの確実性を優先する。GitHubを共有の管理場所に近づけ、起票と委譲受付をActionsに集約する。ユーザーは、管理用Issueの採用、共通窓口への集約、必須チェックによるマージ停止を選んだ。

## 機能要件

| 名前 | 必要な動作 |
| --- | --- |
| 共有状態 | 固定の管理用Issueに、信頼する制御workflowのbotコメントで状態を保存する。ローカルの記録は共有状態を上書きしない |
| 要求の保持 | 要求IDと公開計画の参照を消えないコメントに残す。未配送・未処理・結果不明を区別し、同じ要求を照合できる |
| 作業の識別 | 波と独立したtask_keyを使う。同じキーで作業本文のdigestが違えば、上書きせず競合として止める |
| 起票の重複防止 | Actionsの単一writerが状態を保存してからIssueを作る。結果不明では作成済みIssueを照合し、無条件に再作成しない |
| 起動の重複防止 | 起動受付、担当確保、起動直前のbeginを共有状態に残す。1つのラッパー実行だけが既存CLIを1回起動する |
| 不明な起動結果 | 応答喪失・呼び出し元終了・予約期限切れで担当を自動解放しない。既存セッションとプロセスを照合するまで止める |
| 状態の引き継ぎ | Issue・起動試行・セッション・PRの対応を保存する。既存YAML、履歴、集計、日次ログを読めるまま保つ |
| 起動設定 | runnerと要求したmodelを明示する。Cloudの実値を確認できなければmodelをunknownとし、既定値を推測しない |
| レビュー証拠 | Claudeは固定作者ID・完全head SHA・verdict・証拠URL、Codexは固定bot ID・完了・一意に解決した完全SHAを確かめる。作者と最終編集者を別に照合し、信頼できない編集を成功証拠にしない |
| 指摘への対応 | Codex完了と指摘解決を別に扱う。Claude完了には確認したCodex証拠集合を結び、新しいCodex指摘で再確認を要求する |
| マージの判定 | agent-reviewを必須チェックにする。同じhead SHAを持つOPEN PRを集め、対象PR全件の証拠が揃うまで成功にしない。未完了・古いSHA・未解決の対象指摘・取得失敗は成功にしない |
| 対象外PR | 人やCodexが作成した対象外PRにもagent-reviewのcontextを出す。同じSHAに対象PRが無ければ対象外として成功、あればその対象PR全件の判定を待つ |

## 非機能要件（性能・セキュリティ・可用性など。無ければ「対象外」）

- このリポジトリはpublic。管理Issueにraw prompt、CLI生ログ、指摘本文、認証情報、起動許可の秘密を保存しない。
- GitHubに書けないときは、起票・起動を止める。読み取りの縮退表示は、未確認であることを明示する。
- 全更新を短いActions処理で直列化する。Devinの実装時間をActionsの占有時間にしない。
- コメント・レビュー・スレッド・workflow runはページ送りし、取得上限に達した途中結果で成功を判定しない。
- 自動の後続起動、アプリの可用性・応答時間の変更は対象外。GitHubイベントの配送は非同期であり、即時の原子的な失効は保証しない。

## 正常系

1. 公開計画のタスクを登録すると、共有の要求IDとtask_keyからIssueを1つ作る。
2. 担当を確保したラッパーがbeginを1回送り、初回の許可を受け取ってCLIを1回起動する。
3. セッションとPRを結び、現在headのCodex完了と指摘への対応をClaudeが確認する。
4. agent-reviewが成功し、既存必須CIも成功したPRをユーザーがマージする。

## 異常系

| 条件 | 期待する結果 |
| --- | --- |
| 同じ要求・同じ作業を同時に送る | 既存の受付結果を示し、Issueや起動試行を増やさない |
| 同じキーで本文digestが違う | 競合として止め、既存Issueを上書きしない |
| Issue作成後に応答を失う | 起票結果不明に残し、同じ印のIssueを照合する |
| beginの応答喪失、起動前後のクラッシュ | 起動結果不明に残し、再実行したラッパーには許可を使い回さない |
| 共有コメントの欠落・破損、信頼するrunを確認できない | 状態破損として書き込みと成功判定を止める |
| 古いレビュー、偽の印、開始の反応だけ | レビュー済みにしない |
| 完了証拠を他のwrite権限者が編集する、編集情報を取得できない | 作者IDだけで採用せず未確認にする。Claudeは新規の完了投稿、Codexは信頼bot自身の証拠を求める |
| 対象PRと対象外PRが同じhead SHAを使う | 対象外PRだけの成功を出さず、関連する対象PR全件のレビューを待つ |
| Codexの新しい指摘、未解決の対象指摘 | 古いClaude完了を使わず、再確認が必要と示す |
| ghが無い・未認証 | 接続済みMCPで同じ要求を送れる場合だけ共通窓口を使う。直接起票・直接起動に切り替えない |

## 境界条件（null・空・上限/下限・権限境界）

- task_key・要求ID・公開計画参照・digestが空の要求は受け付けない。仕様の版が違う要求も拒否する。
- 予約期限が切れた場合も未着手とは扱わない。セッションIDが空なら、起動成功とは表示しない。
- Codexの短縮SHAを一意に解決できない、全ページを読めない、レビュー対象PRを特定できない場合は未確認にする。
- 指摘なしで完了したCodexレビューも数える。Draftはレビュー待ちを示し、マージ可能な成功にはしない。
- 認証した固定作者ID・信頼する最終編集者・制御workflowだけを信頼する。Claude完了は初回では編集済みを無効とし、新規投稿を求める。表示名・login・コメントの印だけでは権限を判断しない。

## 前提

GitHub Actionsと現在のDevin CLIを使う。新しいDevin APIキーは追加しない。Codexの実機設定とActions botからの起動は未確認のため、初回は動作が確認されたユーザーアカウントから明示的にレビューを依頼する。

## 制約

設計承認後に実装する。mainへの直接コミット、AIによるPRマージ、結果不明な起動の自動やり直しは禁止する。Cloud／Localの既定の食い違いは今回の文書で勝手に確定しない。休眠中のGate B・改善3Agentを必須化しない。

## 対象範囲

`.claude/scripts/`の受付・共有状態・起動ラッパー・レビュー判定、既存delegation CLIとstatus、`.github/workflows/`の制御workflow、関連スキル・記録形式、導入時のGitHub設定。アプリの`apps/`と`packages/`は変更しない。

## 対象外

新しいDevin API認証、後続Issueの完全自動起動、Merge Queue、PR間の自動競合解消、全Issueの依存関係移行、新しいAIエージェント、アプリ機能の変更。開始条件の確認は既存実装計画に従い、後続の自動ready化は作らない。

## 後方互換性・データ移行（該当なければ「対象外」）

既存YAMLの形式とIssue番号／pr-Nのキーを読めるままにする。進行中のIssue・セッション・PRを先にimportし、未登録を未着手と推測しない。古い短縮SHAの記録は履歴として残すが、新しいチェックの成功証拠には使わない。

## 受け入れ条件（Definition of Done に対応）

- 並行した同じ登録・claim・beginの試験で、Issue作成とCLI起動がそれぞれ1回以下になる。途中失敗では安全のため止まる。
- 要求の二重配送、100件を超えるコメント、欠落・破損、上限到達を試験し、未処理の要求を確認できる。
- 同じhead SHAの対象PR全件で両レビューと対象指摘の確認が揃った場合だけagent-reviewが成功する。対象外PRにもcontextがあり、SHAを共有する対象PRの不足を迂回できない。
- head更新とCodex指摘追加で再確認を要求する。偽の作者・不正な編集者・古いSHA・曖昧な完了・取得失敗を成功にしない。
- quality・build・api-dbを維持し、agent-review自身へのCIの自己依存を作らない。PR headとCIのmerge commitを区別する。
- ハーネス試験と実機の正常／不足証拠のPRで確認した後、Protect-mainへagent-reviewを追加する。設計・実装PRのマージはユーザー。
