# 要件定義: 結合検証環境（integration-env）

- task-id / 変更レベル: integration-env / L3（外部サービス・認証の経路・秘密情報に触れる）
- 作成日: 2026-10-12

## 背景

アプリの機能は、旅行・予定、支払い・精算の中核、記録と4画面、通知まででそろった。どれも手元（ローカルとCIの実PostgreSQL・E2E）では確かめたが、本番と同じVercel・Neonの上では一度も動かしていない。設計資料（詳細設計08「Vercel＋Neonのデプロイと無料枠運用」と「運用設定と公開チェック」）は、画面からAPIへの転送とCookie、Googleログイン、Neonへの接続と休止からの復帰、`waitUntil`、実際の端末での通知などを「未検証」として残している。

## 目的

本番と同じ構成の検証用の環境を作り、架空のデータで、手元では確かめられないことを確かめる。見つかった問題を、公開準備の前に直す。

## ユーザー要求（原文の要約）

- 次の段階（結合検証環境）に進みたい（2026-10-12）。
- デプロイ先はCloudflareと比べたうえで、設計資料どおりVercel＋Neonにする（2026-10-12）。
- 要件は最終的に、分かりやすいようにHTMLのページで見せてほしい（2026-10-12）。

## 機能要件

| ID | 要件 |
| --- | --- |
| R-01 | 検証用の環境として、Vercelに画面とAPIの2プロジェクト（web-test・api-test）、Neonに検証用のプロジェクト（test）を作る。地域は、Vercelの関数の実行場所をsin1（シンガポール）、NeonをAWS Singapore（ap-southeast-1）にそろえる。Vercelの関数は設定しないとアメリカ東部（iad1）で動くので、sin1を明示する。本番の地域は、PERF-01で測ってから決める |
| R-02 | APIを、Vercelの公式のNestJSの入口で1つのNode.jsの関数として動かす。Nodeは24.x（ADR-0008）、`maxDuration`は60秒、`pg.Pool`は最大2で、関数が休むときに使っていない接続を手放す（`attachDatabasePool`） |
| R-03 | 保存のあとの通知の送信を、Vercelの`waitUntil`で応答のあとに動かす（通知の設計書で、この段階に回した「保存のあとの処理の口」のVercelの実装）。手元とCIでは今の`InProcessAfterResponse`のまま |
| R-04 | 画面の`/api/...`を、APIの固定のURLへ転送する（Vercelの外部rewrite）。`/api`の応答と、Cookieに依存する画面は、共有のキャッシュに載せない（`Cache-Control: private, no-store`など） |
| R-05 | 検証用の環境の設定（環境変数）を、`運用設定と公開チェック.md`の1節の表のとおりに置く。ただし通知の鍵は、表の`VAPID_KEY_ID`・`VAPID_PUBLIC_KEY`・`VAPID_PRIVATE_KEY`ではなく、今のコード（`apps/api/src/modules/notification/infrastructure/env-vapid-keyring.ts`）が読む`VAPID_KEYS`（鍵の束のJSONの配列）と`VAPID_SUBJECT`で置く。表は今のコードに合わせて直す。`APP_ENV`は`staging`。通知を確かめる間だけ`PUSH_ENABLED`相当を有効にする |
| R-06 | NeonのDBに、管理用（migrator）と実行用（app_runtime）のロールを作り、migrationを管理者の端末から1回だけ適用する。利用を許す二人に、二人の普段のGoogleアカウントを、初期登録のCLI（`npm run cli:enroll -w @tomotabi/api -- --slot <0か1>`）で登録する |
| R-07 | 検証用のGoogleのOAuthのクライアントを2つ作る。1つはログイン用（ウェブアプリ型）で、戻り先（redirect URI）を検証用の画面のURLの`/api/auth/callback/google`に完全一致で登録する。もう1つは初期登録のCLI用（デスクトップ型。ADR-0002）で、`ENROLL_GOOGLE_CLIENT_ID`・`ENROLL_GOOGLE_CLIENT_SECRET`として管理者の端末にだけ置く |
| R-08 | 検証用のVAPIDの鍵を1組作る（`npm run cli:generate-vapid-key -w @tomotabi/api`。出力の1要素を`VAPID_KEYS`の配列に入れる）。運用者の連絡先（`VAPID_SUBJECT`）は、このリポジトリのGitHubのURL（`https:`）にする |
| R-09 | 検証用の環境へのデプロイは、確かめたいときに手動で行う（CIが通ったcommitを指定する）。mainへのマージで自動にはデプロイしない |
| R-10 | 下の「確かめること」を検証用の環境で確かめ、日付・環境・結果を検証の記録に残す |
| R-11 | 確かめたあと、無料枠の消費（CPU・メモリ・関数の呼び出し・DBの容量とCU時間・転送量）を記録する |
| R-12 | 確かめ終わったあとも、検証用の環境は残し、使わないあいだはデプロイも利用もしない |

### 確かめること（R-10）

公開前の確認（`運用設定と公開チェック.md`の3節）のうち、環境で初めて確かめられるものと、実際の端末での通知と、描画の遅れの内訳。

| ID | 確かめること |
| --- | --- |
| OPS-03 | 公開URLと転送: `/api`が抜けたり二重になったりせず、固定のAPIに届く。転送先を要求から指定できない |
| OPS-04 | Cookieとヘッダー: 複数の`Set-Cookie`、`Origin`、`X-Expected-Version`、`Idempotency-Key`、本文が転送で保たれる。ログアウトでCookieが消える |
| OPS-05 | キャッシュ: APIと、認証・個人ごとの画面が、共有のキャッシュに載らない。一人の結果がもう一人に見えない |
| OPS-06 | Googleと二人の制限: 二人がログインできる。登録していないGoogleアカウント、APIへの直接の要求、別の旅行への要求を断る。公開URLでVercelのログインを求めない |
| OPS-07 | DBの接続: Neonのpooledの接続で、TLSの検証と認証が通る。管理用の接続と実行用の接続が分かれている |
| OPS-08 | 休止・pool・期限: Neonが休んだあとに戻れる。使わない接続が手放される。ロックとSQLの待ちに上限がある |
| OPS-09 | DBの同時操作: 2つの接続で、精算の二重の完了・取り消し・再送が正しく扱われる |
| OPS-10 | 実行用のロール: 履歴の更新・削除、DDL、TRUNCATEができない。必要な操作・行のロック・認証の書き込みはできる |
| OPS-11 | 通知: 保存が成功したあとに届く。`waitUntil`と3秒の打ち切りが動く。消えた購読の扱いが正しい |
| OPS-17 | 実機の画面: 主な使い方の流れ、ほかのアプリから戻ったときの動き、結果が分からない操作のやり直し |
| OPS-18 | 利用量: 確かめたあとのCPU・メモリ・DB容量・CU時間・転送量を記録し、無料枠で使い始められる余裕を確かめる |
| PERF-01 | 描画の遅れの内訳: 日本の実機から、主な操作（ホームを開く、予定を足す、支払いを記録する）の応答の時間を測り、日本とシンガポールの距離・Neonの休止からの復帰・関数の起動に分けて記録する。関数がsin1で動いていることも確かめる。距離が原因で遅いなら、本番を作る前に、東京の地域があるPostgreSQLのサービスへの変更をADRで検討する |
| PM-03 | 実際の端末での通知: iPhone（ホーム画面に追加したアプリ）とAndroid（Chrome）の両方で、相手の操作の通知が届き、押すと対象が開く |

## 非機能要件

- 費用: Vercel Hobby・Neon Free・GitHub Freeの範囲にとどめる。無料枠の7割で原因を確かめ、9割で検証を止める（詳細設計08の2節）。課金に進まない。
- セキュリティ: 秘密情報（DBの接続URL、Better Authの鍵、ログイン用と初期登録用のGoogleのsecret、VAPIDの秘密鍵）は、ユーザーが管理画面で登録する。Claude Codeは値を見ない。`NEXT_PUBLIC_*`や公開の設定に秘密を入れない。`trustedOrigins`は検証用の画面のURLだけで、`*.vercel.app`を許さない。ログにCookie・Googleのtoken・通知の宛先と鍵・本文・SQLの引数を出さない。
- データ: 架空の旅行・予定・金額だけを入れる。本番のデータや、実際の金銭の受け渡しは使わない。
- 可用性: 検証用の環境は、常に動いている必要はない。keep-aliveや定期のDBへの接続は置かない。

## 正常系

| ID | 流れ |
| --- | --- |
| N-01 | 二人が普段のGoogleアカウントで、検証用の画面にログインできる |
| N-02 | 画面からの要求が、転送でAPIに届き、Cookieと必要なヘッダーが保たれる |
| N-03 | 旅行・予定・支払い・精算・記録の操作が、Neonに保存され、二人の画面に出る |
| N-04 | 一人の操作のあと、もう一人の端末（iPhoneはホーム画面に追加したアプリ、AndroidはChrome）に通知が届き、押すと対象が開く |
| N-05 | Neonが休んだあとの最初の操作も、待ったうえで成功する |

## 異常系

| ID | 起きること | 期待 |
| --- | --- | --- |
| E-01 | 登録していないGoogleアカウントでログインする | 断られる |
| E-02 | APIのURLへ直接要求する | 画面からの要求と同じ認証・二人の制限・旅行の参加者・`Origin`の確かめが効く |
| E-03 | Neonが休んでいる・遅い | 有限の時間で待ち、成功か失敗かが分かる。時間切れを成功として扱わない |
| E-04 | 配信サービスへの通知の送信が失敗する | 保存は成功のまま。通知が届かないだけになる |
| E-05 | 無料枠の9割に届く | 検証のデプロイと利用を止める |

## 境界条件

- 利用を許すのは二人（許可リストの2枠）だけ。3人目は登録しない。
- 同時の操作は、2つの端末からの同じ操作まで（OPS-09）。
- 通知の購読は、1人3台まで（通知の設計のとおり）。
- APIの1回の実行は60秒まで。DBのロック待ちは3秒、SQLは5秒まで（実行用のロールの既定。`apps/api/db/admin/create-roles.sql`）。通知の送る処理の読み取りは2秒まで。

## 前提

- Vercel・Neon・Google Cloudのアカウントは、ユーザーがすでに持っている（2026-10-12の答え）。
- 二人の端末は、iPhoneとAndroidが1台ずつ（2026-10-12の答え）。
- アカウントの設定・プロジェクトの作成・秘密情報の登録はユーザーが行う。Claude Codeは手順書と、アプリ側の作り（R-02〜R-04）を用意する。
- アプリの機能は、通知までマージ済み（`main`）。

## 制約

- Vercel Hobbyは個人の非商用の利用に限る。関数は1つの地域だけで動く。
- Neon Freeは、無操作5分で休止し、復元の履歴は最大6時間。
- 本番のDBの秘密を、PRのCIに渡さない。migrationは管理者の端末から行う（詳細設計08の7節）。
- 独自ドメインは使わない（詳細設計08の1節）。

## 対象範囲

- Vercelの2プロジェクトとNeonの1プロジェクト（検証用）を作る手順書（`docs/`の中に置く）
- アプリ側の作り: APIのVercelの入口と関数の設定（`apps/api`）、`waitUntil`の実装（`apps/api`の保存のあとの処理の口）、画面の転送とキャッシュの設定（`apps/web/next.config.ts`）
- DBのロールの作成とmigrationの適用の手順、二人の登録の手順
- 検証の記録（確かめた日・環境・結果）

## 対象外

- 本番の環境（Vercelのweb・api、Neonのproduction）を作ること。公開準備の段階で行う
- バックアップと復元（dump／restore、OPS-13）、コードの巻き戻し（OPS-14）、完全停止（OPS-15）、秘密とログの点検（OPS-16）、プランと課金の制御（OPS-01）、環境の分離（OPS-02）、公開の順番（OPS-12）。公開準備の段階で確かめる
- 独自ドメイン、Cloudflare、有料のアドオン、外部の監視（Sentryなど）
- PRごとのPreviewにDBや通知をつなぐこと（詳細設計08の3節のとおり、画面の確認だけ）
- アプリの機能の追加

## 後方互換性・データ移行

対象外（新しい環境に、今のmigrationを最初から適用する。既存のデータは無い）。

## 受け入れ条件

- 検証用の環境（web-test・api-test・Neon test）が動き、二人が普段のGoogleアカウントでログインできる。
- 「確かめること」の全項目（OPS-03〜11・17・18、PM-03、PERF-01）を確かめ、検証の記録に日付・環境・結果がある。見つかった問題は直したか、公開準備までに直すものとして記録してある。
- 無料枠の消費を記録し、無料枠で使い始められる余裕があることを確かめた。
- 描画の遅れの内訳を記録し、本番の地域（今のままシンガポールか、東京の地域があるDBのサービスに変えるか）を決めるための材料がそろった。
- 秘密情報がリポジトリ・ログ・CIの成果物に無い。
- R-02〜R-04のアプリ側の作りに試験があり、品質ゲート（lint・type-check・test・build・E2E）が通る。
