## 背景

M1 で、登録済みの二人だけがログインでき、業務 API が Guard の渡す userId で動く土台ができた。M3 以降の支払い・精算・記録は、すべて「どの旅行の、どの予定か」を前提にしている。そのため M2 で、旅行と予定の作成・選択・編集と、その書き込みを安全にする共通の仕組み（ETag による競合検出、Idempotency-Key による再送制御、旅行単位のロック順序）を先に固める。

## 目的

- 二人が旅行を作り、選び、手動で開始・終了でき、日ごとの予定（しおり）を追加・編集・日の移動・取りやめできる。
- 旅行作成で参加者二人と金融 guard が同じトランザクションで作られること、日付・ETag・取りやめの規則を、実 API（実 PostgreSQL）と画面で確認できる。
- 書き込み API の共通部品（ETag・Idempotency-Key・receipt・エラー形式・画面の保存状態）を M2 で完成させ、M3 の支払い・精算がそれを使うだけにする。

## ユーザー要求（原文の要約）

「M2（旅行・予定）の要件と設計を始める」。2026-09-27 の確認で次を決定した。

- 達成・予約: M2 では表（履歴・取消・有効占有）と、種類変更の判定（履歴があれば変更不可）だけを作る。達成・予約の追加・取消の API と画面は M4。
- 画面: handoff-v3 の画面を完成度高く作る。v3 に無い入力画面（旅行の作成、予定の追加・編集・日の移動、取りやめの確認）は、v3 のトークンと部品（支払いを記録のシートなど）から AI が組み、実装後にスクリーンショットで確認してもらう。
- 結果不明の書き込みの復帰: M2 はメモリ内まで（同じ要求で確かめる仕組み）。IndexedDB による再読み込みを跨ぐ復帰は M3。
- web のライブラリ: 取得状態は TanStack Query、フォームは React の状態＋既存の Zod（ADR-0004）。

## 機能要件

### 旅行

| ID | 要件 |
|---|---|
| F-01 | 旅行を名前・開始日・終了日で作成する。参加者はサーバーが allowlist の二人（slot 0 / 1）から決め、クライアントから指定させない |
| F-02 | 旅行の作成と同じトランザクションで、参加者二人（trip_participants）、金融 guard（trip_finance_guards）、再送 receipt を作る。どれかが失敗したら全体をロールバックする |
| F-03 | 利用できる許可アカウントが二人揃っていなければ作成を拒否する（409 PARTICIPANTS_NOT_READY） |
| F-04 | 自分が参加している旅行だけを一覧する。並びは作成日時の新しい順（同時刻は id の降順）。状態の絞り込みとカーソルによる追加取得を持つ |
| F-05 | 旅行を 1 件取得する。応答に ETag（旅行の version）を付ける |
| F-06 | 旅行名を変更する（If-Match 必須） |
| F-07 | 旅行期間を変更する（If-Match 必須）。取りやめ済みを含むすべての予定が新しい期間に収まらなければ拒否し、予定を自動で動かさない |
| F-08 | 旅行を手動で開始（planning → traveling）・終了（traveling → finished）する。開始・終了した日時と操作者を保存する。日付による自動遷移、終了の取り消し、旅行の削除、参加者の変更は提供しない |
| F-09 | 終了後も、予定の追加・編集・日の移動・取りやめと、旅行名・期間の変更を許可する（終了はデータの凍結ではない） |

### 予定

| ID | 要件 |
|---|---|
| F-10 | 予定を追加する。名前・種類・日付は必須、時刻・メモは任意。日付は旅行期間内に限る |
| F-11 | 予定を 1 件取得する。現在の値、有効な達成・予約、種類変更の可否（canChangeKind）と不可の理由を返し、ETag を付ける |
| F-12 | 予定の名前・種類・時刻・メモを部分更新する（If-Match 必須）。日付は含めない。実質同じ値なら version を増やさない |
| F-13 | 予定の日を移動する（If-Match 必須）。移動先は旅行期間内に限る |
| F-14 | 予定を取りやめる（If-Match 必須）。取りやめた日時と操作者を一度だけ記録し、復活の API は持たない。取りやめ済みの予定もメモ等は編集できるが、編集で取りやめを解除しない |
| F-15 | 種類の変更は、達成・予約の履歴（取り消し済みを含む）が一度も無い予定に限る。履歴があれば拒否する（409 PLAN_HAS_RECORD_HISTORY） |
| F-16 | 日別しおりを取得する。旅行と指定日の予定一覧（取りやめ済みを含む）を返す。並びは時刻の早い順・時刻未定は末尾・登録日時・id。日付を省略したら、日本時間の今日が期間内なら今日、それ以外は初日にする |

### 書き込みの共通規則

| ID | 要件 |
|---|---|
| F-17 | すべての業務の書き込みに Idempotency-Key（UUID）を必須とする。同じ利用者・操作・キーの成功の再送は、If-Match の再評価より先に、保存した元の結果（DTO と ETag）を返す。同じキーで入力が違えば拒否する（409 IDEMPOTENCY_KEY_REUSED）。再送でも現在の認証・参加者の確認は行う |
| F-18 | 更新系は If-Match（引用符付き 10 進数の強い ETag、1 つだけ）を必須とする。欠落は 428 IF_MATCH_REQUIRED、不一致は 409 VERSION_CONFLICT。ワイルドカード・弱い ETag・複数値は受け付けない |
| F-19 | エラー応答は `{ code, message, requestId, retryable }` とする。画面は code で分岐し、message をそのまま表示しない |
| F-20 | 旅行・予定の API は、Guard の検証済み userId がその旅行の参加者であることを毎回確認する |

### 達成・予約の土台

| ID | 要件 |
|---|---|
| F-21 | 達成・予約の履歴（plan_events）、取消（plan_event_cancellations）、有効占有（active_plan_events）の 3 表を作る。履歴と取消は追記のみで、UPDATE / DELETE を DB で拒否する。M2 では書き込む API を持たない（M4） |
| F-22 | 予定の取得・しおりは、有効な達成・予約を結合して返す（M2 では常に null になるが、表に行があれば正しく返す） |

### 画面

| ID | 要件 |
|---|---|
| F-23 | ログイン後の入口: 前回選んだ旅行（利用者ごとにブラウザへ保存）が取得・参加確認できればその旅行のしおりへ、できなければ旅行一覧へ進む。保存した id を権限の根拠にしない。ログアウトで消す |
| F-24 | 旅行一覧（v3 の 15 切り替え・19 旅行 0 件）と旅行の作成画面（v3 に無い。v3 の部品から組む） |
| F-25 | 旅行のヘッダーとメニュー（v3 の 16〜18）。旅行名・期間の変更、開始・終了（終了は確認ダイアログ 17） |
| F-26 | しおり（v3 の 08）と予定の詳細（v3 の 09）。予定の追加・編集・日の移動・取りやめ（v3 に無い。v3 の部品から組む） |
| F-27 | 共通の状態: 読み込み・更新中・更新できていません（v1）、ログイン切れ（C-1）、開けない（C-2）、オフライン（C-3）、保存の結果が不明（C-4）、競合（C-5） |

## 非機能要件（性能・セキュリティ・可用性など）

- 整合性: 旅行・予定の書き込みは、旅行 → 予定の順でロックする（旅行は FOR SHARE、期間変更と旅行自体の更新は FOR UPDATE、予定は FOR NO KEY UPDATE）。M3 以降の財務は別の trip_finance_guards を使い、予定と逆順にロックしない。
- セキュリティ: 他人の旅行の名前・件数・存在を返さない。参加していない旅行と存在しない旅行は同じ 403 にする。Google の sub・メールを応答に含めない。receipt にセッショントークン等を保存しない。
- 可用性: DB に接続できないときは 503。画面は 503・通信失敗を「保存失敗」と断定せず、結果不明（C-4）として同じ要求で確かめる。
- 時刻: 日付は date（`YYYY-MM-DD`）、時刻は秒とタイムゾーンを持たない `HH:mm`（日本時間の現地時刻）、履歴の日時は timestamptz。時刻未定を 00:00 に変換しない。「今日」は Asia/Tokyo で決める。
- 入力の上限: 旅行名・予定名 1〜100 文字（前後の空白を除いて空でない）、メモ 2,000 文字。文字数は Unicode のコードポイント数で数える。
- 性能: 目標値は対象外（二人利用）。しおりは 1 日分を 1 回の読み取りで返す。
- アクセシビリティ: 入力に可視ラベル・エラーの関連付け。取りやめ・エラーを色だけで区別しない。完了・失敗を読み上げ領域でも伝える。

| ID | 内容 |
|---|---|
| N-01 | 二人が登録済みのとき、旅行を作成すると 201 で旅行 DTO と ETag が返り、参加者 2 行・guard 1 行・receipt 1 行が同じトランザクションでできる |
| N-02 | 旅行一覧は自分が参加する旅行だけを新しい順で返し、カーソルで続きを取得できる。状態で絞り込める |
| N-03 | 旅行名の変更で version が 1 増え、新しい ETag が返る |
| N-04 | 期間の変更は、全予定（取りやめ済みを含む）が新期間に収まれば成功する |
| N-05 | 開始で traveling になり started_at / started_by が入る。終了で finished になり finished_at / finished_by が入る |
| N-06 | 終了後も予定の追加・編集・移動・取りやめ、旅行名・期間の変更ができる |
| N-07 | 予定を追加すると 201 で予定 DTO と ETag が返る。時刻未定は null のまま保存・表示される |
| N-08 | 予定の部分更新・日の移動・取りやめで version が 1 増える。実質同じ値の更新は version を増やさず 200 を返す |
| N-09 | 履歴の無い予定は種類を変更できる |
| N-10 | しおりは指定日の予定を、時刻順・未定は末尾・登録日時・id の順で、取りやめ済みも含めて返す。日付を省略すると今日（期間内）または初日になる |
| N-11 | 同じ Idempotency-Key・同じ入力の再送は、元の結果（状態コード・DTO・ETag）を返し、行を増やさない。その後に相手が更新していても、再送は元の DTO を返す |
| N-12 | 画面: 旅行を作ってしおりへ進み、予定を追加・編集・移動・取りやめし、旅行を開始・終了できる（ローカルの Mac のブラウザで二人分を確認） |
| N-13 | 画面: 前回選んだ旅行が有効なら、ログイン後にその旅行のしおりが開く |

## 異常系

| ID | 内容 | 期待 |
|---|---|---|
| E-01 | allowlist の二人が揃っていない（1 人だけ・一方が無効）で旅行を作成 | 409 PARTICIPANTS_NOT_READY。何も作られない |
| E-02 | 旅行の作成の途中で失敗（例: guard の作成で失敗） | 旅行・参加者・guard・receipt のどれも残らない |
| E-03 | 参加していない旅行・存在しない旅行の取得・更新 | 403（両者を区別しない） |
| E-04 | 認可済みの旅行に属さない予定 id（別の旅行の予定を含む） | 404 |
| E-05 | 更新で If-Match が無い | 428 IF_MATCH_REQUIRED |
| E-06 | If-Match が古い（相手が先に更新した） | 409 VERSION_CONFLICT。相手の変更を上書きしない |
| E-07 | If-Match が不正な形式（`*`、`W/"1"`、複数値、引用符なし） | 400 |
| E-08 | 同じ Idempotency-Key で入力（body・If-Match・対象）が違う | 409 IDEMPOTENCY_KEY_REUSED |
| E-09 | Idempotency-Key が無い・UUID でない | 400 |
| E-10 | 予定の日付・日の移動先が旅行期間の外 | 422 PLAN_OUTSIDE_TRIP_PERIOD |
| E-11 | 期間の変更で、はみ出す予定（取りやめ済みを含む）がある | 422 PLAN_OUTSIDE_TRIP_PERIOD。予定も期間も変わらない |
| E-12 | 達成・予約の履歴（取り消し済みを含む）がある予定の種類変更 | 409 PLAN_HAS_RECORD_HISTORY。他の項目も変更しない |
| E-13 | 取りやめ済みの予定をもう一度取りやめる（別のキー） | 409 PLAN_CANCELLED |
| E-14 | 不正な状態遷移（finished → start、planning → finish） | 409 INVALID_TRIP_TRANSITION |
| E-15 | 入力の不正（名前が空白だけ・101 文字、開始日 > 終了日、実在しない日付、時刻が `24:00` や秒付き、メモ 2,001 文字、未知の項目、未知の種類） | 422（形式違反は 400） |
| E-16 | Origin 不一致・Content-Type 違い（M1 の共通 Guard） | 403 / 415 |
| E-17 | 同じキーで二つの旅行の作成が同時に走る | 片方だけが成立し、もう片方は同じ結果（同じ旅行）を返す。旅行は 1 件だけ |
| E-18 | 予定の追加・日の移動と期間の変更が同時に走る | 期間外の予定が成立しない |
| E-19 | 種類変更と達成の記録（M2 ではテストで表へ直接挿入）が同時に走る | 記録が先なら種類変更を拒否する（予定のロックを共有する） |
| E-20 | app_runtime で履歴・取消表への UPDATE / DELETE、receipt・参加者への UPDATE / DELETE、DDL | 権限エラーまたはトリガーで拒否 |
| E-21 | 画面: 保存中に通信が切れた・5xx | 「保存されたか確認できません」（C-4）。入力を固定し、同じ要求（同じキー・本文・If-Match）でだけ確かめられる |
| E-22 | 画面: VERSION_CONFLICT | 競合（C-5）。入力を残して最新と並べ、本人が選んで新しい ETag・キーで保存する。自動で上書きしない |

## 境界条件（null・空・上限/下限・権限境界）

| ID | 内容 |
|---|---|
| B-01 | 旅行名・予定名は前後の空白を除いて 1〜100 コードポイント。絵文字（サロゲートペア）1 つは 1 文字 |
| B-02 | 開始日 = 終了日（日帰り）は有効。開始日 > 終了日は無効 |
| B-03 | 予定の日付 = 開始日・終了日ちょうどは期間内 |
| B-04 | 時刻 `00:00` と `23:59` は有効。null は「時刻未定」で `00:00` と区別する |
| B-05 | メモの改行・内部の空白は保持する。空のメモは null として保存する |
| B-06 | 旅行一覧の上限（limit）の既定と最大は設計書で決める。0 件は空配列 |
| B-07 | 同じ状態への遷移（traveling の旅行に start）で ETag が一致するなら 200 で現在の旅行を返し、version・日時を変えない |
| B-08 | PATCH の本文が空（項目 0 個）は 400。null を送った時刻・メモは消去 |
| B-09 | 前回選んだ旅行 id が、参加していない・存在しない旅行を指す | 旅行一覧へ戻り、保存した id を消す |

## 前提

- M1 が main に入っていること（済み。M-06 の利用停止の手動確認は未実施だが M2 の前提にしない）。
- ローカル開発 DB は compose の PostgreSQL 16。M1 で二人を登録済みの DB を使って画面を確認する。

## 制約

- `sql/03`・`sql/04`・`sql/01` をそのまま本番 migration として実行しない。Drizzle スキーマとカスタム migration に落とす（ADR-0003）。
- 別の業務領域の表へ直接書き込まない。予定の種類変更で使う履歴の照会は、planning 側の IF と record 側の読み取り実装を composition で結ぶ（詳細設計 11 §5）。
- 通知（M5）・支払い（M3）・ホームの集約（M4）を先回りして作らない。
- 本番（Neon / Vercel）の作成・操作は行わない。

## 対象範囲

- `apps/api`: planning モジュール（旅行・予定の Controller / UseCase / Domain / Infrastructure）、record モジュールの最小部分（履歴の照会）、共通の書き込み部品（Idempotency・ETag・エラー応答）、DB スキーマと migration（planning / record / infra の各表と GRANT）
- `apps/web`: 旅行・しおり・予定の画面、共通の取得状態・保存状態、TanStack Query の導入
- `packages/contracts`: 旅行・予定の OpenAPI（詳細設計の 2 ファイルから M2 の操作を移植し、重複する getTrip を 1 つに統合）
- ADR-0004（web の取得状態ライブラリと API の入力検証）

## 対象外

- 達成・予約の追加・取消 API と画面、記録一覧（M4）
- ホームの集約 API（GET /trips/{tripId}/home）とホーム画面の予定・精算・最近の記録（M4）
- 支払い・精算（M3）、通知（M5）
- IndexedDB による未確定要求の永続化と再読み込み後の復帰（M3）
- オフラインしおり、持ち物・思い出、ダークモードの各画面の作り込み（後続）
- Playwright E2E（M2 は Vitest + Testing Library と実 DB の HTTP テスト、画面は手動確認）

## 後方互換性・データ移行

- 既存の本番データは無い（本番 DB は未作成）。M1 の identity スキーマは変更しない。
- ログイン後の入口が、M1 の最小ホーム（表示名とログアウト）から、旅行一覧・しおりに変わる。表示名とログアウトは旅行の画面のメニューへ移す。
- `/api/foundation/*` の検証経路と web の検証 UI は、M2 では変更しない（扱いは設計書の未決事項）。

## 受け入れ条件（Definition of Done に対応）

1. N-01〜13、E-01〜22、B-01〜09 を試験計画の観点に採番して反映し、自動テストで確認する。N-12・N-13 の画面操作はローカルでの手動確認とし、結果を記録する。
2. 旅行の作成（参加者・guard の同時作成とロールバック）、ETag の競合、Idempotency の再送・同時作成、期間と予定の競合を、実 NestJS + 実 PostgreSQL（Testcontainers）の HTTP テストで確認する。同時実行は 2 つの接続で再現する。
3. 空 DB への migration の適用と、app_runtime の権限（許可・拒否）を Testcontainers で確認する。
4. 画面の保存状態（保存中・成功・拒否・結果不明・競合）を Vitest + Testing Library で確認する。
5. lint / type-check / test / test:api-db / build がすべて成功する。
6. v3 に無い画面（旅行の作成、予定の追加・編集・日の移動、取りやめの確認）のスクリーンショットをユーザーが確認する。
