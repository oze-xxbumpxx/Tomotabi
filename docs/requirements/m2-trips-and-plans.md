## 背景

M1で、登録済みの二人だけがログインでき、業務APIがGuardの渡すuserIdで動く土台ができた。M3以降の支払い・精算・記録は、すべて「どの旅行の、どの予定か」を前提にしている。そのためM2で、旅行と予定の作成・選択・編集と、その書き込みを安全にする共通の仕組み（ETagによる競合検出、Idempotency-Keyによる再送制御、旅行単位のロック順序）を先に固める。

## 目的

- 二人が旅行を作り、選び、手動で開始・終了でき、日ごとの予定（しおり）を追加・編集・日の移動・取りやめできる。
- 旅行作成で参加者二人と金融guardが同じトランザクションで作られること、日付・ETag・取りやめの規則を、実API（実PostgreSQL）と画面で確認できる。
- 書き込みAPIの共通部品（ETag・Idempotency-Key・receipt・エラー形式・画面の保存状態）をM2で完成させ、M3の支払い・精算がそれを使うだけにする。

## ユーザー要求（原文の要約）

「M2（旅行・予定）の要件と設計を始める」。2026-09-27の確認で次を決定した。

- 達成・予約: M2では表（履歴・取消・有効占有）と、種類変更の判定（履歴があれば変更不可）だけを作る。達成・予約の追加・取消のAPIと画面はM4。
- 画面: handoff-v3の画面を完成度高く作る。v3に無い入力画面（旅行の作成、予定の追加・編集・日の移動、取りやめの確認）は、v3のトークンと部品（支払いを記録のシートなど）からAIが組み、実装後にスクリーンショットで確認してもらう。
- 結果不明の書き込みの復帰: M2はメモリ内まで（同じ要求で確かめる仕組み）。IndexedDBによる再読み込みを跨ぐ復帰はM3。
- webのライブラリ: 取得状態はTanStack Query、フォームはReactの状態＋既存のZod（ADR-0004）。

## 機能要件

### 旅行

| ID | 要件 |
|---|---|
| F-01 | 旅行を名前・開始日・終了日で作成する。参加者はサーバーがallowlistの二人（slot 0 / 1）から決め、クライアントから指定させない |
| F-02 | 旅行の作成と同じトランザクションで、参加者二人（trip_participants）、金融guard（trip_finance_guards）、再送receiptを作る。どれかが失敗したら全体をロールバックする |
| F-03 | 利用できる許可アカウントが二人揃っていなければ作成を拒否する（409 PARTICIPANTS_NOT_READY） |
| F-04 | 自分が参加している旅行だけを一覧する。並びは作成日時の新しい順（同時刻はidの降順）。状態の絞り込みとカーソルによる追加取得を持つ |
| F-05 | 旅行を1件取得する。応答にETag（旅行のversion）を付ける |
| F-06 | 旅行名を変更する（If-Match必須） |
| F-07 | 旅行期間を変更する（If-Match必須）。取りやめ済みを含むすべての予定が新しい期間に収まらなければ拒否し、予定を自動で動かさない |
| F-08 | 旅行を手動で開始（planning → traveling）・終了（traveling → finished）する。開始・終了した日時と操作者を保存する。日付による自動遷移、終了の取り消し、旅行の削除、参加者の変更は提供しない |
| F-09 | 終了後も、予定の追加・編集・日の移動・取りやめと、旅行名・期間の変更を許可する（終了はデータの凍結ではない） |

### 予定

| ID | 要件 |
|---|---|
| F-10 | 予定を追加する。名前・種類・日付は必須、時刻・メモは任意。日付は旅行期間内に限る |
| F-11 | 予定を1件取得する。現在の値、有効な達成・予約、種類変更の可否（canChangeKind）と不可の理由を返し、ETagを付ける |
| F-12 | 予定の名前・種類・時刻・メモを部分更新する（If-Match必須）。日付は含めない。実質同じ値ならversionを増やさない |
| F-13 | 予定の日を移動する（If-Match必須）。移動先は旅行期間内に限る |
| F-14 | 予定を取りやめる（If-Match必須）。取りやめた日時と操作者を一度だけ記録し、復活のAPIは持たない。取りやめ済みの予定もメモ等は編集できるが、編集で取りやめを解除しない |
| F-15 | 種類の変更は、達成・予約の履歴（取り消し済みを含む）が一度も無い予定に限る。履歴があれば拒否する（409 PLAN_HAS_RECORD_HISTORY） |
| F-16 | 日別しおりを取得する。旅行と指定日の予定一覧（取りやめ済みを含む）を返す。並びは時刻の早い順・時刻未定は末尾・登録日時・id。日付を省略したら、日本時間の今日が期間内なら今日、それ以外は初日にする |

### 書き込みの共通規則

| ID | 要件 |
|---|---|
| F-17 | すべての業務の書き込みにIdempotency-Key（UUID）を必須とする。同じ利用者・操作・キーの成功の再送は、If-Matchの再評価より先に、保存した元の結果（DTOとETag）を返す。同じキーで入力が違えば拒否する（409 IDEMPOTENCY_KEY_REUSED）。再送でも現在の認証・参加者の確認は行う |
| F-18 | 更新系はIf-Match（引用符付き10進数の強いETag、1つだけ）を必須とする。欠落は428 IF_MATCH_REQUIRED、不一致は409 VERSION_CONFLICT。ワイルドカード・弱いETag・複数値は受け付けない |
| F-19 | エラー応答は`{ code, message, requestId, retryable }`とする。画面はcodeで分岐し、messageをそのまま表示しない |
| F-20 | 旅行・予定のAPIは、Guardの検証済みuserIdがその旅行の参加者であることを毎回確認する |

### 達成・予約の土台

| ID | 要件 |
|---|---|
| F-21 | 達成・予約の履歴（plan_events）、取消（plan_event_cancellations）、有効占有（active_plan_events）の3表を作る。履歴と取消は追記のみで、UPDATE / DELETEをDBで拒否する。M2では書き込むAPIを持たない（M4） |
| F-22 | 予定の取得・しおりは、有効な達成・予約を結合して返す（M2では常にnullになるが、表に行があれば正しく返す） |

### 画面

| ID | 要件 |
|---|---|
| F-23 | ログイン後の入口: 前回選んだ旅行（利用者ごとにブラウザへ保存）が取得・参加確認できればその旅行のしおりへ、できなければ旅行一覧へ進む。保存したidを権限の根拠にしない。ログアウトで消す |
| F-24 | 旅行一覧（v3の15切り替え・19旅行0件）と旅行の作成画面（v3に無い。v3の部品から組む） |
| F-25 | 旅行のヘッダーとメニュー（v3の16〜18）。旅行名・期間の変更、開始・終了（終了は確認ダイアログ17） |
| F-26 | しおり（v3の08）と予定の詳細（v3の09）。予定の追加・編集・日の移動・取りやめ（v3に無い。v3の部品から組む） |
| F-27 | 共通の状態: 読み込み・更新中・更新できていません（v1）、ログイン切れ（C-1）、開けない（C-2）、オフライン（C-3）、保存の結果が不明（C-4）、競合（C-5） |

## 非機能要件（性能・セキュリティ・可用性など）

- 整合性: 旅行・予定の書き込みは、旅行 → 予定の順でロックする（旅行はFOR SHARE、期間変更と旅行自体の更新はFOR UPDATE、予定はFOR NO KEY UPDATE）。M3以降の財務は別のtrip_finance_guardsを使い、予定と逆順にロックしない。
- セキュリティ: 他人の旅行の名前・件数・存在を返さない。参加していない旅行と存在しない旅行は同じ403にする。Googleのsub・メールを応答に含めない。receiptにセッショントークン等を保存しない。
- 可用性: DBに接続できないときは503。画面は503・通信失敗を「保存失敗」と断定せず、結果不明（C-4）として同じ要求で確かめる。
- 時刻: 日付はdate（`YYYY-MM-DD`）、時刻は秒とタイムゾーンを持たない`HH:mm`（日本時間の現地時刻）、履歴の日時はtimestamptz。時刻未定を00:00に変換しない。「今日」はAsia/Tokyoで決める。
- 入力の上限: 旅行名・予定名1〜100文字（前後の空白を除いて空でない）、メモ2,000文字。文字数はUnicodeのコードポイント数で数える。
- 性能: 目標値は対象外（二人利用）。しおりは1日分を1回の読み取りで返す。
- アクセシビリティ: 入力に可視ラベル・エラーの関連付け。取りやめ・エラーを色だけで区別しない。完了・失敗を読み上げ領域でも伝える。

| ID | 内容 |
|---|---|
| N-01 | 二人が登録済みのとき、旅行を作成すると201で旅行DTOとETagが返り、参加者2行・guard 1行・receipt 1行が同じトランザクションでできる |
| N-02 | 旅行一覧は自分が参加する旅行だけを新しい順で返し、カーソルで続きを取得できる。状態で絞り込める |
| N-03 | 旅行名の変更でversionが1増え、新しいETagが返る |
| N-04 | 期間の変更は、全予定（取りやめ済みを含む）が新期間に収まれば成功する |
| N-05 | 開始でtravelingになりstarted_at / started_byが入る。終了でfinishedになりfinished_at / finished_byが入る |
| N-06 | 終了後も予定の追加・編集・移動・取りやめ、旅行名・期間の変更ができる |
| N-07 | 予定を追加すると201で予定DTOとETagが返る。時刻未定はnullのまま保存・表示される |
| N-08 | 予定の部分更新・日の移動・取りやめでversionが1増える。実質同じ値の更新はversionを増やさず200を返す |
| N-09 | 履歴の無い予定は種類を変更できる |
| N-10 | しおりは指定日の予定を、時刻順・未定は末尾・登録日時・idの順で、取りやめ済みも含めて返す。日付を省略すると今日（期間内）または初日になる |
| N-11 | 同じIdempotency-Key・同じ入力の再送は、元の結果（状態コード・DTO・ETag）を返し、行を増やさない。その後に相手が更新していても、再送は元のDTOを返す |
| N-12 | 画面: 旅行を作ってしおりへ進み、予定を追加・編集・移動・取りやめし、旅行を開始・終了できる（ローカルのMacのブラウザで二人分を確認） |
| N-13 | 画面: 前回選んだ旅行が有効なら、ログイン後にその旅行のしおりが開く |

## 異常系

| ID | 内容 | 期待 |
|---|---|---|
| E-01 | allowlistの二人が揃っていない（1人だけ・一方が無効）で旅行を作成 | 409 PARTICIPANTS_NOT_READY。何も作られない |
| E-02 | 旅行の作成の途中で失敗（例: guardの作成で失敗） | 旅行・参加者・guard・receiptのどれも残らない |
| E-03 | 参加していない旅行・存在しない旅行の取得・更新 | 403（両者を区別しない） |
| E-04 | 認可済みの旅行に属さない予定id（別の旅行の予定を含む） | 404 |
| E-05 | 更新でIf-Matchが無い | 428 IF_MATCH_REQUIRED |
| E-06 | If-Matchが古い（相手が先に更新した） | 409 VERSION_CONFLICT。相手の変更を上書きしない |
| E-07 | If-Matchが不正な形式（`*`、`W/"1"`、複数値、引用符なし） | 400 |
| E-08 | 同じIdempotency-Keyで入力（body・If-Match・対象）が違う | 409 IDEMPOTENCY_KEY_REUSED |
| E-09 | Idempotency-Keyが無い・UUIDでない | 400 |
| E-10 | 予定の日付・日の移動先が旅行期間の外 | 422 PLAN_OUTSIDE_TRIP_PERIOD |
| E-11 | 期間の変更で、はみ出す予定（取りやめ済みを含む）がある | 422 PLAN_OUTSIDE_TRIP_PERIOD。予定も期間も変わらない |
| E-12 | 達成・予約の履歴（取り消し済みを含む）がある予定の種類変更 | 409 PLAN_HAS_RECORD_HISTORY。他の項目も変更しない |
| E-13 | 取りやめ済みの予定をもう一度取りやめる（別のキー） | 409 PLAN_CANCELLED |
| E-14 | 不正な状態遷移（finished → start、planning → finish） | 409 INVALID_TRIP_TRANSITION |
| E-15 | 入力の不正（名前が空白だけ・101文字、開始日 > 終了日、実在しない日付、時刻が`24:00`や秒付き、メモ2,001文字、未知の項目、未知の種類） | 422（形式違反は400） |
| E-16 | Origin不一致・Content-Type違い（M1の共通Guard） | 403 / 415 |
| E-17 | 同じキーで二つの旅行の作成が同時に走る | 片方だけが成立し、もう片方は同じ結果（同じ旅行）を返す。旅行は1件だけ |
| E-18 | 予定の追加・日の移動と期間の変更が同時に走る | 期間外の予定が成立しない |
| E-19 | 種類変更と達成の記録（M2ではテストで表へ直接挿入）が同時に走る | 記録が先なら種類変更を拒否する（予定のロックを共有する） |
| E-20 | app_runtimeで履歴・取消表へのUPDATE / DELETE、receipt・参加者へのUPDATE / DELETE、DDL | 権限エラーまたはトリガーで拒否 |
| E-21 | 画面: 保存中に通信が切れた・5xx | 「保存されたか確認できません」（C-4）。入力を固定し、同じ要求（同じキー・本文・If-Match）でだけ確かめられる |
| E-22 | 画面: VERSION_CONFLICT | 競合（C-5）。入力を残して最新と並べ、本人が選んで新しいETag・キーで保存する。自動で上書きしない |

## 境界条件（null・空・上限/下限・権限境界）

| ID | 内容 |
|---|---|
| B-01 | 旅行名・予定名は前後の空白を除いて1〜100コードポイント。絵文字（サロゲートペア）1つは1文字 |
| B-02 | 開始日 = 終了日（日帰り）は有効。開始日 > 終了日は無効 |
| B-03 | 予定の日付 = 開始日・終了日ちょうどは期間内 |
| B-04 | 時刻`00:00`と`23:59`は有効。nullは「時刻未定」で`00:00`と区別する |
| B-05 | メモの改行・内部の空白は保持する。空のメモはnullとして保存する |
| B-06 | 旅行一覧の上限（limit）の既定と最大は設計書で決める。0件は空配列 |
| B-07 | 同じ状態への遷移（travelingの旅行にstart）でETagが一致するなら200で現在の旅行を返し、version・日時を変えない |
| B-08 | PATCHの本文が空（項目0個）は400。nullを送った時刻・メモは消去 |
| B-09 | 前回選んだ旅行idが、参加していない・存在しない旅行を指す | 旅行一覧へ戻り、保存したidを消す |

## 前提

- M1がmainに入っていること（済み。M-06の利用停止の手動確認は未実施だがM2の前提にしない）。
- ローカル開発DBはcomposeのPostgreSQL 16。M1で二人を登録済みのDBを使って画面を確認する。

## 制約

- `sql/03`・`sql/04`・`sql/01`をそのまま本番migrationとして実行しない。Drizzleスキーマとカスタムmigrationに落とす（ADR-0003）。
- 別の業務領域の表へ直接書き込まない。予定の種類変更で使う履歴の照会は、planning側のIFとrecord側の読み取り実装をcompositionで結ぶ（詳細設計11 §5）。
- 通知（M5）・支払い（M3）・ホームの集約（M4）を先回りして作らない。
- 本番（Neon / Vercel）の作成・操作は行わない。

## 対象範囲

- `apps/api`: planningモジュール（旅行・予定のController / UseCase / Domain / Infrastructure）、recordモジュールの最小部分（履歴の照会）、共通の書き込み部品（Idempotency・ETag・エラー応答）、DBスキーマとmigration（planning / record / infraの各表とGRANT）
- `apps/web`: 旅行・しおり・予定の画面、共通の取得状態・保存状態、TanStack Queryの導入
- `packages/contracts`: 旅行・予定のOpenAPI（詳細設計の2ファイルからM2の操作を移植し、重複するgetTripを1つに統合）
- ADR-0004（webの取得状態ライブラリとAPIの入力検証）

## 対象外

- 達成・予約の追加・取消APIと画面、記録一覧（M4）
- ホームの集約API（GET /trips/{tripId}/home）とホーム画面の予定・精算・最近の記録（M4）
- 支払い・精算（M3）、通知（M5）
- IndexedDBによる未確定要求の永続化と再読み込み後の復帰（M3）
- オフラインしおり、持ち物・思い出、ダークモードの各画面の作り込み（後続）
- Playwright E2E（M2はVitest + Testing Libraryと実DBのHTTPテスト、画面は手動確認）

## 後方互換性・データ移行

- 既存の本番データは無い（本番DBは未作成）。M1のidentityスキーマは変更しない。
- ログイン後の入口が、M1の最小ホーム（表示名とログアウト）から、旅行一覧・しおりに変わる。表示名とログアウトは旅行の画面のメニューへ移す。
- `/api/foundation/*`の検証経路とwebの検証UIは、M2では変更しない（扱いは設計書の未決事項）。

## 受け入れ条件（Definition of Doneに対応）

1. N-01〜13、E-01〜22、B-01〜09を試験計画の観点に採番して反映し、自動テストで確認する。N-12・N-13の画面操作はローカルでの手動確認とし、結果を記録する。
2. 旅行の作成（参加者・guardの同時作成とロールバック）、ETagの競合、Idempotencyの再送・同時作成、期間と予定の競合を、実NestJS + 実PostgreSQL（Testcontainers）のHTTPテストで確認する。同時実行は2つの接続で再現する。
3. 空DBへのmigrationの適用と、app_runtimeの権限（許可・拒否）をTestcontainersで確認する。
4. 画面の保存状態（保存中・成功・拒否・結果不明・競合）をVitest + Testing Libraryで確認する。

6. v3に無い画面（旅行の作成、予定の追加・編集・日の移動、取りやめの確認）のスクリーンショットをユーザーが確認する。
