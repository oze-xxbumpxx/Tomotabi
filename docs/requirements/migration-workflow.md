# 要件定義: migration-workflow（migrationを出先からも流せるようにする）

- 変更レベル: L3（本番のDBに触る運用を変える。ADR-0003の決定を1つ改める。migratorの接続をGitHubに置く）
- 作成日: 2026-11-15
- ステータス: 承認待ち
- 決めたこと: `docs/discussions/migration-workflow.md`（確認のページ: https://claude.ai/artifact/AfuqoRSjeQbEJsVyrupZPt ）
- ADRの案: `docs/decisions/ADR-0011-migration-by-manual-workflow.md`（Proposed。この要件のPRのマージで承認とする）

## この文書の読み方

- **F-01などの番号**は機能要件、**E-01など**は異常系、**B-01など**は境界の番号。
- **migrationのボタン**は、GitHub Actionsの手動のワークフロー。スマートフォンのGitHubからも押せる。
- **migrator**は、表を作り変えられるDBのロール。その直接の接続が`MIGRATION_DATABASE_URL`。

## 背景

DBのmigrationは、管理者の端末から`npm run db:migrate`で流すと決めている（ADR-0003）。デプロイはGitHubのボタンでスマートフォンからも押せるが、migrationだけは端末が要る。出先ではDBを変える変更を出せない。11月9日には、migrationを流さないままデプロイして、本番のToDoが読み込めなくなった。

## 目的

- 管理者が、出先からでも、検証用と本番のmigrationを自分の意思で流せる。
- 流れるものを見てから承認でき、レビューしていないSQLは流れない。
- migratorの接続を読めるのは、migrationを流すジョブだけにする。

## ユーザー要求（原文の要約）

「出先の時もあるので、改善を行いたい」。2026-11-15に確認のページで5つを決めた（理由と選ばなかった案は論点の記録）。

- 検証用と本番の両方を、ボタンで流せるようにする。
- 本番のバックアップの決まりは変えない。本番のボタンは、端末でバックアップを取ってから押す。
- 流す前に、流れるmigrationの一覧を見て承認する。
- migrationのボタンは、デプロイのボタンと分ける。
- 端末から流す今の手順は、予備として残す。

## 機能要件

| ID   | 要件                                                                                                                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| F-01 | migrationのボタンを、検証用（`migrate-integration`）と本番（`migrate-production`）の2つ作る                                                                                                      |
| F-02 | デプロイのボタンは変えない。デプロイのワークフローはmigrationを流さない                                                                                                                          |
| F-03 | 流せるのは、`main`の履歴にあるcommitのmigrationだけ。既定は`main`の最新。SHAを指定するときは40桁で入れる                                                                                         |
| F-04 | ボタンを押すと、まず「これから流すmigration」の一覧（名前）をワークフローの画面に出す。この段階ではDBを変えない                                                                                  |
| F-05 | 一覧を出したあと、Environmentの承認で止まる。管理者が承認したら流す。承認しなければ何も流れない                                                                                                  |
| F-06 | 流すものが1本も無ければ、「流すものはありません」と出して、承認を求めずに成功で終わる                                                                                                            |
| F-07 | 本番のボタンの一覧の画面に、「本番でDBを変える前に、バックアップを取って照合したか」を確かめる文と、手順書の場所を出す。バックアップを取ったかどうかを、ワークフローは確かめない（人が確かめる） |
| F-08 | 流し終えたら、流したmigrationの名前と、DBの最後のmigrationをワークフローの画面に出す                                                                                                             |
| F-09 | 同じ環境のmigrationのボタンは、同時に2つ動かない。あとから押したものは、前のものが終わるまで待つ                                                                                                 |
| F-10 | 端末から流す手順（`npm run db:migrate`）は残す。どちらで流しても、Drizzleの履歴の表に同じ記録が残り、もう片方から見て「流し済み」になる                                                          |
| F-11 | 手順書（検証用・本番）に、migration専用のEnvironmentの作り方、ボタンでの流し方、migratorのパスワードを替えたときに秘密を入れ直す手順を足す                                                       |

## 非機能要件

- セキュリティ: migratorの接続は、migration専用のEnvironmentの秘密に置く。そのEnvironmentを使えるブランチは`main`だけにし、承認を必須にする。デプロイのジョブ、PRのCI、ブランチのワークフローは、この秘密を読めない。
- セキュリティ: 接続文字列・パスワードを、ワークフローのログと画面に出さない。SQLのエラーの文は出してよいが、接続文字列を含む文は出さない。
- セキュリティ: 一覧を出す段階（承認の前）も、migratorの接続を使う。この段階は読むだけにする。
- 記録: 誰が・いつ・どのcommitのmigrationを流したかが、ワークフローの実行の履歴で追える。
- 可用性: GitHubが使えないときは、端末から流せる（F-10）。
- 性能: 対象外（migrationは数本で、手で押すときだけ動く）。

## 正常系

1. 出先で、DBを変えるPRをマージする。スマートフォンのGitHubで`migrate-integration`を押す。
2. 画面に「これから流すmigration: 0013_todo_categories、0014_todo_categories_grants」と出て、承認を求められる。承認すると流れ、流した名前が出る。
3. `deploy-integration`で検証用に出し、画面を確かめる。
4. 本番は、出かける前に端末でバックアップを取って照合してある。`migrate-production`を押し、一覧とバックアップの確かめの文を読んで承認する。
5. `deploy-production`で本番に出す。

## 異常系

| ID   | 場面                                                                        | 振る舞い                                                                                                              |
| ---- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| E-01 | 指定したcommitが`main`の履歴に無い、SHAが40桁でない                         | DBにつながずに止める。理由を出す                                                                                      |
| E-02 | migratorの接続の秘密が置かれていない                                        | 止める。どのEnvironmentの何が無いかを出す（値は出さない）                                                             |
| E-03 | DBにつながらない                                                            | 止める。何も流れていない                                                                                              |
| E-04 | migrationの途中でSQLが失敗した                                              | 止める。どのmigrationで失敗したかを出す。失敗したmigrationは流し済みにならない。前のmigrationまでは流し済みのまま残る |
| E-05 | 承認しないまま時間が過ぎた、または拒んだ                                    | 何も流れない                                                                                                          |
| E-06 | 一覧を出してから承認するまでのあいだに、端末から同じものを流した            | 承認のあと、流すものが無ければ何もせず成功で終わる。一覧と違っていたら、実際に流したものを出す                        |
| E-07 | DBが、指定したcommitより新しいmigrationまで流し済み（前のcommitを指定した） | 「流すものはありません」で終わる。DBは戻さない                                                                        |
| E-08 | `main`以外のブランチから、このワークフローを動かそうとした                  | Environmentの決まりで、秘密を読めずに止まる                                                                           |

## 境界条件

| ID   | 条件                                                                                                          |
| ---- | ------------------------------------------------------------------------------------------------------------- |
| B-01 | 流すものが0本。承認を求めずに終わる（F-06）                                                                   |
| B-02 | DBに1本も流していない（最初の構築）。ボタンでは扱わない。ロールを作る最初の構築は、今の手順書どおり端末で行う |
| B-03 | 検証用のボタンは検証用のDBだけ、本番のボタンは本番のDBだけに流す。取り違えないよう、Environmentと秘密を分ける |

## 前提

- migrationは後方互換の追加だけにしている（`docs/runbooks/production.md` 12章）。流してから出すまでのあいだも、前の版のapiは動く。
- デプロイのボタンと同じく、Environmentの承認はGitHubの機能を使う。

## 制約

- 「自動では流さない。管理者が明示的に流す」は変えない（ADR-0003の決定3の考え方）。PRのCI・マージ・デプロイをきっかけには流さない。
- 本番のバックアップは今のまま端末で取り、実データを端末の外に出さない（`docs/runbooks/backup-and-restore.md`）。

## 対象範囲

- ワークフロー: `.github/workflows/`に、migrationのボタン2つと、共通の処理。
- スクリプト: 流すものの一覧を出す処理（`_journal.json`とDBの履歴の表を比べる）。
- 文書: ADR-0011（ADR-0003の決定3を改める）、手順書（`docs/runbooks/integration-env.md`・`production.md`）、`docs/designs/migration-deploy-check.md`の止めたあとの案内。
- GitHubの設定（ユーザーが行う）: migration専用のEnvironmentを2つ作り、秘密を置く。

## 対象外

- デプロイのボタンがmigrationも流すこと。
- 本番のバックアップをワークフローで取ること。Neonの「時点を指定して戻す」機能でバックアップに代えること（使えるかを確かめてから、別に提案する）。
- migrationを戻す（巻き戻す）ボタン。
- ロールを作る最初の構築をボタンにすること。
- 流し忘れをデプロイの前に止める仕組み（`migration-deploy-check`）の実装。この機能のあとに、案内の文を直して実装する。

## 後方互換性・データ移行

- 表とデータは変えない。
- 端末からの流し方は変わらない。
- ADR-0003の決定3の「管理者の端末から」を、「管理者の端末、または承認つきの手動のワークフローから」に改める（ADR-0011）。

## 受け入れ条件

- F-01〜F-11、E-01〜E-08、B-01〜B-03を満たす。一覧を出す処理は、自動の試験で確かめる（流し済み・一部だけ流し済み・0本・DBの方が新しい）。
- ワークフローは、検証用で実際に動かして確かめる（流すものがある・無い・承認しない）。
- `main`以外のブランチから動かしても、migratorの接続を読めないことを、検証用のEnvironmentで確かめる。
- ログに接続文字列が出ないことを、検証用の実行のログで確かめる。
- 品質コマンド（`npm run lint` / `npm run type-check` / `npm test` / `npm run build`）と`npm run test:harness`が通る。

## 未決事項

論点の記録で、仮決定が3件。migratorの接続はmigration専用のEnvironmentに置く、流せるのは`main`のcommitだけ、`migration-deploy-check`はこの機能のあとに実装する。設計の承認までに異議がなければ決定にする。
