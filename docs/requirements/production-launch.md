# 要件定義: 本番の公開（production-launch）

- task-id / 変更レベル: production-launch / L3（本番の環境の新設。本番のGoogleログイン・秘密情報・二人の実データに触れる）
- 作成日: 2026-10-29

## 背景

結合検証環境で、ログイン・旅行と予定・支払いと精算・通知を、二人の実機で確かめた。主な点検は合格し、見つかった問題も直した（docs/tests/integration-env.md）。設計資料（詳細設計08「Vercel＋Neonのデプロイと無料枠運用」と「運用設定と公開チェック」）は、本番の環境を作ること、バックアップと復元の確かめ、公開の順番、公開前の確認（OPS-01〜18）の残りを、公開準備の段階に回している。

## 目的

二人が実際の旅行で使う本番の環境を作り、公開する。支払いと精算の記録を失っても戻せるよう、初回の公開の前にバックアップと復元を確かめる。

## ユーザー要求（原文の要約）

- そろそろ本番の公開に移ってよいと判断した（2026-10-28）。
- 公開するのは、二人で使う本番。一般への公開や商用にはしない（2026-10-28）。

## 機能要件

| ID   | 要件                                                                                                                                                                                                                                                                                                      |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P-01 | 本番を作る前に、結合検証環境の残りの点検を済ませる。APIのURLへの直接の要求と別の旅行への要求（IE-05）、接続の設定（IE-06）、使わない接続が手放されるか（IE-07）、実行用ロールの制限（IE-09）、使用量（IE-14）、main以外のブランチから出せないか（IE-15）。見つかった問題は、本番を作る前に直す            |
| P-02 | 本番の環境として、Vercelに画面とAPIの2プロジェクト、Neonに本番のプロジェクトを作る。地域は検証用と同じく、Vercelの関数をsin1（シンガポール）、NeonをAWS Singapore（ap-southeast-1）にする。PostgreSQLの版は16（手元・CI・検証用と同じ）                                                                   |
| P-03 | 本番の設定（環境変数）を、`運用設定と公開チェック.md`の1節の表と、検証用の手順書（docs/runbooks/integration-env.md の6章）の形で置く。秘密情報は検証用と共有せず、本番用に作り直す。通知の運用者の連絡先（`VAPID_SUBJECT`）は、検証用と同じくこのリポジトリのGitHubのURLにする                            |
| P-04 | 本番のNeonに、管理用（migrator）と実行用（app_runtime）のロールを作り、migrationを管理者の端末から1回だけ適用する。二人の普段のGoogleアカウントを、初期登録のCLIで登録する                                                                                                                                |
| P-05 | 本番のGoogleのOAuthのクライアントを、検証用とは別に2つ作る（ログイン用と初期登録のCLI用）。同意の画面は「テスト」のままにし、テストユーザーに二人だけを足す                                                                                                                                               |
| P-06 | 本番のVAPIDの鍵を、検証用とは別に1組作る                                                                                                                                                                                                                                                                  |
| P-07 | 本番へのデプロイは、検証用と同じ形のGitHub Actionsのボタン（手動で動かすワークフロー）で行う。GitHubのEnvironment「production」を新しく作り、本番用の期限つきのVercelのトークンを置き、実行に承認を必須にし、mainだけから動かす。CIが通ったcommitだけを出せる。mainへのマージで本番に自動でデプロイしない |
| P-08 | 本番の手順書を書く。環境を作る手順、公開の順番（DB → API → 画面、詳細設計08の7節）、公開の記録（「運用設定と公開チェック」4節のテンプレート）、日常の運用（使用量の確かめ、バックアップ）、障害のときに最初に残す情報（同5節）                                                                            |
| P-09 | 本番のDBのバックアップを、管理者の端末から直接の接続の`pg_dump`で取り、暗号化して手元のPCに置く。普段使っているクラウドのストレージにも、暗号化したコピーを置く。直近4回と、変更の前の1回を残す。暗号の鍵（パスフレーズ）は、PCとは別のところ（パスワード管理ソフトなど）に控える                         |
| P-10 | バックアップは、利用中は週1回、旅行の前・旅行の終わったあと・DBを変える前に、手動で取る                                                                                                                                                                                                                   |
| P-11 | 初回の公開の前に、暗号化したdumpを隔離したDBへ戻し、件数・金額・占有の表を照合する（OPS-13）。戻したDBのセッションの失効と通知の購読の停止、ロールの作り直しも確かめる                                                                                                                                    |
| P-12 | 下の「確かめること」を本番で確かめ、日付・環境・根拠を公開の記録に残す                                                                                                                                                                                                                                    |

### 確かめること（P-12）

公開準備に回した確認（`運用設定と公開チェック.md`の3節）は全部確かめる。検証用で確かめた確認は、本番では設定の誤りを見つけるための短い確かめにする。

| ID         | 確かめること                             | 本番での確かめ方                                                                                                       |
| ---------- | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| OPS-01     | Vercel・Neon・GitHubのプランと課金の制御 | 全部確かめる。無料のプランで、意図しない有料の連携が無く、GitHubの有料の追加使用が止まっている                         |
| OPS-02     | 環境の分離                               | 全部確かめる。PRに本番の秘密が無い。検証用から本番のDBにつながらない。復元したコピーから通知を送らない                 |
| OPS-03〜05 | 転送・Cookieとヘッダー・キャッシュ       | 短く。画面から`/api`に届く。ログインとログアウトでCookieが付いて消える。`/api`の応答にキャッシュを止めるヘッダーがある |
| OPS-06     | Googleと二人の制限                       | 短く。二人がログインでき、登録していないアカウントが断られる。公開URLでVercelのログインを求めない                      |
| OPS-07・08 | DBの接続・休止                           | 短く。pooledの接続で動き、Neonの休止のあとの最初の操作が成功する                                                       |
| OPS-09     | DBの同時操作                             | 本番では確かめない（実際の金銭の受け渡しを作らないため。検証用のIE-08で合格）                                          |
| OPS-10     | 実行用のロール                           | 短く。実行用のロールで、履歴の表の更新とDDLが断られる                                                                  |
| OPS-11     | 通知                                     | 短く。二人の端末に通知が1件届く。通知は実機で届いてから有効にする                                                      |
| OPS-12     | CIと公開の順番                           | 全部確かめる。CIが通ったcommitだけが出て、DB → API → 画面の順で出せる。mainへのpushで本番が切り替わらない              |
| OPS-13     | dumpと復元                               | 全部確かめる（P-11）                                                                                                   |
| OPS-14     | コードの巻き戻し                         | 全部確かめる。前の版が、今のschemaで動く                                                                               |
| OPS-15     | 完全停止                                 | 全部確かめる。古いデプロイと直接のAPIも含めて、書き込みを止められる                                                    |
| OPS-16     | 秘密とログ                               | 全部確かめる。画面のbundle・ログ・CIの成果物に、秘密の値とdumpが無い                                                   |
| OPS-17     | 実機の画面                               | 短く。二人が本番で旅行を1つ作り、開ける                                                                                |
| OPS-18     | 利用量                                   | 全部確かめる。公開のあとの使用量を記録し、無料枠の余裕を確かめる                                                       |

## 非機能要件

- 費用: Vercel Hobby・Neon Free・GitHub Freeの範囲にとどめる。週1回と旅行の前に使用量を見て、7割で原因を確かめ、9割で検証用のデプロイと実行を止める（詳細設計08の2節）。課金に進まず、超えそうなら公開と更新を止める。
- セキュリティ: 本番の秘密情報（DBの接続、Better Authの乱数、ログイン用と初期登録用のGoogleのシークレット、VAPIDの秘密鍵、Vercelのトークン）は、ユーザーが管理画面で登録する。Claude Codeは値を見ない。検証用と共有しない。`trustedOrigins`は本番の画面のURLだけ。本番のdumpは、Git・設計資料・Actionsの成果物に入れない。
- データの保全: 失うおそれがあるのは、最後に取ったバックアップより後の記録（Neonの短い復元の期間は最大6時間）。復旧は、管理者が取りかかった当日中を目標にする（詳細設計08の8節）。
- 可用性: keep-aliveや定期のDBへの接続は置かない。Neonの休止からの最初の操作は、待ったうえで成功すればよい。

## 正常系

| ID   | 流れ                                                                              |
| ---- | --------------------------------------------------------------------------------- |
| N-01 | 二人が普段のGoogleアカウントで、本番の画面にログインできる                        |
| N-02 | 二人が本番で旅行を作り、予定・支払い・精算・記録を使える                          |
| N-03 | 一人の操作のあと、もう一人の端末に通知が届く                                      |
| N-04 | 管理者がActionsのボタンでcommitを指定し、承認すると、本番にそのcommitが出る       |
| N-05 | 管理者がバックアップを取り、暗号化して2か所に置ける。隔離したDBへ戻して照合できる |

## 異常系

| ID   | 起きること                                                    | 期待                                                                                    |
| ---- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| E-01 | 登録していないGoogleアカウントでログインする                  | Googleの同意の画面か、アプリの許可リストで断られる                                      |
| E-02 | mainに入っていないcommit、CIが失敗したcommitを出そうとする    | ワークフローが止まり、本番は変わらない                                                  |
| E-03 | 本番のデプロイの途中で失敗する（APIだけ出て画面で止まるなど） | 止まった手順が記録に残り、同じcommitで出し直せる。DBは巻き戻さない                      |
| E-04 | アプリの不具合が本番で見つかる                                | 前の版のweb・apiに戻す。DBは戻さない（詳細設計08の8節）                                 |
| E-05 | 本番のDBの記録が壊れた・消えた                                | 書き込みを止め、隔離したDBへ戻して照合してから切り替える（詳細設計08の8節の復旧の手順） |
| E-06 | 無料枠の9割に届く                                             | 検証用のデプロイと実行を止める。超えそうなら本番の公開と更新を止める                    |

## 境界条件

- 利用を許すのは二人（許可リストの2枠）だけ。Googleの同意の画面のテストユーザーも二人だけ。
- バックアップは直近4回と、変更の前の1回を残す。それより古いものは消してよい。
- Vercelのトークンには期限を付ける。期限が来たら作り直す。
- APIの1回の実行は60秒まで。DBのロック待ちは3秒、SQLは5秒まで（検証用と同じ）。

## 前提

- 二人の個人利用。Vercel Hobby（個人の非商用のプラン）とNeon Freeで、独自ドメインと有料の追加は使わない（詳細設計08の1節）。
- 利用規約とプライバシーポリシーのページは作らない（#245を2026-10-28に閉じた）。
- 本番のデータは空から始める。結合検証環境の架空のデータは移さない。
- 結合検証環境は残し、公開後の変更は本番の前にそこで確かめる。
- アカウントの設定、プロジェクトの作成、秘密情報の登録、バックアップの取得はユーザーが行う。Claude Codeは手順書、本番のデプロイのワークフロー、アプリ側で要る作りを用意する。

## 制約

- Vercel Hobbyは個人の非商用の利用に限る。関数は1つの地域だけで動く。
- Neon Freeは無操作5分で休止し、復元の履歴は最大6時間。外向きの転送量を超えるとcomputeが止まり、dumpのダウンロードも転送量を使う。
- 本番のDBの秘密を、PRのCIに渡さない。migrationは管理者の端末から行う（詳細設計08の7節）。
- `pg_dump`は、サーバーと合う版（PostgreSQL 16に対応するもの）を使う。

## 対象範囲

- 本番の環境（Vercelのweb・api、Neonのproduction、GoogleのOAuthのクライアント2つ、VAPIDの鍵）を作る手順書（`docs/runbooks/`）
- 本番へのデプロイのワークフロー（`.github/workflows/`）
- バックアップと復元の手順と、隔離したDBでの照合の手順
- 完全停止（OPS-15）とコードの巻き戻し（OPS-14）の手順。アプリ側の作りが要るかは設計で決める
- 公開前の確認の記録と、公開の記録
- 結合検証環境の残りの点検（P-01）と、見つかった問題の直し
- 設計資料の「運用設定と公開チェック」のうち、今のコードと食い違う表の直し

## 対象外

- 一般への公開、商用の利用、有料のプラン、独自ドメイン
- 利用規約とプライバシーポリシーのページ
- 自動の定期バックアップ（Cron）、外部の監視（Sentryなど）、ログの転送
- 結合検証環境のデータを本番に移すこと
- アプリの機能の追加
- 本番での同時操作の確かめ（OPS-09。実際の金銭の受け渡しを作らないため）

## 後方互換性・データ移行

対象外（新しい本番の環境に、今のmigrationを最初から適用する。既存のデータは無い）。公開のあとのDBの変更は、詳細設計08の8節のとおり後方互換の追加を基本にする。

## 受け入れ条件

- 結合検証環境の残りの点検（P-01の6件）を確かめ、検証の記録にある。見つかった問題は直してある。
- 本番の環境が動き、二人が普段のGoogleアカウントでログインして旅行を作れる。
- 本番へのデプロイが、承認とmainだけの制限つきのActionsのボタンで動き、CIが通っていないcommitでは止まる。
- 初回の公開の前に、暗号化したdumpを隔離したDBへ戻して照合した記録がある。
- 「確かめること」の全項目を確かめ、公開の記録に日付・環境・根拠がある。
- 秘密情報とdumpが、リポジトリ・ログ・CIの成果物に無い。
- 手順書があり、ユーザーが手順書だけで本番を作り、出し、バックアップを取れる。
- ワークフローやアプリ側の作りを変えたときは、試験があり、品質ゲート（lint・type-check・test・build）が通る。
