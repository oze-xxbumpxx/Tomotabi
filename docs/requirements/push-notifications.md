## この文書の読み方

- **F-01などの番号**は機能要件の番号、**E-01など**は異常系（うまくいかない場面）の番号、**B-01など**は境界の番号。設計書と試験計画から「どの要件を満たすか」を指すために付けている。
- **購読**は、ある端末のブラウザが「この宛先に送れば、この端末に通知が出る」とAPIに登録したもの。宛先（endpoint。通知の配信サービスのURL）と、中身を暗号化するための鍵の組でできている。
- **配信サービス**は、ブラウザの会社が用意している通知の中継（ChromeならGoogleのFCM、iPhoneならAppleのサーバー）。APIはここへ送り、ここが端末へ届ける。
- **VAPIDの鍵**は、APIが「このアプリからの通知だ」と配信サービスに示すための鍵の組。秘密鍵はAPIだけが持ち、公開鍵をブラウザに渡す。
- **相手**は、操作をした人ではないほうの参加者。旅行の参加者は二人で決まっている。

## 背景

記録と4画面ができたので、設計資料の作る順番で次にあたる「通知」に入る。
二人のうち片方が予定を足したり支払いを記録したりしても、もう片方はアプリを開くまで気づけない。
設計方針の合意事項は、アプリを開いていない間も相手の操作をスマートフォンに知らせると決めている。詳細設計「Web Push通知」に、方式・DB・API・送る操作・通知から開く画面・ログアウトのときの止め方まで書いてある。
今のアプリにはService Workerもホーム画面に追加するための設定（manifest）も無く、ログアウトはBetter Authのサインアウトを呼ぶだけ。

## 目的

- 相手が11種類の操作（予定の追加・取りやめ・日の移動、達成・予約・支払いの記録と取り消し、精算の完了と取り消し）をしたとき、アプリを開いていなくても自分の端末に通知が出る。
- 通知を押すと、その操作の対象（予定・記録・精算）を開ける。
- 端末ごとに通知を有効にでき、止められる。ログアウトした端末には新しい通知が届かない。
- 通知が届かなくても、保存した操作は成功のまま。アプリを開けば最新の状態が見られる。

## ユーザー要求（原文の要約）

「1の通知で進めてください」。2026-10-07に確認のページで次を決めた（理由と選ばなかった案は論点の記録）。

- 作る範囲: 設計資料のとおり全部。古い鍵を残して購読ごとに使い分ける鍵の入れ替えも含める（推奨は「鍵は1つにする」だった）。
- 実機で確かめる時期: 今回は手元のPCのChromeで確かめ、iPhone・Androidの実機は結合検証の環境を作る回で確かめる。
- 通知の設定の画面の入口: 旅行のメニュー（右上の「…」）に「この端末の通知」の行を足す。
- 有効にするよう勧めるか: この端末で有効でなければ、ホームの上部に案内のカードを出す。閉じたらその端末では出さない。
- 本文: 相手の名前と旅行の名前を入れる（「あおいが「沖縄旅行」で予定を追加しました」。推奨は決まった文だけだった）。
- 精算の通知の行き先: 精算の画面を開き、精算の履歴のその1件を目立たせる。

仮決定（異議がなければ設計の承認で決定にする）: 通知のタイトルは「tomotabi」。アプリを開いているときに通知が来ても、画面は自動で読み直さない。

## 正常系

- 片方の端末で通知を有効にし、もう片方が支払いを記録すると、通知が出る。押すと記録の一覧のその1件が開く。
- 予定の追加・取りやめ・日の移動、達成・予約の記録と取り消し、精算の完了と取り消しでも、同じように通知が出て、押すと対象を開ける。
- 自分の操作では、自分のどの端末にも通知が出ない。
- 設定の画面で止めると、その端末には届かなくなる。ほかの端末には届く。
- ログアウトすると、その端末には新しい通知が届かない。
- ホームの案内のカードから有効にでき、閉じたカードはその端末で出ない。

## 異常系

| ID   | 場面                                                      | 期待                                                                                 |
| ---- | --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| E-01 | 通知を送るのに失敗した（配信サービスの5xx・時間切れなど） | 保存の応答は成功のまま。購読は残す。送り直さない                                     |
| E-02 | 配信サービスが404・410を返した                            | 購読を無効にする（同じ版のときだけ）。業務の保存には影響しない                       |
| E-03 | 許していないホストの宛先を登録しようとした                | 422 `UNSUPPORTED_PUSH_SERVICE`。画面は通知が使えないことを出し、アプリのほかは使える |
| E-04 | 鍵の形が違う購読を登録しようとした                        | 422 `INVALID_PUSH_SUBSCRIPTION`。形・大きさが崩れた本文は400                         |
| E-05 | 登録のkeyIdが今の鍵と違う                                 | 409 `PUSH_KEY_CHANGED`。端末は公開鍵を取り直して登録し直す                           |
| E-06 | 4台目を有効にしようとした                                 | 409 `PUSH_LIMIT_REACHED`。ほかの端末で止める案内                                     |
| E-07 | ログアウトで止めたログインから購読を登録した              | 409 `PUSH_SESSION_CLOSED`                                                            |
| E-08 | ログアウトの前の、通知を止める処理が失敗した              | 503。ログアウトできたと出さず、もう一度押せる                                        |
| E-09 | 別の人が登録している宛先を登録しようとした                | 409 `PUSH_ENDPOINT_OWNED_BY_OTHER`。持ち主を黙って移さない                           |
| E-10 | 通知の中身が決まった形でない                              | 汎用の文で出し、押すと旅行一覧（F-45）                                               |
| E-11 | 通知から開いた対象が無い・権限が無い                      | 「この項目を開けません」と旅行一覧への案内                                           |
| E-12 | VAPIDの設定が違い、配信サービスが401・403を返した         | 設定を調べるログを出す。購読は消さない。業務の保存には影響しない                     |

## 境界条件

| ID   | 条件                                                                                                              |
| ---- | ----------------------------------------------------------------------------------------------------------------- |
| B-01 | 有効な購読が2台なら3台目を登録できる。3台あれば4台目を断る。期限の過ぎた購読は、数える前に無効にする              |
| B-02 | 期限（expirationTime）がnullの購読は期限なし。値があれば未来の日時だけ受け付ける                                  |
| B-03 | 旅行の名前が100文字、相手の名前がどれだけ長くても、APIが送る通知の中身は2KB以内になる                             |
| B-04 | 相手が利用を止められている（利用許可を外された）ときは、その人には送らない                                        |
| B-05 | 旅行が終了したあとの操作も、11種類なら送る（旅行の状態で送るかを変えない）                                        |
| B-06 | 宛先のホストが`fcm.googleapis.com.evil.example`のような末尾の一致、IPアドレス、localhost、443以外のポートなら断る |

## 前提

- 通知の方式は、ブラウザ標準のWeb Push（Service Worker＋VAPID）。APIは`web-push`で暗号化と署名をし、NodeのHTTPSで送る。有料の通知サービスは使わない。
- 届かないことは許す（設計方針の合意事項 2026-09-05）。通知は業務のデータの正本にも、領域どうしの同期にも使わない。
- iPhoneはiOS 16.4以降でホーム画面に追加したアプリから。Androidは、まずChromeで確かめる。
- 記録の一覧を1件に絞るURLは、記録と4画面で作った`?recordType=&recordId=`を使う（設計資料の案は`?type=`）。
- 公開用の環境（Vercel・Neon）はまだ無い。今のAPIはNestJSのサーバーとして動く。

## 制約

- 宛先が許したホストだけになるよう、登録と送信で確かめる（N-01）。
- 通知の設定の画面はv3に無い。設計書でv3の部品を使って見本を描き、設計の承認で決める。
- 手元のPCのChrome（localhost）で、許可・受け取り・押して開くまでを確かめる。iPhone・Androidの実機での確認は、結合検証の環境を作る回に回し、`docs/tests/final-acceptance.md`に行を足す。

## 対象範囲

- API: 購読の4つの操作、DBの表2つ（購読、ログアウトの停止の記録）、保存の後に送る処理と11種類の操作へのつなぎ込み、ログアウトの前に通知を止める処理、VAPIDの鍵の入れ替え、宛先の確かめ方。
- 画面: 通知の設定の画面、旅行のメニューの行、ホームの案内のカード、精算の画面で履歴の1件を目立たせる表示、ログアウトの流れの変更。
- ブラウザ: Service Worker（受け取り・表示・押したとき）、ホーム画面に追加するための設定（manifestとアイコン）。
- 試験: 単体・実DB・HTTP（通知の失敗と保存、同じ要求の再送で送らない、古い版の無効化、ログアウトとの競合、端末の数）、E2E（設定の画面の状態、ホームのカード、通知から開く画面のURL）。配信サービスへの実際の送信は、手元のChromeでの手動の確認だけ。

## 対象外

- iPhone・Androidの実機での確認（結合検証の環境を作る回）。
- 公開用の環境づくり（Vercel・Neon）と、本番のVAPIDの鍵・連絡先の設定。
- 届かなかった通知の送り直し、通知を送るためのキュー（Outbox）。
- 電波がないときのしおり（Service Workerでの画面の保存）。
- 精算の履歴の詳細の画面（行き先は精算の画面にした）。
- 通知の種類ごとのオン・オフ、旅行ごとのオン・オフ。
- アプリを開いているときに画面を自動で読み直すこと。

## 後方互換性・データ移行

- DBに表を2つ足す（migration）。今ある表は変えない。
- ログアウトの流れが変わる。APIの`POST /api/auth/sign-out`の前に、通知を止める処理が入る。購読が無い人では、今と同じ動きになる。
- 11種類の保存のAPIの応答は変えない。

## 受け入れ条件

- F-01〜F-85・N-01〜N-06・E-01〜E-12・B-01〜B-06が、試験計画の観点から辿れ、試験が通る。
- 手元のPCのChromeで、片方のユーザーで有効にし、もう片方の操作で通知が出て、押すと対象が開くことを確かめた（11種類のうち、予定・記録・精算から1つずつ以上）。
