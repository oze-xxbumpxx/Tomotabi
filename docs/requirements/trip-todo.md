## この文書の読み方

- **F-01などの番号**は機能要件、**E-01など**は異常系（うまくいかない場面）、**B-01など**は境界の番号。設計書と試験計画から「どの要件を満たすか」を指すために付けている。
- **ToDo**は、ToDoリストの一つの項目。旅先でやること（行きたい場所・食べたいもの）も、出発前の用事（予約する・両替する）も同じ一つのリストに書く。

## 背景

旅行で行きたい所ややることを、旅行ごとにToDoリストにまとめたい、とユーザーから要望があった。今のアプリが持つのは、日付の決まった予定（しおり）と、支払い・達成・予約の記録だけ。予定は日付が必須なので（`apps/api/src/infrastructure/database/schema/planning.ts:111`）、日付の決まっていない「行けたら行きたい店」や「出発前にやる用事」を書く場所が無い。

## 目的

- 二人が、旅行ごとに日付の決まっていないToDoを書き足し、済んだら完了の印を付けられる。
- ToDoの日付が決まったら、名前を打ち直さずに予定にできる。予定にしたToDoは完了になる。
- 下のタブから、旅行の中のどの画面からでも一度でリストを開ける。

## ユーザー要求（原文の要約）

「特に旅行でしたいことをToDoリストでまとめられるようにしたい」。2026-11-08に確認のページで次を決めた（理由と選ばなかった案は論点の記録）。

- 書くもの: 旅先でやることと出発前の用事を分けず、一つのリストに書く。
- 予定への移し方: 「予定にする」で、名前を入れた状態の予定の追加の画面を開く。保存したらToDoを完了にする。
- 開く場所: 下のタブに足して5つにする（推奨はしおりの画面からの入口だった）。
- 相手への知らせ: 誰が追加・完了したかを画面に出す。通知は送らない。

次の3つは推奨で仮に決めた（設計の承認までに異議がなければ決定にする）。書けるのは名前とメモ。並べ替えは無く、未完了を上・完了を下に追加した順で並べる。削除は確認のうえでできる。

## 機能要件

### リストと項目

| ID   | 要件                                                                               |
| ---- | ---------------------------------------------------------------------------------- |
| F-01 | ToDoは旅行ごとに持つ。旅行の参加者（二人）だけが見て、追加・編集・完了・削除できる |
| F-02 | ToDoは名前（必須）とメモ（任意）を持つ                                             |
| F-03 | リストは未完了を上、完了を下に分けて出す。それぞれの中は追加した順（古いものが上） |
| F-04 | 各項目に、誰が追加したかを出す。完了した項目には、誰が完了にしたかも出す           |
| F-05 | リストの画面から、名前を一行で入れてすぐ追加できる。メモは項目を開いたときに書く   |
| F-06 | 名前とメモをあとから直せる                                                         |
| F-07 | 完了の印は付け外しできる。外したら未完了に戻り、誰が完了にしたかの表示も消える     |
| F-08 | 項目を削除できる。削除の前に確かめる。削除したものは戻せない                       |

### 予定にする

| ID   | 要件                                                                                                                                                                                           |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-09 | 未完了のToDoから「予定にする」を押すと、名前とメモを入れた状態で予定の追加の画面を開く。種類・日付・時刻は予定の追加の画面で選ぶ                                                               |
| F-10 | 予定の追加の画面で保存したら、元のToDoを完了にする。完了にした人は、予定を保存した人。予定の保存と完了は、サーバーの一つの書き込みで決める。予定だけができて、ToDoが未完了のまま残ることはない |
| F-11 | 予定の追加の画面で保存せずに戻ったら、ToDoは変えない                                                                                                                                           |
| F-12 | 予定にしたToDoは、どの予定になったかを覚えておく。予定を取りやめても、ToDoは完了のまま。完了の印を外したら、予定とのつながりも消す                                                             |
| F-16 | 予定にしたToDoの行に、予定の日付（「10/13 の予定」）を出し、押すと予定の詳細を開く。予定を取りやめていたら「取りやめた予定」と出す。予定の詳細からToDoへは戻らない                             |

## 非機能要件

- 保存の確かさ: 追加・完了の付け外し・編集・削除は、今ある保存と同じく、同じ要求の再送で二重に作られない。保存できたか分からなくなったときは、同じ内容で送り直して確かめられる。
- 同時の変更: 二人が同じToDoを同時に編集したときは、今ある予定の編集と同じく、後から保存した側に「相手が先に変えた」と出す（v3の24と同じ扱い）。
- 性能: 一つの旅行のToDoは最大200件。リストは1回の読み込みで全件を出す。
- セキュリティ: 旅行の参加者でない人は、ほかの旅行のToDoを見ることも変えることもできない（今ある旅行の権限の確かめを使う）。
- 個人情報: 新しく持つのは、二人が書く名前とメモだけ。

## 正常系

1. 出発前に、本人がToDoのタブを開き「清水寺」「湯豆腐」「両替する」を追加する。リストに3件が未完了で並び、追加した人の名前が出る。
2. パートナーがToDoのタブを開くと、同じ3件が見える（通知は届かない）。
3. 本人が「両替する」に完了の印を付ける。リストの下の完了の欄に移り、完了にした人が出る。
4. 日程が決まり、パートナーが「湯豆腐」の「予定にする」を押す。予定の追加の画面に名前が入っている。種類「食べ処」と日付を選んで保存すると、しおりに予定が増え、「湯豆腐」は完了になる。
5. 「清水寺」が要らなくなり、削除を確かめて消す。

| ID   | 場面                                                                     | 振る舞い                                                                                                                                               |
| ---- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| E-01 | 名前が空、または上限を超えている                                         | 保存しない。入力欄の下に理由を出す                                                                                                                     |
| E-02 | 一つの旅行のToDoが200件ある状態で追加する                                | 追加しない。上限に達したことを出す                                                                                                                     |
| E-03 | 相手が先に同じ項目を編集した                                             | 保存しない。「相手が先に変えた」と出し、最新の内容を読み直せる                                                                                         |
| E-04 | 相手が先に削除した項目を、編集・完了・削除しようとした                   | 保存しない。項目が無くなったことを出し、リストを読み直す                                                                                               |
| E-05 | 「予定にする」で予定を保存したが、その間に相手が元の項目を削除していた   | 予定は保存したままにする。ToDoを完了にできなかったことは出さない（項目はもう無いため）                                                                 |
| E-06 | 「予定にする」で予定を保存したが、その間に相手が元の項目を完了にしていた | 予定は保存したままにする。ToDoは完了のままで、完了にした人は先に完了にした人のまま                                                                     |

| E-09 | 電波が無いときにToDoのタブを開いた                                       | 今ある画面と同じく、オフラインの表示を出す。追加する・完了にする操作は押せない見た目にする                                                             |

## 境界条件

| ID   | 条件                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------- |
| B-01 | ToDoが0件のとき、リストの代わりに「ToDoはまだありません」と足し方の一言を出す                              |
| B-02 | 名前は1〜100字（前後の空白を除いて数える）。予定の名前と同じ上限にして、予定にするときに入りきるようにする |
| B-03 | メモは0〜2000字。空はメモ無し（`null`）として持つ                                                          |
| B-04 | 一つの旅行のToDoは最大200件（完了を含む）                                                                  |
| B-05 | 全件が完了のとき、未完了の欄に「すべて済みました」を出す                                                   |
| B-06 | 旅行が終わったあとに編集できるかは、設計の工程で決める（未決事項）                                         |

## 前提

- 旅行の参加者は二人で固定（v3の画面一式の概要）。
- 予定の追加の画面（`apps/web/src/app/trips/[tripId]/plans/new`）を使う。予定の保存のAPIは、元のToDoを任意で受け取れるように広げる（F-10）。ToDoを渡さない今の使い方は変わらない。
- 保存の再送・結果不明の確かめは、今ある端末に残す仕組み（ADR-0006）に載せる。

## 制約

- v3は下のタブを4つとしている。5つにするのはユーザーの判断（2026-11-08）で、v3から外れる。タブ1つの幅が狭くなるので、名前は短くする。
- 新しい表は、今のDBの移し替え（Drizzleのマイグレーション）で足す。

## 対象範囲

- DB: ToDoの表を足す。
- API（`apps/api`）: ToDoの一覧・追加・編集・完了の付け外し・削除。予定の保存のAPIで元のToDoを受け取り、予定の保存と同じ書き込みで完了にする（F-10）。
- 契約（`packages/contracts`）: ToDoの型。
- 画面（`apps/web`）: ToDoのタブの画面、項目の詳細（メモの編集・削除・予定にする）、下のタブの5つ化、予定の追加の画面で名前を受け取る流れ。
- 試験: API・画面の単体試験と、E2Eに「追加する → 予定にする → 完了になる」の流れ。

## 対象外

- 相手への通知（F-15）。
- 並べ替え・期日・担当者・種類の分類。
- 旅行をまたいだリスト（いつか行きたい場所の一覧）。
- 予定の取りやめに合わせてToDoを未完了に戻すこと、予定の詳細から元のToDoへのリンク。
- 持ち物リスト（設計資料で別に扱う領域）。
- ホームにToDoの欄を出すこと。

## 後方互換性・データ移行

- 表を足すだけで、今ある表と列は変えない。既存の旅行は、ToDoが0件の状態で始まる。
- 下のタブの並びが変わる。今あるタブの行き先のURLは変えない。
- 予定の保存のAPIに、元のToDoを渡す任意の欄を足す。渡さない今の要求はそのまま通る。

## 受け入れ条件

- F-01〜F-16、E-01〜E-09、B-01〜B-06（B-06は設計で決めたとおり）を、API・画面の自動の試験で確かめる。
- E2Eで、二人のうち一人が追加したToDoをもう一人が見られ、「予定にする」で予定ができ、ToDoが完了になる。
- 参加者でない人が、ほかの旅行のToDoを読めず変えられないことを、APIの試験で確かめる。
- 品質コマンド（`npm run lint` / `npm run type-check` / `npm test` / `npm run build`）が通る。
- 結合検証環境で、スマートフォンの幅で5つのタブが読める大きさで並ぶことを手で確かめる。
