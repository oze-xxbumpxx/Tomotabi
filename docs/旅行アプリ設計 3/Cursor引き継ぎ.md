## 3. 確定した設計の要点

### 利用と運用

- Webアプリ。Googleログインで許可した二人だけが利用可能。旅行ごとの参加者認可もサーバーで実施する。
- 本番はVercel Hobby＋Neon Free（PostgreSQL）。月額0円、Vercelの無料URLを前提とする。無料枠不足時に無断で有料化しない。
- 初期版は国内旅行を優先し日本円のみ。外貨・為替換算・海外の時差対応は後回し。
- アプリを開いていない間もスマートフォンへ通知する。標準Web Push＋VAPID＋web-pushを詳細設計06で選定。保存後に通知し、欠落を許容する。通知失敗で支払い・精算の記録や調整を失わない。
- オフラインは保存済みしおりの閲覧のみ実装候補。主要オンライン機能の後に取り組み、負担が大きければ延期する。オフライン更新や後からの同期はしない。

### 画面と責務

- ホームを入口とし、しおり・記録・精算へ移動する構成で設計を進めている。抜粋件数などの採用した初期値は第4節を参照。
- フロントは表示・入力・遷移、バックエンドは本人確認・参加者認可・業務ルールと確定計算を担当。
- planningは旅行・予定、recordは達成・予約・支払いとその取り消し、settlementは精算と調整を所有する。既存のmemory・packingの境界も維持する。
- ホームとしおりの表示に必要な情報を結合する。ホーム独自の精算式は持たない。

### 予定と記録

- 予定名・種類・日付は必須、時刻・メモは任意。時刻未定を0時と扱わない。
- 有効な達成・予約記録は予定ごとにそれぞれ1件まで。取り消し後は現在の予定の条件を満たせば再登録できる。
- 達成できる種類は場所・食べ処・買い物。取りやめ済みの予定には達成を追加しない。
- 予約できる種類は食べ処・宿・移動。取りやめ済みでも予約記録を追加できる。
- 予定の取りやめで既存の達成・予約を自動取り消ししない。予約記録操作は実際の予約・キャンセルではない。
- 達成・予約の履歴がある予定は種類変更不可。取り消し済み履歴も含む。支払いだけが紐づく場合は変更可能。
- 記録の訂正は取り消し＋新規登録。履歴を残し、直接編集しない。

### 支払いと精算

- 支払いごとに負担割合を1％単位、合計100％で指定できる。折半・どちらか全額も簡単に選択できる入力方式。
- 各人の割合と負担額を表示。支払者以外の負担額を円未満切り捨て、支払者は総額との差額を負担する。支払いごとに確定し、精算時に再度丸めない。
- 精算は実際の受け渡し完了の記録。アプリは送金しない。どちらか一人が記録でき、承認不要。
- 残額を見るだけでは対象を固定しない。「受け渡しを確認する」で対象と金額を固定し、追加の支払いは次回へ回す。
- 対象が取り消され、受け渡し前なら再確認。元の確認金額を全額受け渡し済みなら元の内容で完了を記録し、取り消し分を次回へ調整する。
- 同じ対象の先行精算は二重登録しない。一部だけ先行精算された場合も全体を精算済みと扱わない。
- 精算自体も取り消せるが、旅行ごとに最新の有効な1件のみ。古い精算の個別訂正は運用後に検討。履歴は残し、実際の返金はしない。
- 支払いと誤った精算の両方を取り消したら、支払いを復活させず、その精算に対する未処理の逆向き調整も残さない。
- 金額の一致だけでなく、対象・調整の重複防止と未処理対象を検証する。

### 通知

予定の追加・取りやめ・日の移動、達成・予約・支払いの追加と取り消し、精算の完了と取り消しが通知対象。通常編集は通知しない。記録タイムラインは予定の全編集履歴ではなく、予定の現在状態はしおりで確認する。

## 5. 詳細設計で必ず解決すること

1. 固定した精算確認を外部送金アプリへの移動・再読み込み後にも再開する方法。期限だけで受け渡し済みの記録を不能にしない。
2. 同時精算、最新の精算の取り消し、支払い取り消しと精算完了の競合を安全に成立させるDB制約とトランザクション。
3. 取り消した精算の対象の再精算、調整の無効化・再利用、重複禁止条件。全履歴で支払いIDを一度しか使えない設計にはしない。
4. API入力の検証、旅行・予定・記録の所属照合、許可アカウントと旅行参加者の認可。
5. 種類変更と達成・予約の同時登録で、不適切な種類に記録が付かない保証。
6. Vercelの実行寿命内での通知送信、Neonへの接続管理。無期限のバックグラウンド処理や常時ポーリングを前提にしない。
7. 無料枠の現行条件の再確認、ログ・使用量確認、バックアップ・復元、デプロイを戻す手順。
8. 既存の限定的な競合許容（予定取りやめと達成照会の競合）を、精算の二重計上許容へ拡大しない。

## 6. Cursorでの進め方

1. 参照資料を読み、合意・提案・詳細設計事項を整理する。第4節は採用済みとして扱い、既存資料に残る旧提案と取り違えない。
2. 詳細設計を作る：API、データモデル、依存関係、認証・認可、精算確認とトランザクション、テスト方針、運用構成。
3. Googleログインと二人限定の認可、旅行選択、予定の縦につながる最小機能を作る。
4. 達成・予約・支払いの記録と訂正を実装する。
5. 精算の対象確認・完了・取り消し・調整を実装し、同時操作を含む受け入れ条件を検証する。
6. ホームの情報集約、通知、スマートフォンでの操作を仕上げる。
7. 無料構成で公開・運用確認。オフラインしおりは負担を見て後続対応する。

これは今回整理した4画面の実装順序。memory・packingなど他の領域を勝手に廃止・実装済み扱いしない。今回の引き継ぎではそれらの画面詳細を定義していない。
