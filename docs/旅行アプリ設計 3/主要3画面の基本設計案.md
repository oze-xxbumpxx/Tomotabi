## 1. 共通の構成（提案）

旅行を選択した後、スマートフォンの下部に「ホーム／しおり／記録／精算」の4タブを置く。最初にホームを表示する。タブを移動しても選択中の旅行は維持する。旅行の切り替えは画面上部から行う。

| 共通情報・操作 | 内容 |
|---|---|
| 旅行の識別 | 旅行名、旅行期間。旅行名は表示に必要な追加項目として提案 |
| 参加者の識別 | 自分と相手の表示名。支払った人と入力した人を区別する |
| 更新 | 画面を開いた時・操作成功後に最新情報を取得。手動更新も可能にする |
| 入力中 | 保存中を表示し、同じ操作の連打を防ぐ。入力エラー時は入力を維持する |
| 保存の結果が不明 | 通信切断等では成功・失敗を断定しない。最新状態を確認する導線を出す。サーバー側の重複防止は詳細設計で扱う |
| 同時編集 | 相手の更新で競合した場合は、再取得して内容を確認する。上書きを強行しない |
| 通知 | 保存成功と通知成功は分離。通知が届かなくてもデータは残る |
| オフライン | 保存済みしおりの閲覧のみ実装候補。記録・精算の更新操作は不可。古い残額で精算できないようにする |

確認ダイアログは、予定の取りやめ・記録の取り消し・精算の完了記録・精算の取り消しに絞る。通常の追加・編集保存で相手の承認は求めない。操作結果は画面内で示し、編集のたびに相手への通知は送らない。

## 2. しおり：今日の予定と準備状況を確認する

### 表示

| 配置 | 必要な情報 |
|---|---|
| 上部 | 旅行名、日付切り替え、「今日」への移動 |
| 日ごとの一覧 | 予定名、種類、時刻（任意の提案）、メモの抜粋 |
| 予定の状態 | 取りやめ、達成済み、予約記録あり。それぞれ独立して表示する |
| 予定詳細 | メモ全文、その予定に関連する記録への導線 |
| 下部等 | 「予定を追加」 |
| 保存済み情報の閲覧時 | オフラインであること、最終取得日時 |

予定名・種類・日付を必須、時刻・メモを任意とする（2026-09-06合意済み）。既存資料の日単位の管理に、予定名と任意時刻を明示的に追加する。時刻順、時刻未定は末尾、同時刻は安定した順序とする案。ドラッグによる並べ替え、移動時間の自動計算、地図連携はこの案に含めない。

### 操作

| 操作 | 入力・確認 | 結果・制約 |
|---|---|---|
| 予定追加 | 名前、種類、日付、任意の時刻・メモ | 選択日に予定を追加。相手に通知 |
| 予定編集 | 名前・時刻・メモを編集する案 | 通常の編集では通知しない。種類は達成・予約の履歴がない場合のみ変更可能。支払いだけの場合は変更可能（2026-09-06合意済み） |
| 日を移動 | 移動先の日付 | 旅行期間内へ移動。相手に通知 |
| 予定を取りやめ | 対象の予定名を確認 | 予定は残し取りやめ表示。達成や予約を自動で取り消さない。相手に通知 |
| 達成を記録 | 対象の予定を確認 | 場所・食べ処・買い物が対象。取りやめ済みは不可 |
| 予約済みを記録 | 対象の予定を確認 | 食べ処・宿・移動が対象。取りやめ済みでも可能。外部の予約処理はしない |
| 支払いを記録 | 支払いフォームを開く | 予定との関連を初期設定する。入力項目は記録画面と共通 |
| 関連記録を見る | 対象の予定で記録を絞り込む | 記録タイムラインへ移動 |

取りやめた予定は初期状態では一覧内に残して薄く表示する案。達成済みの予定を後から取りやめた場合は「取りやめ」「達成済み」を併記する。予約記録がある予定を取りやめる確認には「実際の予約はキャンセルされません」と表示する。

同一予定への有効な達成記録・予約記録はそれぞれ1件までとする（2026-09-06合意済み）。取り消し後は現在の予定が記録の条件を満たす場合に再登録できる。履歴は残す。有効な記録がある間は追加ボタンを状態表示に置き換える案。二人の同時登録でもサーバー側で重複を防ぐ。

空の日は「この日の予定はまだありません」と追加ボタンを表示。取得失敗時は再試行、オフラインで未保存の日は取得が必要な旨を表示する。

## 3. 記録タイムライン：起きたことと訂正履歴を確認する

### 表示

| 配置 | 必要な情報 |
|---|---|
| 上部 | 種類の絞り込み：すべて／達成／予約／支払い。予定から遷移した場合は予定の絞り込みを表示・解除可能にする |
| 一覧 | 新しい記録から順に、記録種別、登録日時、入力した人、関連する予定名、内容、取り消し状態 |
| 支払いカード | 金額、支払った人、負担区分、任意の用途名。精算との関係は詳細から確認 |
| 取り消し履歴 | 何を誰がいつ取り消したか。元の記録へ移動できるようにする |
| 追加操作 | 「支払いを記録」。達成・予約は対象の予定を選んでから記録する |

初期版では登録日時の順に並べる案。実際に起きた日時の遡及入力・並べ替えは別要件とし、登録日時を出来事の発生日時だと誤表示しない。

### 支払いフォーム

| 項目 | 入力案 |
|---|---|
| 金額 | 必須。初期版は日本円のみで進める（2026-09-06）。入力は円単位の正の整数を提案 |
| 支払った人 | 必須。自分／相手。初期値は自分だが変更可能とする案 |
| 負担の分け方 | 必須。「二人で半分ずつ」「支払った人が全額負担」「もう一人が全額負担」「割合を指定」から選択する案。割合指定時は二人の割合と負担額を表示 |
| 関連する予定 | 任意。しおりから開いた場合は選択済み。取りやめた予定も関連付け可能 |
| 用途名 | 任意の追加項目として提案。例：昼食、電車代。予定に紐づかない支払いも識別できるようにする |

負担区分の補足には実名の表示名を使う。例えば、相手が支払い「もう一人が全額負担」を選んだ場合、「あなたが全額負担」と表示し、入力者基準との混同を避ける。

### 操作と訂正

- 支払い・達成・予約の記録は直接編集しない。誤りは取り消し、新しい記録を追加する。取り消した履歴も残す。
- 取り消し操作では対象を確認し、成功後に相手へ通知する。既に取り消した記録に同じ操作はできない。
- 予約記録の取り消しは実際の予約キャンセルではない。
- 精算済みの支払いの取り消しは過去の精算を書き換えず、次の精算への調整として扱う既存方針を表示文言にも反映する。
- 精算の完了・取り消し履歴は精算画面を正本とする案。記録タイムラインへ重複掲載する機能は初期版に含めない。
- 予定の通常編集・追加・日の移動は、この記録タイムラインの対象ではない。しおりで現在の予定を確認する。
- 記録がなければ空状態と追加導線、取得失敗時は再試行を表示。過去分は「もっと見る」で追加取得する案。

## 4. 精算：受け渡す金額を確認し、完了した事実を残す

### 表示

| 配置 | 必要な情報 |
|---|---|
| 最上部 | 「相手からあなたへ3,000円」のように、渡す人・受け取る人・金額を明記 |
| 内訳 | 未精算の支払い、支払った人、負担区分、計算への寄与。過去の取り消しによる調整は通常の支払いと分ける |
| 完了操作 | 「受け渡しを確認する」→対象と金額を確認→「受け渡し完了を記録」 |
| 精算履歴 | 記録日時、操作した人、受け渡し方向・金額、対象明細、完了／取り消しの状態 |
| 履歴の詳細 | 元の対象明細と、取り消しがある場合の操作者・日時。取り消し操作への導線 |

架空の表示例：あなたが二人分8,000円、相手が二人分2,000円を支払った場合、相手からあなたへ3,000円。総支出10,000円と受け渡し額3,000円を混同しない表示にする。

### 状態による操作

| 状態 | 振る舞い |
|---|---|
| 精算対象なし | 「精算する支払いはありません」。完了操作なし |
| 対象はあるが差額0円 | 「受け渡しは不要です」。対象を確認し「受け渡し不要として精算を記録」とする案。対象なしとは区別 |
| 受け渡しが必要 | 金額・方向・対象を確認し、アプリ外で受け渡した後に完了記録 |
| 精算完了 | 対象を次回の通常計算から除外し、履歴に残す。どちらか一人の操作で確定し、相手に通知 |
| 誤った完了記録 | 履歴から取り消し。元の履歴と取り消しの事実を残し、相手に通知。返金操作ではない |
| 通信不能・残額取得失敗 | 現在の精算額として断定しない。完了・取り消しを実行させず再取得へ誘導 |

### 確認中に支払いが変わる場合（追加分を次回へ回す方針は2026-09-06合意）

確認画面を開いた時点の対象と金額を固定し、「この明細について受け渡し済み」と記録する。確認後に追加された支払いは次回分へ回す（合意済み）。例えば3,000円の確認後に新しい支払いが増えても、完了操作で勝手に3,500円分を締めない。

競合時の方針は合意済み。対象支払いが取り消された場合、受け渡し前なら最新内訳を再確認する。元の確認金額を全額受け渡し済みなら、変更を明示して元の内容で完了を記録し、取り消し分を次回の調整とする。相手が同じ対象を精算済みなら既存記録を表示して二重登録しない。具体例は「受け渡し後の支払い訂正案.md」を参照。

対象固定の識別・有効期限・同時実行の排他・再送時の重複防止はCursorで設計するが、「何を締めるか」はこの会話で先に決める。

### 精算の取り消し範囲（2026-09-06合意）

初期版では「現在有効な精算のうち最新の1件のみ取り消せる」とする。古い精算の個別訂正は運用後に必要性を検討する。古い精算を取り消す場合は、新しいものから順に取り消す。後続の精算を自動で取り消さない。

例：1回目、2回目と精算した状態で1回目を取り消そうとした場合、2回目の確認・取り消しが先に必要であると表示する。取り消しは実際の受け渡しを逆に動かさないため、この制限が二人の訂正作業に適切か確認が必要。

対象の支払いが取り消されている場合に元の支払いを復活させないこと、対象だった調整分を二重に戻さないこと、取り消した精算の対象を再度精算できることを守る。最新のみの制限を採用しても、これらの計算ルールは別途確定する必要がある。

## 5. 読み取りAPIに求める情報

URLと返却形式を確定する段階ではなく、画面が必要とする情報を整理する。

| 読み取り | 必要な情報 |
|---|---|
| しおり | 旅行の識別・期間、選択日、予定ID・名前・種類・日付・任意時刻・メモ・取りやめ状態、達成・予約の有効な記録、取得日時、編集競合を検知する情報 |
| 記録一覧 | 記録ID・種類・登録日時・操作者、関連予定の識別と表示名、支払者・金額・負担区分・任意用途名、取り消しと元記録の関係、続きの取得情報 |
| 現在の精算内容 | 受け渡す人・受け取る人・金額、対象支払いと調整の明細、対象が空かどうか、確認対象を識別する情報 |
| 精算履歴 | 精算ID・登録日時・操作者・金額・方向、元の対象明細、取り消しの事実、取り消し可能かと不可の理由 |

計算結果はサーバーを正とする。精算計算には支払者と金額だけでなく、各参加者の負担割合と確定した負担額が必要。固定の3区分だけでは可変割合を表現できないため、読み取り情報も拡張する。端数処理、既精算の支払い取り消し、精算自体の取り消しを組み合わせた例を先に整理し、Cursorへの受け入れ条件とする。

各取得・更新はサーバーで旅行の参加者を確認する。予定と記録が指定旅行に属することも検証する。画面でボタンを隠すだけで権限や業務ルールを守ったことにしない。

## 7. ホーム追加案（2026-09-06）

ユーザー提案の「その日の予定等を一目で確認する入口」を具体化する。下記の配置・件数・操作は未合意の提案。しおり・記録・精算の詳細機能はそれぞれの画面に維持する。

### 表示の優先順位

| 順位 | 表示内容 | 操作 |
|---|---|---|
| 1 | 選択中の旅行名・日付・旅行何日目か | 旅行を切り替える |
| 2 | 今日の予定：予定名、任意時刻、達成・予約の状態。最大3件を表示し、残りの件数を示す | 予定詳細、今日のしおりを開く |
| 3 | 「支払いを記録」の目立つボタン | 既存の支払いフォームを開く。予定の関連付けは任意 |
| 4 | 現在の精算額と受け渡し方向 | 精算画面で内訳を確認する |
| 5 | 最近の記録3件：種類・要約・登録者・登録日時 | 記録タイムラインを開く |

最大3件などは画面の情報量を抑えるための初期案。取りやめた予定は今日の予定の抜粋から除外し、しおりで確認する。今日の残りの予定が分かるよう未達成を優先するが、全種類が達成可能ではないため、時刻だけで自動的に達成扱いにはしない。

精算は「今の未精算分」の要約を表示する。確認中の固定した精算額とは別の値であり、ホームの金額を見ただけでは対象を固定しない。完了記録は精算画面で対象を確認してから行う。

### 旅行の状況に応じた表示

| 状況 | 表示案 |
|---|---|
| 旅行中 | 今日の予定を最上部に表示 |
| 旅行開始前 | 出発日と初日の予定を表示。「今日の予定」とは表記しない |
| 旅行終了後 | 終了した旅行であること、現在の未精算分、最近の記録を表示 |
| 今日の予定なし | 「今日の予定はありません」としおりへの導線 |
| 旅行が未作成 | 旅行作成への導線 |

選択中の旅行は維持する。初回など未選択のときは旅行一覧で選ぶ案とし、旅行の自動切り替えは行わない。日付の判定は初期版で日本時間を使う案。海外旅行向けの時差対応は将来候補とし、初期版には含めない（2026-09-06）。

### データ取得と失敗時

- しおり、現在の精算内容、記録一覧と同じ業務データを参照し、ホーム専用の計算ルールは作らない。
- ホーム向けに必要なのは、旅行の識別・期間、当日（開始前なら初日）の予定の抜粋と総件数、現在の精算額・方向・対象の有無、最近の記録。
- 一部の取得が失敗しても他の取得できた部分は表示する。精算額の取得失敗を0円として表示しない。
- オフラインのホーム全体の保存は今回追加しない。保存済みしおりの閲覧を実装する場合は、そこへ移動できる導線を確保する。
- APIをホーム専用に集約するか既存の読み取りAPIを組み合わせるかはCursorで決める。常時ポーリングは前提にしない。

## 8. 精算取り消し範囲のレビュー案（2026-09-06）

状態：操作範囲は2026-09-06合意済み。古い精算の個別訂正は運用後に検討する。以下の具体的な画面文言は提案。

### 提案する操作ルール

- 旅行ごとに、取り消されていない精算のうち最新の1件を取り消し可能とする。
- どちらの参加者も操作でき、相手の承認は不要。相手への通知と履歴の追記は既存の合意どおり。
- 古い精算は詳細を閲覧できるが、取り消し操作では「後の精算があるため、この精算は取り消せません」と理由を表示する。
- 後の精算を自動で取り消さない。後の精算も誤りである場合は、新しい順に各対象を確認して取り消す。
- 後の精算が実際の受け渡しを正しく記録している場合は、古い精算を取り消すためだけにその記録を取り消すよう誘導しない。この場合の訂正は、この制限だけでは完結しない残論点として扱う。

### 例と期待する表示

| 状況 | 操作・結果 |
|---|---|
| 1回目の精算を誤って完了。後の精算なし | 1回目を取り消せる。元の履歴は「取り消し済み」と分かる形で残す |
| 1回目と2回目が有効 | 2回目のみ取り消せる。1回目には操作不可の理由を表示 |
| 2回目を取り消した | 1回目が最新の有効な精算となり、取り消し可能になる |
| 1回目は誤りだが2回目は正しい受け渡しの記録 | 1回目の直接取り消しは不可。このケースにもアプリ内で対応する必要があれば、任意の精算の訂正方式を別途設計する |
| 二人が同時に同じ精算を取り消した | 取り消しは1回だけ成立。後の操作には既に取り消し済みの最新状態を表示 |

取り消し確認には、対象の日時、金額と方向、対象明細、および「受け渡しの完了記録を取り消します。返金は行われません」を表示する。

取り消した精算の対象は、支払い自体の現在の状態や他の有効な精算を踏まえて再計算する。金額を無条件に未精算額へ足す処理にはしない。二重計上防止・調整分・端数・実際に渡した金額との整合性は、この操作範囲を決めた後に具体例で確認する。

### 判断結果

二人運用では誤りのリスクが低いと判断し、最新の有効な精算のみ取り消せる範囲で開始する。後の正しい精算を維持しながら古い誤りを訂正する機能は、運用後に必要性を検討する。


## 9. 国内旅行を優先した入力範囲（2026-09-06）

国内旅行を優先し、日本円のみの初期案で進める。海外旅行向けの外貨・為替換算・時差対応は将来検討とする。

- 金額欄には「円」を明示し、通貨選択は設けない。
- 支払いの入力は正の整数とする案。取り消しの調整は計算側が扱い、負の支払い入力で代用しない。
- 端数処理は第10節の合意に従い、支払いごとに確定する。
- 予定は予定名・種類・日付を必須、時刻・メモを任意とする（2026-09-06合意済み）。未定の時刻を0時として登録しない。
- 海外対応を追加するときは、記録通貨、精算通貨、換算時点、為替レート、旅行先の日付・時刻を改めて設計する。初期版で先行実装しない。


## 10. 可変の負担割合（2026-09-06）

ユーザーから割合が変動する可能性への対応要望あり。支払いごとに割合を指定できる設計へ見直す。以下の入力方式・1％単位の割合指定・支払いごとの端数処理は合意済み（2026-09-06）。

### 入力と表示

- 既存の折半・どちらかが全額という選択肢に「割合を指定」を加える。
- 二人の表示名と割合を並べ、一方を入力するともう一方は100％から差し引いて表示する。初期版は0〜100％の1％単位とする。
- 保存前に二人それぞれの負担額を円で表示する。支払った人を変更しても、各人に指定した割合は入れ替えない。
- 割合は支払い単位で保存し、旅行全体の設定変更によって過去の支払いの割合を変更しない。共通の初期割合設定は今回の要望から自動的に追加しない。
- 記録詳細と精算明細にも、二人の割合と負担額を表示する。

### 計算例

10,000円、あなた70％・相手30％の場合：

| 支払った人 | あなたの負担 | 相手の負担 | この支払いから生じる受け渡し |
|---|---|---|---|
| あなた | 7,000円 | 3,000円 | 相手からあなたへ3,000円 |
| 相手 | 7,000円 | 3,000円 | あなたから相手へ7,000円 |

精算では、このような支払いごとの受け渡しを相殺し、過去の取り消しによる調整を加える。折半専用の計算式は使わない。

### 端数処理の確定と変更点

支払った人以外の負担額を円未満切り捨てとし、支払った人の負担額を支払い総額との差額とする。二人の負担額の合計は必ず支払い総額に一致する。

例：あなたが1,001円を支払い、二人50％ずつなら、あなた501円・相手500円。あなた30％・相手70％なら、あなた301円・相手700円。

これは既存の「精算ごとにまとめて端数処理する」案を置き換える合意。複数の奇数額の支払いをまとめた結果が従来案と異なる場合がある。各支払いの負担額を確定して保持し、精算時に再度丸めない。既精算支払いの取り消しによる調整では元の確定負担額に基づく寄与を逆向きに扱い、新しい割合や端数規則で計算し直さない。

割合の精度・端数規則は上記で確定し、数値の保存形式とAPI契約はCursorに引き継ぐ。精算自体の取り消しと組み合わせた二重計上防止は引き続き別途確認する。


## 11. 精算確認中の競合時の表示（2026-09-06）

状態：基本動作は合意済み。下記の画面文言は提案。

| 検知した状態 | 表示・操作 |
|---|---|
| 新しい支払いが追加された | 確認中の金額・対象は変えず、新しい支払いを次回へ回す |
| 確認対象の支払いが取り消された | 変更を表示。受け渡し前なら最新内訳を再確認。元の確認金額を受け渡し済みなら元の内容で完了を記録し、差額を次回へ回す |
