# 画面とバックエンドの責務設計案

> 2026-09-07更新：採用状況は「Cursor引き継ぎ.md」第4節と「設計方針の合意事項.md」の最新決定を優先する。本書に残る「提案」「未合意」は作成時点の表記を含む。採用対象外の案まで合意済みとは扱わない。

作成日：2026-09-06
状態：2026-09-06、画面とバックエンドの役割分担・残額閲覧と対象確認の分離を合意済み。具体的な実装方式と第6節の残る判断は未確定。既存の境界と合意した業務ルールを画面へ対応付ける。Next.js・NestJSを含む技術案全体の一括採用を意味しない。URL・JSON形式・DB構造・クラス設計はCursor主体。

## 1. 責務の境界

| 領域 | 担当 | 担当させないこと |
|---|---|---|
| フロントエンド | 表示、入力、画面遷移、保存結果の表示、再取得 | 確定精算額や参加権限の独自決定 |
| planning | 旅行と予定、参加者、予定の種類・日付・取りやめ状態 | 支払い・精算履歴の所有 |
| record | 達成・予約・支払いとそれらの取り消し、支払いごとの確定負担額 | 精算完了の所有、予定の自動取りやめ |
| settlement | 精算の対象確認、完了・取り消し、現在の残額と調整 | 元の支払い記録の書き換え |
| 表示用の組み立て | ホームやしおりに必要な各領域の情報の結合 | 独自の精算式や業務データの正本の所有 |

表示用の組み立てはアプリケーション層の役割として設ける案。第6の業務領域や独立サービスは追加しない。memory・packingの既存境界も維持するが、今回の4画面では詳細化しない。

画面上で割合から負担額をプレビューしても、保存時はサーバーで検証・確定する。精算の方向・金額・対象はサーバーの結果を表示する。

## 2. 画面が必要とする読み取り

| 画面 | 必要な情報 | 情報の正本 |
|---|---|---|
| ホーム | 旅行名・期間、当日の予定の抜粋、最近の記録、現在の残額と方向 | planning＋record＋settlement |
| しおり | 選択日の予定と、各予定の達成・予約の有効状態 | planning＋record |
| 記録 | 種類・日時・操作者・取り消しとの対応、支払者・割合・確定負担額、関連予定の表示名 | record＋planning |
| 精算 | 未処理の支払いと調整、受け渡し方向・金額、固定した確認内容、完了・取り消し履歴 | settlement（支払い情報はrecordから照会） |

記録は支払いを登録した人と支払った人を区別する。予定名は表示のために照会する。過去時点の予定名を保存するかは未確定であり、現在の予定名を過去の名称として表記しない。

各画面で同じ情報を使うときは同じ計算ルールとデータを参照する。ホームの取得を1APIにまとめるか複数APIで取得するかは、実装時の詳細設計で決める。

## 3. 書き込みの担当

| 操作 | 担当 | 必須の検証 |
|---|---|---|
| 予定追加・編集・日の移動・取りやめ | planning | 参加権限、必須項目、期間、同時編集 |
| 達成・予約の追加 | record | 対象予定と旅行の一致、種類・取りやめ状態、有効記録の重複防止 |
| 支払い追加 | record | 参加権限、金額、参加者別の割合、確定負担額、関連予定と旅行の一致 |
| 記録の取り消し | record | 対象記録、参加権限、既存の取り消し、履歴の保持 |
| 精算対象の確認 | settlement | 最新情報、対象・方向・金額、確認内容の識別と保持 |
| 精算完了 | settlement | 元の確認内容、重複対象、受け渡し後の支払い取り消しの例外、必要な調整の整合性 |
| 精算取り消し | settlement | 最新の有効な精算か、二重取り消しの防止、対象・調整の再計算 |

支払いを取り消しても精算の完了記録を書き換えない。settlementはrecordの最新状態と自身の履歴を用いて調整を判定する。通知欠落によって調整が欠落する構成にしない。

## 4. 精算確認は通常の閲覧と分ける

ホームや精算画面で現在の残額を見るだけでは精算対象を固定しない。「受け渡しを確認する」を明示的に実行して初めて、サーバーが対象と金額を固定する。

これは外部サービスから戻った後も元の確認内容を参照するための区別。現在の残額取得と確認内容の作成を同じ読み取りとして曖昧にしない。確認を作っただけでは受け渡し済み・精算済みにしない。

確認が取り消し済み支払いを含む場合でも、元の確認金額を全額受け渡し済みなら完了を記録し差額を次回へ回す合意に従う。確認の作成自体は相手への通知対象に追加しない。

## 5. Cursorへ引き継ぐ詳細設計

- 各読み取り・操作のURL、返却項目、エラー、認証・認可契約。
- 固定した精算確認の保存・識別・再開・期限の扱い。受け渡し後に期限だけで元の金額を記録できなくしない。
- 対象の重複防止、同時実行、再送、最新精算の取り消し制限をサーバー側で保証する方法。
- 支払い・割合・確定負担額・精算・調整・取り消し履歴のDB構造。
- 表示更新と競合時の再確認。通知の成否と保存結果の分離。
- ORM、認証ライブラリ、テスト、監視・ログの具体的な選択。Vercel Hobby＋Neon Freeの月額0円の制約を維持する。

## 6. 基本設計で残る判断

- 予定の種類変更は第7節で合意済み。制約の同時実行時の保証をCursorへ引き継ぐ。
- 支払いの任意用途名、支払者の初期値など未合意の入力補助。
- ホームの抜粋件数・並び順、確認画面の再開導線など未確定の表示案。
- Next.js・NestJSを含む技術構成の正式な採用確認。既存の提案と合意済み事項を区別する。

これらを含め、残る基本設計案をまとめてレビューし、確定事項・未決事項・受け入れ条件を一式でCursorへ渡す。


## 7. 予定の種類の変更（2026-09-06合意済み）

- 達成・予約を一度も記録していない予定は、種類を変更できる。
- 達成・予約の履歴がある予定は、取り消し済みの記録だけでも種類を変更不可とする。記録時の種類と現在の種類を別々に管理する複雑さを初期版に持ち込まないため。
- 関連する支払いだけがある場合は、種類変更を許可する。支払いには予定の種類による制限がないため。
- 変更不可の場合、正しい種類の予定を新しく作成し、誤った予定を取りやめる。既存記録・支払いを新しい予定へ自動で移さない。予約記録があれば実際の予約はキャンセルされないことを示す。
- 名前・時刻・メモの通常編集は、種類変更の制限とは分ける。
- 種類の変更だけでは相手へ通知しない。通常編集では通知しない合意に従う。
- 種類変更と達成・予約の登録が同時に起きても、種類と記録の制約が食い違わないようサーバー側で保証する。方法はCursorで詳細設計する。

例：「食べ処」へ予約記録を追加した後に「買い物」へ変える操作を防ぎ、予約できない種類に予約記録が紐づく状態を作らない。
