## 2026-09-05：取りやめ済みの予定への予約記録

状態：合意済み
関連：ADR-002 の「未決」を解消する決定。

### 方針

- 取りやめ済みの予定への予約済みの記録を許可する。
- 予定の存在と予約できる種別（食べ処・宿・移動）であることは検証する。
- 予定の取りやめによって予約記録を自動で取り消さない。取りやめ状態と予約済みの記録は併存できる。
- 予約記録の追加・取り消しは、実際の予約や予約キャンセルを実行する操作ではない。

### 判断理由

予約済みの記録は、予約した事実を残す操作である。予約後に予定を取りやめ、その後で予約した事実を入力する場合も許容する。

### 既存方針との関係

取りやめ済みの予定への達成を拒否する既存方針は維持する。達成には既存の業務上の制約を適用する一方、予約は取りやめ後にも予約した事実を記録できるようにする。

### 詳細設計・実装への受け入れ条件

- 取りやめ済みでも予約可能な種別の予定には予約記録を追加できる。
- 予約できない種別や存在しない予定への予約記録は拒否する。
- 参加者の認可は既存の方針に従う。
- 予定を取りやめても既存の予約記録は残る。
- 記録の追加・取り消しによって外部の予約処理は実行されない。

## 2026-09-05：通知対象

状態：合意済み
関連：ADR-002 決定 1 の通知対象を確認。

### 方針

- 予定の追加・取りやめ・日の移動を通知する。
- 達成・予約済み・支払いの記録の追加と取り消しを通知する。
- 精算の実行を通知する。
- 予定のメモ編集などの編集操作では通知しない。日の移動は明示した通知対象として扱う。
- 記録には更新操作がないため、修正は既存方針どおり取り消し＋入れ直しとなり、それぞれ通知対象に含む。

### 判断理由

細かな編集のたびに通知すると煩わしいため。通知対象は上記の操作に限定する。

## 2026-09-05：精算の意味

状態：合意済み
関連：ADR-001 決定 6、ADR-002 決定 5 の意味を明確化。

### 方針

- 精算は、その時点で溜まっている受け渡しが完了したことを記録し、対象を締める操作とする。
- 現在の差額を表示・確認するだけでは精算済みにしない。
- 実際のお金の受け渡しは現金や送金サービスなどアプリ外で行い、アプリは差額の計算と完了の記録を担当する。
- 締めた対象は次回の通常の精算対象から除外する。精算後に支払いが取り消された場合の巻き戻しは、ADR-002 の既存方針に従う。

### 詳細設計への引き継ぎ

- 精算は今後払う金額の確定や請求の作成ではなく、受け渡しの完了記録であることを画面上でも明確にする。
- 金額確認から完了記録までの間に支払いの追加・取り消しが発生した場合、実際に受け渡した金額と締める対象の対応をどう守るかは、今後方針を確認する。

## 2026-09-05：精算を確定できる人

状態：合意済み

### 方針

- 旅行の参加者のどちらか一人が操作すれば、精算の完了記録を確定できる。
- 相手の承認は求めない。
- 精算の実行を相手に通知する。通知の受信や確認は精算確定の条件にしない。

### 判断理由

二人で使い、実際のお金の受け渡しを終えてから記録するため、アプリ内で追加の承認手続きは設けない。

## 2026-09-05：精算自体の取り消し

状態：合意済み
関連：ADR-002 決定 5 の「精算自体の取り消しは持たない」を変更する。

### 方針

- 誤った完了記録を訂正できるよう、精算自体の取り消しを認める。
- 元の精算履歴は残し、取り消した事実を追記する。元の履歴の更新・削除による訂正は行わない。
- 精算の取り消しは、実際のお金の返金を実行する操作ではない。
- 元の支払いが正しい場合、精算の誤りを訂正するためにその支払いを取り消す必要はない。

### 判断理由

受け渡しが終わっていないのに精算済みにするなど、支払い記録の誤りとは別に精算の完了記録を誤る場合がある。自然な訂正操作として精算自体の取り消しを認める。

### ADR・引き継ぎ資料で必要な変更（原本未反映）

- ADR-002 決定 5：精算の取り消しを認め、履歴を追記で保持することを明記する。
- ADR-002「判断を変えるべき条件」：精算の取り消しを将来の条件付き検討としている項目を見直す。
- ADR-002 付録 A・B：精算を取り消すユースケースと API を追加する。具体的な契約は詳細設計で定義する。
- ADR-002 決定 1：精算の取り消しを相手への通知対象に追加する（合意済み）。
- HANDOFF：精算自体の取り消しなしという要約を更新する。追記のみという方針は維持する。

### 設計上の残論点

- 取り消し可能な精算の範囲。操作できる人と相手への通知は下記で合意済み。
- 精算の取り消し後に、対象の支払いと巻き戻し分を次の精算へどう戻すか。
- 二重計上や巻き戻し漏れを防ぎつつ、取り消された精算に含まれていた支払いを再精算できるよう、既存の ID 重複禁止の不変条件を見直す必要がある。
- 後続の精算や支払いの取り消しが既に存在する場合の扱い。

## 2026-09-05：通知の欠落と開発目的

状態：合意済み
関連：ADR-002 決定 8 を確認。

### 方針

- 本アプリは二人の個人利用とポートフォリオを目的とする。
- データの保存を完了してから通知する。
- 通知の欠落は許容する。通知が届かなくても保存済みのデータは残り、アプリで最新の状態・履歴を確認できることを前提とする。
- 初期段階では通知の到達保証や、そのための再送の仕組みを設けない。ADR-002 のコミット後のプロセス内イベント発行と Outbox 不採用の方針を維持する。
- 精算の取り消しもアプリ内で確認できる履歴に含める。

### 判断理由

個人利用とポートフォリオの目的に対して、通知の欠落を許容できる範囲と判断した。通知の到達保証による複雑さを初期段階で持ち込まない。

### 詳細設計への引き継ぎ

- 通知の欠落の許容は、支払い・精算データの欠落や二重計上を許容する意味ではない。
- 通知配信と業務データの保存結果を区別し、通知失敗によって完了済みの業務操作を失敗したように扱わない。

## 2026-09-05：オフラインでのしおり閲覧

状態：ユーザーは実現可能なら希望。負担が大きい場合は必須としない。以下を初期版の実装候補の範囲とする。

### 範囲

- 一度オンラインで取得・保存したしおりを、圏外でも閲覧できるようにする。
- 保存済みの予定一覧・メモ・達成や予約済みの表示を対象とする。未取得の日程やデータまで閲覧できるとは保証しない。
- 最終取得日時と、保存済みの情報を表示していることを画面に示す。
- オフラインでの追加・編集・取り消し・精算や、それらの後からの同期は初期版の対象に含めない。
- 地図や外部ページのオフライン利用は含めない。
- 通信が戻った後、アプリの表示・再取得時にサーバーの最新情報へ更新する。

### 実現性と優先順位

- Service Worker とブラウザ内の保存機能による閲覧用キャッシュで実現可能。競合解決を伴うオフライン更新を含めないため、範囲を限定できると判断する。実装工数は未見積もり。
- 主要なオンライン機能を先に完成させ、その後でこの閲覧機能を実装・実機検証する。負担が大きい場合は初期リリースから延期できる。
- ブラウザに保存したデータは利用者による削除やストレージ都合で失われる場合がある。未保存・消失時は、通信して再取得する必要があることを案内する。

### Cursor への引き継ぎ

- しおりのデータだけでなく、オフラインで表示するために必要な画面のファイルも保存する。
- 保存方法と更新・破棄方法は詳細設計で決める。利用者別のデータ分離とログアウト時の扱いを定義する。
- iPhone と Android で、一度取得後にアプリを閉じて圏外で再度開き、保存済みのしおりが表示できることを検証する。
- 未保存の場合の案内、最終取得日時、オンライン復帰後の再取得、オフライン中に更新操作ができないことを確認する。
