# 詳細設計01：支払い・精算・訂正

作成日：2026-09-07
状態：実装前の詳細設計案。合意済み業務ルールに対する実現方式を定義する。必要な制約とトランザクションを定義する。後続の「02_ORMとDB_API.md」でDrizzle＋pgを選定し、SQLとOpenAPIを追加した。

設計はこの会話で継続し、実装は引き続きCursorへ渡す。添付の基本設計を正本とし、設計スキル内の別プロジェクト向けGraphQL・Sequelize指定は採用しない。この作業フォルダに既存のAGENTS.md・DB設計・API仕様・コード規約は見つかっていない。

## 1. 対象と設計判断

今回は支払いの保存、精算確認の固定・再開、完了、各取り消し、同時操作を対象とする。全アプリの詳細設計が完了したものではない。

- 記録・精算履歴は追記で保存し、取り消しは別レコードとする。
- 次回の調整は保存済み支払い・精算・取り消しから導出する。通知イベントの到達や非同期ジョブに依存しない。
- 業務履歴とは別に、現在有効な精算対象の占有表を持つ。この表は同じトランザクションで追加・削除する補助状態であり、履歴から再構築できる。
- 支払い追加・取消、確認作成、精算完了・取消は同一旅行の処理順を共有する。二人用なので旅行単位の短い直列化を優先する。

## 2. 金額と参加者

旅行参加者には変更しないslot 0・slot 1を割り当てる。画面の「自分」はログインした利用者から変換する。Googleの表示名やメールアドレスを金額の向きの基準にしない。

内部の符号付き金額は「slot 1からslot 0へ」を正とする。本人がslot 1なら画面表示の向きを逆転する。

支払い額は正の整数、初期上限案は1件999,999,999円。DBはbigint、Node.js側の途中計算・合算はBigIntを使い、APIの円金額は10進整数文字列とする。上限と文字列形式は詳細設計上の提案。割合は整数0〜100、合計100。

支払者以外の負担＝floor(金額×その人の割合÷100)。支払者の負担＝総額−もう一人の負担。二人の割合と確定負担額を保存する。支払者slot 0なら寄与cはslot 1の負担、支払者slot 1ならcはslot 0の負担の負値。

## 3. 論理テーブル

UUIDは識別、timestamptzは登録日時、bigintの旅行内連番は精算順序に使う。日時やUUIDの大小だけで最新精算を決めない。

| テーブル／所有領域 | 主な列 | 制約・用途 |
|---|---|---|
| trip_participants／planning | trip_id, slot, user_id | PK(trip_id,slot)、UNIQUE(trip_id,user_id)、slotは0か1。金額利用開始後の参加者入れ替えは提供しない |
| trip_finance_guards／共通DB調整 | trip_id, next_settlement_sequence | PK trip_id。旅行作成時に用意するロック対象。業務領域のデータ所有とは別の調整機構 |
| payments／record | id, trip_id, plan_id?, amount_yen, payer_slot, slot0_percent, slot0_burden_yen, slot1_burden_yen, contribution_yen, label?, created_by, created_at | 金額・割合・負担和・寄与をCHECK。参加者と任意予定の所属をFK＋サーバーで検証 |
| payment_cancellations／record | payment_id, trip_id, cancelled_by, created_at | PK payment_id。元支払いへの参照。1支払い1取消 |
| settlement_previews／settlement | id, trip_id, created_by, created_at, signed_total_yen | 確認内容は不変。合計は明細合計と一致。機密認証情報を保存しない |
| settlement_preview_items／settlement | preview_id, payment_id, kind, contribution_yen, base_settlement_id?, expected_claim_fingerprint, expected_cancelled | PK(preview_id,payment_id,kind)。確認時の明細と対象状態を保持 |
| settlements／settlement | id, trip_id, preview_id, sequence, signed_total_yen, created_by, created_at | UNIQUE preview_id、UNIQUE(trip_id,sequence)。1確認の完了は1回のみ |
| settlement_items／settlement | settlement_id, payment_id, kind, contribution_yen, base_settlement_id? | PK(settlement_id,payment_id,kind)。BASEは元の寄与c、REVERSALは−c |
| settlement_cancellations／settlement | settlement_id, trip_id, cancelled_by, created_at | PK settlement_id。元の精算を削除しない |
| active_settlement_claims／settlement | trip_id, payment_id, kind, settlement_id | PK(payment_id,kind)。有効なBASE・REVERSALの重複を防ぐ補助表。対象履歴への参照 |
| command_receipts／アプリ共通 | actor_id, operation, idempotency_key, request_hash, resource_id, outcome | UNIQUE(actor_id,operation,idempotency_key)。同じキーの異なる入力は拒否。成功結果を同じ業務トランザクションで保存 |

kindはBASEまたはREVERSAL。REVERSALは元のBASEの精算を参照する。各子テーブルには所属旅行を検証できる複合参照を定義する。異なる旅行のpayment_id等を混ぜない。

列単独のCHECKだけで別行の総和や最新性まで保証できるとは扱わない。合計と履歴・占有表の対応はロック下のUseCaseで検証し、DB統合テストで確認する。PostgreSQLのCHECK・UNIQUE・FKの用途は[公式制約ドキュメント](https://www.postgresql.org/docs/current/ddl-constraints.html)を参照。

## 4. 次回対象の導出

支払いごとに、その支払いが取り消し済みか、有効なBASEとREVERSALがあるかを見る。

| 支払い | 有効BASE | 有効REVERSAL | 次回対象 |
|---|---|---|---|
| 有効 | なし | なし | BASE、金額c |
| 有効 | あり | なし | なし |
| 取り消し済み | なし | なし | なし |
| 取り消し済み | あり | なし | REVERSAL、金額−c |
| 取り消し済み | あり | あり | なし |

BASEなしでREVERSALだけ有効な状態、有効な支払いにREVERSALがある状態は不正として検出する。

c＝0でも未処理BASEは対象として扱う。取り消し後のREVERSALも0円の明細として閉じられる。対象の件数と金額0円は別物。

精算を取り消したら、その精算の占有だけを除去して上表を再評価する。BASEを取り消した場合、支払いが有効なら再精算へ戻り、取り消し済みなら対象なしとなる。REVERSALを取り消した場合、有効BASEが残るので同じ調整が再び対象となる。

元BASEより後のREVERSAL精算が有効な間は、最新の有効な精算のみ取り消せる規則によってBASEを取り消せない。

## 5. 確認内容の保持・再開

確認作成時に、その時点の対象をすべてスナップショットとして保存する。画面の再描画・残額GETでは作らない。新しい支払いが来ても明細へ加えない。

確認内容は自動期限切れにしない案。小規模運用で、受け渡し後の記録を妨げないことを優先する。これは認証セッションの無期限化ではない。再ログイン後も参加者認可を行う。

精算画面に自分の未完了確認を新しい順で表示し、「確認内容を再開」できる。自動選択せず、日時・方向・金額で識別する。新しい確認を作っても古い確認を消さない。有効性は再開時と完了時に検証する。

対象のfingerprintは有効なBASE／REVERSALの精算IDに加え、その支払いを含む精算明細と精算取消の履歴IDから作る。履歴を安定した順序で正規化して比較し、精算と取り消しを経て占有が元に戻った場合も変化を検出する。支払い取消状態は別列で比較する。別の精算の成立・取消で対象状態が変わった確認は競合扱いとし、金額が同じだけで有効と見なさない。

## 6. API契約案

全て認証・旅行参加者認可を実施。POSTはIdempotency-Keyを必須とする。金額や確認対象をクライアントから申告させて確定しない。

| Method・path | 入力概要 | 正常結果 |
|---|---|---|
| POST /trips/{tripId}/payments | amountYen, payerUserId,負担割合, label?, planId? | 201：確定負担額を含む支払い |
| POST /trips/{tripId}/payments/{id}/cancel | なし | 201：取消記録。既に取消済みなら200で既存を返す |
| GET /trips/{tripId}/balance | なし | 200：現在の方向・金額・対象件数・明細 |
| POST /trips/{tripId}/settlement-previews | なし | 201：固定した確認ID・明細・合計。対象なしは422 |
| GET /trips/{tripId}/settlement-previews?status=pending | ページカーソル | 200：自分の未完了確認一覧 |
| GET /trips/{tripId}/settlement-previews/{id} | なし | 200：元の明細と現在の検証結果 |
| POST /trips/{tripId}/settlements | previewId, completionKind, acknowledgedCancellationPaymentIds | 201：完了記録。0円の場合は受け渡し不要として記録した旨を表示 |
| GET /trips/{tripId}/settlements | ページカーソル | 200：履歴。各件の取り消し状態・可能性 |
| GET /trips/{tripId}/settlements/{id} | なし | 200：元明細、操作者、取り消し履歴 |
| POST /trips/{tripId}/settlements/{id}/cancel | なし | 201：取り消し。既に取消済みは200で既存 |

completionKindは非0円ならtransfer_completed、0円ならno_transfer_requiredを指定する。取消済み対象への例外を自動承認せず、変更明細を表示して了承したpaymentIdの集合を取得する。現在の取消済みBASEの集合と完全一致を検証する。契約はopenapi.finance.jsonを参照。

エラーはcode・message・関連ID・再確認先を返す。401未認証、403参加者でない、404対象なし、422入力・対象なし、409業務競合、503一時的処理不能を基本とする。内部SQLや他旅行の情報は返さない。

主要409コード：PREVIEW_CHANGED、CANCELLED_ITEMS_ACK_REQUIRED、TARGET_ALREADY_SETTLED、TARGET_PARTIALLY_SETTLED、SETTLEMENT_NOT_LATEST、IDEMPOTENCY_KEY_REUSED。既存の精算を返せるのは対象全体が同じ既存精算で処理されている場合。取消済みの同じpreviewを再利用して新しい精算は作らず、新規確認へ案内する。

## 7. トランザクションと排他

PostgreSQL READ COMMITTEDを使い、各更新の冒頭で対象旅行のtrip_finance_guards行をSELECT FOR UPDATEする案。同じ旅行の財務更新が同じロック規約を守ることが前提。ロック取得後に対象データを読む。先に読んだ値で更新判断しない。

SELECT FOR UPDATEは他の書き込み・ロック取得を待たせ、トランザクション終了時に解放される。この性質を使い、アプリのメモリ内mutexには頼らない。[PostgreSQL公式：行ロック](https://www.postgresql.org/docs/current/explicit-locking.html)

### 支払いの追加・取消

認証・認可 → BEGIN → 旅行ロック → 再送確認 → 入力／所属検証 → 支払いまたは取消を追記 → receipt → COMMIT → 通知。

取消時に非同期で調整レコードを作る必要はない。次の読み取りで第4節から導出できる。

### 確認作成

旅行ロック下で対象と占有状態を読み、確認と明細を同時に保存する。DBロックは保存後すぐ解放し、利用者の受け渡しを待たない。

### 精算完了

1. BEGIN、旅行ロック、同じコマンド／previewの完了済み確認。
2. 確認が指定旅行に属すること、現在の占有状態が一致することを検証。
3. BASE対象の支払いだけが確認後に取り消された場合、変更の了承と元金額の全額受け渡し申告があれば例外として許可。占有の変更はこの例外で許可しない。
4. 次の旅行内連番を払い出し、精算・明細・占有・receiptを同じトランザクションで作成。
5. COMMIT後に通知。取消済みBASEについては第4節のREVERSALが直ちに次回対象になる。

### 精算取消

旅行ロック下で最新の有効な精算を連番で検証し、取消を追記、対象占有を削除、receiptを保存してCOMMIT。過去明細は変更しない。占有を先に消してから別トランザクションで取消を書く構成は禁止。

### 読み取り・再送

残額や明細の組み立ては、単一SQLのスナップショット、または短いREPEATABLE READ読み取りトランザクションで整合した状態から取得する案。複数のREAD COMMITTEDクエリを跨いで異なる時点を混ぜない。

成功receiptは初期版で自動削除しない案。キーを変えず再送すれば元の結果を返す。ただし元リソースが後に取り消されたことは別の現在状態で表示し、再実行しない。失敗でロールバックした場合は成功receiptを残さず、状態を再検証する。

ロックタイムアウト／デッドロックではトランザクションを全てロールバックし、短い有限回の再試行または一時エラーとする。具体的な秒数・回数はVercel実行制限と合わせて決める。ネットワーク呼び出し・通知・利用者の確認をDBロック中に行わない。

## 8. 境界と実装への制約

共通のDB Unit of Workが接続・トランザクション・旅行ロックを提供する。recordは支払いを書き、settlementはポートを介して同じトランザクションの支払い情報を読む。recordからsettlementの業務処理を呼び出さない。表へのFK参照と、コード上の領域間依存は区別する。

DB接続方式・ORMは対話的トランザクションと行ロックを使えるものから選ぶ。この設計を、HTTP呼び出しごとに別接続になる構成へそのまま移植しない。

## 9. 検証と残作業

添付のfinance_model_check.pyは、対象導出・精算・取消をメモリ上で検証する設計モデル。DBやAPIの実装テストではない。

DB統合テストでは、二つの独立接続による同時完了、取消と完了の競合、最新取消の競合、ロールバック、再送、異なる旅行の並行処理を検証する。加えて占有表を履歴から再構築した結果との一致を検査する。
