# 詳細設計03：Googleログイン・二人限定認可・セッション

作成日：2026-09-07／再検証日：2026-09-08
状態：詳細設計上の選定と構成案。認証ライブラリはBetter Authを選定。ユーザーがライブラリ名や7日期限を個別承認したとの意味ではない。実アカウント・Google Cloud・Vercelの設定は未実施。

## 1. 選定と責務

Better AuthをNestJSの認証基盤として配置し、DrizzleアダプターでNeonへ認証データを保存する。NestJSのExpress基盤への組み込みは公式Nodeハンドラー／Express統合を基に行い、独自にOAuthの暗号検証を作らない。

Next.jsへ認証DB接続や認証ライブラリのサーバー実体を二重配置しない。Next.jsはログインボタン・ログイン後の画面・期限切れ時の遷移を担当する。業務DBへの直接アクセス禁止の合意を維持する。

Better AuthはGoogleプロバイダー、Drizzleアダプター、DBセッションを提供する。今回の構成はそれらを組み合わせる設計判断。

- [Googleプロバイダー](https://better-auth.com/docs/authentication/google)
- [Drizzleアダプター](https://better-auth.com/docs/adapters/drizzle)
- [Express統合](https://better-auth.com/docs/integrations/express)
- [セッション管理](https://better-auth.com/docs/concepts/session-management)

検証バージョンはBetter Auth 1.7.3。既存シェルのNode 20.17.0は依存パッケージの要求を満たさなかったため、導入済みNode 22.23.2で検証した。マシンのデフォルトNodeは変更していない。本番も採用するNext.js／NestJS／ライブラリが共通してサポートするNodeのパッチ版を選んで固定する。

## 2. 公開経路

```text
ブラウザ／ホーム画面から起動したWebアプリ
  ├─ 画面                     → Next.js
  ├─ /api/auth/*（限定経路）   → NestJS上のBetter Auth
  └─ /api/me・/api/trips/*     → NestJSの認証・認可Guard → UseCase
                                        ↓
                              Neon（認証・業務を論理分離）
```

本番の公開オリジンは一つのVercel URLに固定し、/api/*をバックエンドへ転送する案。ブラウザから別オリジンのNestJS URLへ直接呼び出す構成にはしない。Vercelでの実際のrewrites／プロジェクト構成は配信設計で検証する。無料プランの制約を維持する。

- Better AuthのbaseURLとtrustedOriginsは公開オリジンの固定値。リクエストのHostや任意のX-Forwarded-Hostから生成しない。
- CookieにDomainを設定せず、公開ホスト限定とする。プロキシはSet-Cookieを欠落・結合せずブラウザへ返す。
- NestJSの直接URLでも全APIで本人確認・認可を行う。「Next.js経由」という申告ヘッダーを認証の代わりにしない。
- 本番とローカル開発はOAuthクライアント／Cookie／DBを分離する。Preview URLをワイルドカードでtrustedOriginsへ加えない。

## 3. 二人のアカウントの事前登録

Googleが検証したsubを安定した外部識別子として登録する。メールアドレスは表示・連絡先として保持しても、実行時の許可判定の主キーにはしない。Googleはsubによる識別を案内している。[Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)

### 初期設定手順の案

1. 管理者の開発端末など、一般公開しない初期設定用OAuthフローを用意する。二人がそれぞれGoogleで本人確認する。
2. OAuthライブラリでstate・PKCE等を扱い、Googleのトークンの署名・issuer・audience・有効期限等を検証する。確認できたsubと基本プロフィールを初期登録処理に渡す。ブラウザ申告のメール・userId・未検証JWTのdecode結果から登録しない。
3. 管理者が二人に対応することを確認し、各人のアプリUUID、Google accountId=sub、利用許可行を1トランザクションで登録する。既存のGoogleトークン本体を資料やログへ保存しない。
4. 初期設定用フローは本番ルートに含めない。公開後の一般サインアップ・自己登録・メール一致による自動紐付けを提供しない。

これはデプロイ時の初期登録作業であり、毎回のログインに管理者承認を求めるものではない。初期設定コマンド自体はまだ作成していない。

### 実行時の制限

- Googleのみ有効。メール／パスワード認証は無効。
- GoogleのdisableSignUpをtrueにし、ユーザーは事前登録済みのものだけを利用する。
- accountLinking.enabled=false、disableImplicitLinking=true。追加リンク・解除・アカウント削除などの公開ルートも提供しない。
- セッション作成前のdatabase hookで、対象userIdのGoogle accountIdと許可リストのsubが一致し、利用可能であることを確認する。
- 業務APIの毎回の認証Guardでも同じ利用許可を確認する。DBにセッションが残っていても許可停止を反映する。
- Googleプロフィールの表示名・メールが変わってもsubが同じなら同一ユーザー。違うsubをメール一致だけで既存ユーザーへ入れない。

Google OAuthのTesting設定に二人を入れることは補助にはなるが、アプリ側の許可判定の代替にしない。

## 4. 認証データ

Better Authの正式なスキーマ生成結果を採用バージョンで確認し、Drizzleへマッピングする。ライブラリ標準表を推測したDDLで置き換えない。

| 論理表 | 内容・注意 |
|---|---|
| identity.users | アプリUUID、表示名、メール等。財務DDLのidentity.users参照に合わせる。UUID生成を明示設定 |
| identity.accounts | providerId=google、accountId=sub、userId。providerIdとaccountIdの組を一意にする |
| identity.sessions | ライブラリ管理のセッション識別子、userId、expiresAt等。更新・削除が必要であり財務履歴の追記専用トリガーを付けない |
| identity.verifications | OAuth等の一時検証データ。ライブラリの消費・有効期限管理に従う |
| identity.allowed_google_accounts | slot 0/1、userId、google_sub、enabled。最大二人を制約し、通常APIで編集させない |

identity.users.idを財務・旅行の外部キーの共通UUIDとする。Google subを業務のuserIdとして公開しない。旅行の参加者slotは各旅行で固定したものを使用し、認証許可リストのslotと同一であることへ依存しない。

allowed_google_accountsにはPK(slot)、CHECK(slot IN (0,1))、UNIQUE(user_id)、UNIQUE(google_sub)、FK user_idを定義する。accountsとの一致はセッション発行と業務Guardで検証する。

認証テーブル内のセッショントークンやGoogle OAuthトークンは機密情報。ライブラリの実際の保存形式を確認するまで「すべてハッシュ化済み」とは扱わない。ブラウザ向けDTOや通常ログには含めない。Google API呼び出し用の追加scope、refresh tokenの追加取得、オフライン権限は要求しない。標準動作で保存するトークンの最小化・暗号化設定は生成スキーマと併せて実装で確認する。

## 5. セッション

| 項目 | 設計値 |
|---|---|
| 管理方式 | NeonのDBセッション。Redisや独自のJWTを追加しない |
| 本番Cookie名 | __Secure-travel.session_token（採用バージョンの生成結果で確認） |
| 属性 | Secure、HttpOnly、SameSite=Lax、Path=/、Domain未設定 |
| 有効期間 | 発行から7日。初期値の提案 |
| 自動延長 | 無効。期限切れならGoogleで再ログイン |
| Cookieセッションキャッシュ | 無効。APIはDB上の有効性を確認 |
| 保存先 | ブラウザCookieのみ。localStorageへセッショントークンを保存しない |

Better AuthのexpiresIn、disableSessionRefresh、cookieCache.enabledで指定する。Cookieの存在確認だけでログイン済みとは判断しない。署名検証・DB有効期限・利用許可が必要。

セッションをDBで取り消してもCookieキャッシュから利用可能な時間を残さないため、この規模ではCookieキャッシュを使わない。[Better Authの失効とキャッシュ](https://better-auth.com/docs/concepts/session-management)

ログアウトは現在の端末のセッションをサーバーで削除しCookieを失効させる。2026-09-09の通知設計06により、その前に利用者行ロック下で通知セッション停止記録と購読無効化をCOMMITする。前処理失敗時は503で未完了とし、遅い購読PUTは停止記録で拒否する。既にsessionを識別できない場合の200はCookie消去であり、通知停止は保証しない（ブラウザunsubscribe、必要なら再ログインして購読管理）。端末紛失時は管理者が利用許可を無効にし、その利用者の全セッションを失効させる手順を用意する。Google側でアクセスを解除したことを、アプリの全セッションへ即時反映できるとは扱わない。

## 6. ログインから画面表示

1. /sign-inでGoogleログインボタンを押す。
2. 同一オリジンのPOST /api/auth/sign-in/socialへ進む。サーバー側でGoogleのみ、認証コードによるリダイレクトフローのみ許可し、任意provider・idToken直接入力・追加scope・任意callbackURLを拒否する。
3. Googleの画面で本人確認し、登録済みの公開URL /api/auth/callback/googleへ戻る。
4. ライブラリのOAuth検証、事前登録アカウントの一致、利用許可、セッション発行を行う。
5. ブラウザにCookieを設定し、アプリ内の固定したログイン後ページへ移動。
6. GET /api/meで安全な表示用情報を取得し、旅行を選んでホームへ進む。

任意の外部returnToは許可しない。通知等からの復帰先はアプリ内の許可した相対パスに限定し、その対象への権限を遷移先で再検証する。

## 7. Next.jsとNestJSの本人確認

ブラウザの業務API呼び出しは同一オリジンの/api/*にCookieを送る。NestJSはBetter AuthのサーバーAPI getSessionで検証し、そこから得たuser.idをUseCaseへ渡す。リクエストbodyのuserIdやX-User-Idを操作主体にしない。支払者userIdは入力として受けるが、操作者とは別であり旅行の参加者に限定する。

Next.jsのServer Componentでデータを読む場合は、固定したバックエンド宛先に当該リクエストのCookieを転送し、NestJSに検証させる。ユーザーが指定したURLへCookieを転送しない。認証情報付きfetchとページは利用者間でキャッシュ共有しない。明示的にno-storeを使用する案。

Next.jsからサーバー側で業務更新する経路は初期版に追加せず、ブラウザからの同一オリジンPOSTを基本とする。後でServer Actionsを使う場合は、元の利用者の認証・Origin検証を維持し、サーバーからの呼び出しであることだけを理由に認可を省略しない。

## 8. CSRF・公開ルート

認証はCookie方式なので、業務POSTには次の検査をNestJS側で必須とする。

- Originが固定した公開オリジンに完全一致する。欠落・null・他オリジンは拒否。
- JSON bodyがある操作はContent-Type application/json。bodyなしのPOSTでも同ヘッダーを送る契約に統一する。
- CORSは別オリジンからの資格情報付き呼び出しを許可しない。CORSだけをCSRF対策とはしない。
- SameSiteとライブラリのCSRF対策を無効化しない。独自の業務APIはBetter Authハンドラーの外にあるため、ライブラリの保護が自動適用されると思わない。

認証ルートの公開は次に限定する。

| 経路 | 内容 |
|---|---|
| POST /api/auth/sign-in/social | Googleのリダイレクトログイン開始。公開Originを必須とし、入力を限定 |
| GET /api/auth/callback/google | Googleからの戻り。通常のOrigin必須判定の例外とし、state／PKCE等のOAuth検証に委ねる |
| POST /api/auth/sign-out | 現在のセッションの失効。Origin必須 |
| GET /api/auth/error | ライブラリが使用する場合のエラー表示。一般的な説明だけ返す |

Better Authのget-sessionやアカウント・トークン管理APIをそのまま全公開しない。GET /api/meで必要項目だけ返す。UIではsignIn.socialとsignOutだけを利用し、公開get-sessionへ依存するuseSessionは使わない案。

NestJSへの組み込みでは、認証ハンドラーが読むbodyを先に消費しない。経路・入力の検査でFetch Requestのbodyを読むときはcloneを使う等、元のbodyを保持する。OAuth callbackのqueryと複数Set-Cookieを完全に引き渡すことを統合テストする。

ライブラリのOrigin・OAuth保護は[公式セキュリティ資料](https://better-auth.com/docs/reference/security)に従う。

## 9. 業務APIの認可とレスポンス

順序：セッション検証 → 利用許可 → 旅行参加者 → 指定予定／記録の所属 → 業務ルール。

- 401：未ログイン・偽造・失効・期限切れ。
- 403：アプリ利用不可、旅行非参加者、Origin不一致。
- 404：認可済み旅行内で対象が存在しない。
- 503：認証DBに接続できない。一時障害を未認証として扱い、勝手にCookieを消さない。

業務のidempotency receiptがあっても認証・認可を省略しない。失効後の再送には401。再ログイン後に同じ利用者が同じキーを再送した場合は、既存の保存結果を再確認できる。

有効性チェックが終わった直後のログアウトと処理中の更新は競合し得る。ログアウト完了後に新しく検証する要求は拒否するが、既に認証済みで開始した処理まで巻き戻す保証はしない。残る精算の保存結果は再ログイン後に確認する。

## 10. 画面とオフライン

401ならログインへ進み、元の入力や精算確認を勝手に再送しない。再ログイン後に必要なら内容を再確認して続行する。固定済み精算確認はDBに残るため再開できる。

ログアウト成功時には画面状態・クライアントキャッシュを消す。オフラインしおりを実装する場合、利用者別に分離してログアウト時に消去する。Service Workerは/api/auth/*、/api/me、記録・精算APIを汎用キャッシュしない。

オフラインでログアウト操作をした場合は端末内の表示・キャッシュを消せても、サーバーの失効とHttpOnly Cookieの消去は完了できない。「端末の表示を閉じました。サーバーのログアウトは未完了」と区別し、通信復帰後に実行する。ログアウト未完了のフラグは機密トークンを含まず、復帰時に自動ログイン表示する前に失効を試みる。

## 11. 実装への受け入れ条件と今回の検証

validate_auth_design.mjsでは、Better Auth 1.7.3とメモリDBを使い、以下を確認した。

- 本番Cookie名・Secure・HttpOnly・SameSite・Domain未設定。
- 許可したuserIdとGoogle subの一致、第三者へのセッション発行拒否。
- 7日セッション、偽Cookie・期限切れの拒否。
- 署名付きCookieのセッション検証と、旅行参加者でない場合の拒否。
- 利用許可停止・Google sub不一致で既存セッションも拒否。
- 別Originのログアウト拒否と、正常ログアウト後のCookie再利用拒否。
- 業務POSTのOrigin欠落・null・Content-Type不正の拒否（設計モデル）。

Googleへの実認証、初期登録処理、Drizzleの認証スキーマ生成・Neon接続、NestJSでのraw body・Cookie転送、Vercel rewrite、iPhone／Androidでのログインは未検証。テスト内では内部アダプターでセッションを作っているが、本番にそのようなログイン回避APIを公開しない。

次は予定・達成・予約APIとDB制約を具体化する。認証の実装時には上記未検証項目を埋め、ブラウザ開発者ツールとサーバーログにCookie・Google tokenが漏れないことも確認する。
