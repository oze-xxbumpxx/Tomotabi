# 詳細設計04：予定・達成・予約

作成日：2026-09-08
状態：実装前の詳細設計。合意済みの入力・種類変更・重複制限を具体化する。画面の細かな上限値や排他方式は詳細設計上の選択。

## 1. 対象とデータ

旅行期間、予定の追加・編集・日の移動・取りやめ、達成・予約の追加・取り消し、日別しおりと記録一覧を対象とする。旅行作成・一覧と持ち物・思い出の完全な仕様は今回の対象外。

予定種類：place（場所）、food（食べ処）、shopping（買い物）、lodging（宿）、transport（移動）。

| データ | 内容 |
|---|---|
| planning.trips | 旅行名、開始日・終了日、状態planning/traveling/finished、version |
| planning.plans | ID、旅行、予定名、種類、日付、任意時刻・メモ、取りやめ日時・操作者、version |
| record.plan_events | 達成または予約の記録、予定・旅行、登録者、登録日時 |
| record.plan_event_cancellations | 元記録、旅行、取り消した人、日時。1記録1取消 |
| record.active_plan_events | 有効な記録の占有。PK(plan_id,event_kind)、UNIQUE(event_id) |

達成と予約の履歴は同じ構造の表で管理するが、APIでは既存案どおり/achievementsと/bookingsを分ける。取り消し済み履歴も残す。表示状態を単一のstatusへまとめず、予定の取りやめと有効な達成・予約を独立して表示する。

暫定入力上限：予定名100文字、メモ2,000文字、旅行名100文字。時刻はHH:mmまたはnull、秒とタイムゾーンを持たない現地時刻として日本時間で扱う。日時の履歴はtimestamptz、日付はdate。未定時刻を00:00へ変換しない。

## 2. 予定の更新契約

予定GETはETagと本文versionを返す。更新はIf-Match必須とし、サーバーで現在のversionと照合する。形式は強いETagの引用付き10進整数（例："3"）。ワイルドカード・複数値は受け付けない設計。

| 操作 | 入力とルール |
|---|---|
| 追加 | name, kind, date必須。time, memo任意。旅行期間内のみ |
| 通常編集 | name, kind, time, memoの部分更新。日付は含めない |
| 日の移動 | date。旅行期間内の日付を指定 |
| 取りやめ | 本文なし。cancelled_at/cancelled_byを一度設定。復活APIなし |
| 旅行期間変更 | startsOn/endsOn。期間外へはみ出す予定があれば拒否。取りやめ済みも含める |

種類変更は達成・予約の履歴が一度もない場合のみ可能。支払いだけがある場合は可能。取り消し済み記録も履歴として制限に含める。取りやめ済み予定でも通常のメモ等は編集できる案だが、取りやめ状態を編集で解除させない。

更新が実質同じ値ならversionを増やさず、通知も重ねない。更新成功時は新しいETagを返す。If-Matchなしは428、不一致は既存API案に合わせ409 VERSION_CONFLICT（一般的な412を使わない選択を明記）。入力不正は422。

二重送信対策として全書き込みにIdempotency-Keyを使う。同じキーの成功再送はIf-Match再評価より先に既存結果を返すが、現在の認証・認可は必須。本文とIf-Matchもrequest_hashへ含める。予定・旅行は後から変わるため、command_receipts.response_bodyへ成功時DTOを保存し、元のversionからETagを復元する。再送後に現在の状態を確認する場合は別GETを行う。セッショントークン等は保存しない。

## 3. 達成・予約の追加

1. セッション・利用許可・旅行参加者を確認する。
2. トランザクションを開始し、旅行行、対象予定行の順にロックする。
3. planIdとtripIdの一致を確認する。
4. 種類と取りやめ状態を検証する。
5. 有効な同種記録がある場合は追加せず、409 RECORD_ALREADY_ACTIVEと既存記録IDを返す。
6. 履歴行とactive_plan_eventsを同じトランザクションで作成する。
7. COMMIT後に相手へ通知する。

| 記録 | 対象種類 | 取りやめ済み予定 |
|---|---|---|
| 達成 | place/food/shopping | 新規追加不可 |
| 予約 | food/lodging/transport | 追加可能 |

同一Idempotency-Keyの再送は200で元の記録を返す。別のキーによる重複追加は409。UIは既存記録を取得して状態を更新する。

予約記録の追加・取り消しでは外部の予約サービスを操作しない。

## 4. 記録の取り消し

旅行・予定を同じ順序でロックし、指定された記録とURLの種類の一致を検証する。達成URLで予約記録IDを渡した場合も操作しない。

取消行を追記し、対象event_idに対応する占有だけを削除する。取り消しと占有削除は同じトランザクション。履歴行は更新・削除しない。

取り消し後は現在の予定が種類・取りやめ条件を満たせば再登録可能。同じ取消の再実行は既存取消を返し、新しい記録の占有を消さない。古い記録の取り消しを、planIdと種類だけでDELETEする実装は禁止。

## 5. 排他方式

予定ごとの編集の独立性を保つため、通常操作は旅行行をFOR SHARE、対象予定をFOR NO KEY UPDATEの順で取得する。旅行を跨ぐ一括操作は初期版にない。旅行期間変更だけは旅行行をFOR UPDATEで取得する。

- 種類変更と達成・予約の追加は同じ予定ロックを使う。記録が先なら種類変更を拒否、種類変更が先なら新しい種類で記録可否を判定する。
- 予定の取りやめと達成追加も同じ順序で処理する。達成が先に成立した後に取りやめた場合は両方を表示し、取りやめが先なら達成を拒否する。
- この排他により、元資料が許容していた「照会後に取りやめが発生する競合」を初期実装では抑制する。業務ルールの緩和ではなく、種類変更の整合性と同じロックで保証を強める実装判断。
- 予定追加・日の移動・期間変更が同時でも、旅行ロックにより期間外の予定を成立させない。
- 通知送信・外部API・利用者の入力待ちはロック中に行わない。

財務処理は別のtrip_finance_guardsを使う。共有トランザクションが必要な将来機能ではロック順序を再設計し、財務と予定を逆順にロックしない。現在の支払い追加は予定所属を照合するだけで、予定の種類・取消状態による制約は持たない。

## 6. 読み取りと画面

日別しおりは旅行期間を返し、日付ごとの予定に有効達成・有効予約のIDと日時を結合する。並び順はtime ASC NULLS LAST、created_at ASC、id ASC。取りやめ済みも一覧に残す。ホームの抜粋では取りやめを除外する。

予定詳細は現在の予定と有効記録、canChangeKind、不可理由を返す。canChangeKindは取消済みも含めた履歴の存在で判定する。UIの可否は参考であり書き込みで再検証する。

GET /recordsは達成・予約・支払い・各取消を登録日時降順でまとめる。typeとplanIdによる絞り込み、カーソルでの追加取得を設ける。2026-09-09追記：通知の深いリンク向けにrecordId（元記録ID）の条件を追加。指定時はtype必須、cursor／limit併用不可で400。旅行参加者認可後に元記録とその取消の最大2件を取得しnextCursor=null。planId併用はAND、該当なしは200空配列。取消カードは元記録への参照を持ち、元記録も取消状態を表示する。精算履歴は/settlementsで扱う。予定の通常編集履歴を記録タイムラインに追加しない。

単一SQLまたは短いREPEATABLE READトランザクションで、予定・有効占有・取消の読み取り時点をそろえる。全クエリに認可済みtripIdを適用する。

## 8. 検証条件

- 食べ処に達成と予約を各1件登録できる。同種を2件有効にできない。
- 記録を取り消して再登録できる。古い取消を再送しても新記録が消えない。
- 達成・予約の履歴があれば、取消済みでも種類変更を拒否する。
- 支払いだけなら種類変更できる。
- 取りやめ済みへの達成は拒否、予約可能種類の予約は許可。
- 予定取消で既存の達成・予約を自動取消しない。
- 期間変更・日の移動・予定追加の競合で期間外の予定を作らない。
- stale ETagで相手の変更を上書きしない。
- 別旅行・URL種類不一致・第三者のIDで更新できない。

SQLの制約と設計モデルをこの段階で確認する。実際の複数接続による競合とAPI経由の認証は実装後に検証する。
