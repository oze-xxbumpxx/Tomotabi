# 詳細設計05：旅行の作成・選択・開始／終了とホーム

作成日：2026-09-08
状態：実装前の詳細設計。2026-09-08、手動開始・終了、終了後の編集・精算・訂正、終了状態を戻す機能なしを合意。その他の細かな条件・ホーム状態分岐は詳細設計案。

## 1. 今回の範囲と判断

- 旅行は名前・開始日・終了日を指定して作成し、参加者は許可された二人をサーバーで設定する。
- 状態はplanning → traveling → finished。本人・相手のどちらも手動で開始・終了できる案。日付による自動遷移はしない。
- 状態変更を予定日付の到来に限定しない案。早めの開始や、帰宅後の終了記録を妨げない。
- 旅行終了は旅行の進行状態だけを変える。精算を自動実行せず、支払いや記録を自動で取り消さない。
- 終了後も支払い・精算・訂正、および予定の編集を既存の制約内で許可する案。終了をデータ凍結として扱わない。
- 初期版は終了取り消し、旅行の削除、参加者変更を提供しない。誤って終了した場合もデータ操作は継続できるが、状態を戻すUIはない。必要性が出れば基本設計として再検討する。
- 複数の旅行の同時進行を禁止するルールは追加しない。選択中の旅行を明示する。

手動開始・終了、終了後の編集・精算・訂正、終了状態を戻す機能なしは合意済み。日付による操作制限の有無など、その他の細部は詳細設計案として区別する。

## 2. 旅行作成

入力：name（1〜100文字、空白のみ不可）、startsOn、endsOn（YYYY-MM-DD）。終了日は開始日以降。

処理：

1. セッションと利用許可を確認。
2. DBトランザクション内で二人の許可情報を再確認し、登録済み利用者を固定した順序で読み取る。実装時には許可情報変更との競合を避けるため対象行をFOR SHAREで取得する。
3. 利用可能な許可アカウントが二人揃っていることを確認。欠けている場合は409 PARTICIPANTS_NOT_READY。
4. 旅行、二人のtrip_participants、trip_finance_guards、再送receiptを同じトランザクションで作成する。
5. 201と旅行DTO・ETagを返し、作成した旅行のホームへ移動する。

参加者IDをクライアントから指定させない。二人のslotは作成時に確定し、その旅行内では変更しない。Google subはレスポンスに含めない。

旅行作成は既存旅行のguardを使えないため、再送制御はreceiptのユニーク制約を使う。同じキーで同時に二つの旅行を作ろうとした場合、負けたトランザクションを全てロールバックし、既存receiptのrequest_hashを比較して同じ作成結果を返す。

## 3. 一覧と選択

GET /tripsは参加中の旅行だけをcreated_at DESC、id DESCで返す。状態の絞り込みとカーソルを設ける。他人の旅行の名前や件数を返さない。

前回選択のtripIdを利用者ごとのローカル設定として保持する案。これは認証情報ではない。起動時にGET /trips/{tripId}で再検証し、アクセス可能ならホームへ進む。不可なら旅行一覧へ戻る。単にIDを保存していることを権限の根拠にしない。ログアウト時に利用者の選択状態を消す。

一覧の各カード：旅行名・期間・状態。「旅行を作成」から入力へ進む。最初から勝手に別旅行へ切り替えない。前回選択がなければ一覧を表示する。

## 4. 名前・期間・状態の更新

旅行にも独立したversionを持たせる。GET /trips/{tripId}のETagを更新時のIf-Matchとして送る。予定の編集は旅行versionを増やさない。

| 操作 | 条件・効果 |
|---|---|
| 名前変更 | 名前だけ更新。通常編集なので相手へ通知しない |
| 期間変更 | 04の方式で、取りやめ済みを含む全予定が新期間内に収まることを検証 |
| 開始 | planningのみ。travelingへ更新し、started_at／started_byを保存 |
| 終了 | travelingのみ。finishedへ更新し、finished_at／finished_byを保存 |

状態遷移は旅行行のFOR UPDATE下でIf-Matchと現在状態を確認し、versionを増やす。同じキーの成功再送は元のDTOを返す。別キーで同じ遷移を要求した場合は、ETag一致なら既に目的状態の結果を200で返し、再度versionや日時を変更しない。ETag不一致なら409 VERSION_CONFLICT。finishedからstart、planningからfinishなどの不正遷移は409 INVALID_TRIP_TRANSITION。

開始・終了は既存の通知対象に含めていないため、今回勝手にプッシュ通知を追加しない。成功結果は操作者の画面に表示する。

画面では「旅行を終了」前に「未精算分があっても、終了後に精算できます」と説明する。旅行終了を支払い完了の証明として表示しない。

## 5. ホームAPI

GET /trips/{tripId}/homeを追加し、必要な情報をバックエンドの読み取りサービスでまとめる。第6の業務領域や新しい正本は作らない。planning・record・settlementの読み取りポートを共通の短いスナップショットで実行する。

| 情報 | 内容 |
|---|---|
| trip | 名前・期間・状態・version |
| context | 日本時間のtoday、表示モード、対象日、期間上の日数表示、状態とのずれの補足 |
| schedule | 対象日の取りやめていない予定を最大3件、全件数、有効な達成・予約状態 |
| balance | 現在の受け渡し方向・金額・対象件数。確認内容は固定しない |
| recentRecords | 記録タイムラインと同じ規則による最新3件 |
| fetchedAt | 取得日時 |

ホームから支払い入力を開くと予定は未選択。予定カードから詳細を開いた場合は元のホームへ戻れるようにする。精算カードから精算画面を開き、そこで対象を確認する。

## 6. 日付と旅行状態が食い違う場合

ホーム表示モードは、終了状態を優先し、それ以外は日付で対象日を決める案。日付だけで旅行の保存状態は変更しない。

| 条件 | モード・表示 |
|---|---|
| status=finished | completed。精算と最近の記録を優先。しおりへの導線は維持 |
| 未終了でtoday < startsOn | before。初日の予定、出発までの日数 |
| 未終了でstartsOn <= today <= endsOn | during。今日の予定。「期間上の何日目」を表示 |
| 未終了でtoday > endsOn | after_dates。予定期間が終了したことと状態確認への導線 |

planningのまま旅行日になったら「旅行を開始」への導線。travelingでも期間前なら初日の予定を表示し、今日の予定とは呼ばない。期間後でplanningのままなら、開始→終了という手動手順を案内するか、操作せずしおりを開ける。状態を飛ばして自動終了させない。

completedとafter_datesではscheduleをnullとする。予定がない日を取得した場合はschedule.items=[]。この二つを区別する。

当日予定の抜粋は「未達成を先、各グループ内で時刻順・未定末尾・登録日時・ID順」の案。達成対象外の宿・移動は、時刻が過ぎたことだけで完了にしない。全件を見たい場合は対象日を選んだしおりへ移動する。

## 7. 失敗・キャッシュ

全クエリは認可済みtripIdで絞り、同じ読み取りトランザクションを利用する。ホーム用の金額計算はsettlementと共通にする。

最初の旅行／認可取得に失敗した場合は401・403・404・503を返す。その他の部分取得で回復可能な失敗が起きた場合は、各sectionをstatus=unavailableとして返す案。失敗した精算額を0円へ置き換えない。

SQLが失敗するとPostgreSQLのトランザクションが失敗状態になり得るため、部分取得はSAVEPOINTとROLLBACK TO SAVEPOINTで回復できるエラーに限る。接続断や認証失敗など回復不能なエラーならホーム全体を503とする。同じトランザクション接続へPromise.allで複数クエリを投げて独立成功扱いしない。

Cache-Control: private, no-store。CookieやGoogle情報をレスポンスに含めない。常時ポーリングはせず、画面表示・手動更新・自分の操作成功後に再取得する。

## 8. 作成するAPI

| Method | path | 用途 |
|---|---|---|
| POST | /trips | 作成。Idempotency-Key必須 |
| GET | /trips | 自分の旅行一覧 |
| GET | /trips/{tripId} | 既存04の取得契約を拡張 |
| PATCH | /trips/{tripId} | 名前変更。If-Match必須 |
| POST | /trips/{tripId}/start | 開始。If-Match必須 |
| POST | /trips/{tripId}/finish | 終了。If-Match必須 |
| GET | /trips/{tripId}/home | ホームの集約 |

期間変更は既存openapi.planning.jsonのPUT /periodを利用する。共通Trip DTOは同ファイルを正本とし、開始／終了日時と操作者を追加する。
