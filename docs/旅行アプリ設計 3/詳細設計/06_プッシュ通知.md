# 詳細設計06：Web Push通知

作成日：2026-09-08／更新日：2026-09-09
状態：DB・API・関連設計を具体化し、設計モデルの検証10項目が成功。通知ライブラリ、上限値、設定画面、送信文言は詳細設計上の選択。アプリ実装・実配信・実機検証は未実施。

## 1. 方式と前提

標準Web Push＋Service Worker＋VAPIDを使い、NestJSからweb-pushで暗号化・VAPID署名した通知を配信する。有料通知サービスや到達保証の基盤は追加しない。VAPID秘密鍵はバックエンドだけに置き、公開鍵だけをブラウザに配布する。

iPhoneはiOS 16.4以降のホーム画面に追加されたWebアプリから、本人の操作に応じて通知許可を求める。Apple Developer Programへの加入は不要。[WebKit公式](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
Androidは初期の実機検証対象をChromeとする案。実際のブラウザは未確認。UA文字列だけで決めず、Service Worker・PushManager・Notificationの機能有無を確認する。[PushManager.subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe)

Service Workerとmanifestは通知のために先行導入できる。オフラインしおりの実装まで同時に必須とはしない。

## 2. 初回設定と端末ごとの状態

設定画面に「この端末の通知」を設ける。

| 状態 | 表示・操作 |
|---|---|
| 未対応 | この環境では通知を利用できない旨。アプリの利用は継続可能 |
| iPhoneでホーム追加が必要 | ホーム画面へ追加し、追加したアイコンから開く手順 |
| 未許可 | 「通知を有効にする」。タップ後にOS／ブラウザの許可を要求 |
| 拒否済み | ブラウザ／OS設定から変更する案内。毎回許可要求を繰り返さない |
| ブラウザ購読あり・サーバー未登録 | 登録を再試行。許可済みだけで「通知設定完了」としない |
| 登録済み | 有効と表示し、「この端末の通知を停止」 |
| サーバー側で失効 | 再登録への案内。通常のアプリ表示時に状態確認 |

順序：Service Worker登録 → ユーザー操作で許可 → PushManager.subscribe({userVisibleOnly:true, applicationServerKey}) → 購読をサーバー登録 → 完了表示。既存購読があればgetSubscriptionで取得して照合する。

OS権限の許可は初回設定として行う。アプリ内の予定等の通常編集を通知しないという合意は維持する。無効化済みの購読を画面表示だけで自動的に再有効化しない。ID喪失時のPUTによる照合も「通知を有効にする／再登録」の明示操作時に行う。

## 3. DBと所有者

notification.push_subscriptionsを追加する。主な列：id、user_id、endpoint、endpoint_hash、p256dh、auth_secret、expiration_time、registration_session_id、device_label、vapid_key_id、enabled、revision、created_at、updated_at。

- endpoint_hashは元のendpoint文字列のSHA-256で一意。URLのpath/queryを勝手に書き換えない。
- 鍵はbase64urlをデコードしてp256dhが65byteの有効なP-256公開鍵、authが16byteであることをサーバーで確認する。
- 宛先・鍵は秘密情報として扱い、一覧レスポンス・通常ログへ返さない。
- 登録者はセッションから取得し、bodyでuserIdを指定させない。
- 別利用者の同じendpointへの登録は409。所有者を黙って移さない。同じ利用者の再登録はupsert。
- 初期上限案は有効な購読が一人3件まで。利用者行をロックして件数確認とupsertを行い、同時登録で超過させない。
- registration_session_idは登録時のセッション識別子。セッション失効時の自動CASCADE削除をしないため、削除可能なライブラリsession表へのFKは付けない。登録時に検証済みsessionから設定する。

追加のnotification.closed_push_sessionsはsession_id、user_id、closed_atを持つ。ログアウト後の遅延登録を拒否する停止記録であり、通知イベントや再送用キューではない。初期版では保持し、削除を導入する場合は元セッションが再び有効にならないことを確認する。

DBの型・長さ・FK・endpointハッシュ一意性はSQLで制約する。SHA-256とendpointの一致、P-256曲線上の点、canonicalなパディングなしbase64url、所有者、許可ホスト、有効数3はUseCaseの責務。byteaへデコードして保存し、送信時にbase64urlへ戻す。期限はAPIのUnixミリ秒をtimestamptzへ変換し、非nullなら未来かを検証する。

同じ端末で別アカウントへ切り替える場合は、元の端末購読を停止しブラウザ側でunsubscribeしてから再登録する。停止は任意の他利用者の購読に適用できない。

## 4. API

Cookie認証・二人の利用許可を確認し、書き込みはOrigin完全一致を要求する。PUTはJSON必須、DELETEはbody不要。すべての応答はCache-Control: no-store。

| Method | path | 内容 |
|---|---|---|
| GET | /me/push-config | VAPID公開鍵とkeyId、対応する設定情報 |
| GET | /me/push-subscriptions | 自分の購読ID・端末名・有効状態・更新日時。宛先と鍵は返さない |
| PUT | /me/push-subscriptions | endpoint、keys、expirationTime、deviceLabel、keyIdを登録／更新 |
| DELETE | /me/push-subscriptions/{id} | 自分の購読を無効化。繰り返しても204 |

PUTはendpointと所有者で自然に冪等。無変更の再登録はrevisionを増やさない。変更時はrevisionを増やす。Idempotency-Keyを今回の自然に冪等な購読APIに追加しない。

ブラウザ側のsubscriptionとサーバー一覧は購読IDを端末内に保持して対応付ける。IDを失った場合は、同じendpointのPUTで自分の購読を再確認する。通信成功前に設定完了としない。

## 5. 宛先検証

endpointはサーバーからの接続先になるため、任意URLへ送信しない。初期許可ホストはfcm.googleapis.comと、ラベル境界を確認した*.push.apple.com。HTTPS、443、userinfoなし、fragmentなしを必須とする。リダイレクトは追わない。登録時と送信時の両方で検証する。

Appleの許可ドメインはWebKit公式、ChromeのFCM endpointの例は[GoogleのWeb Push説明](https://web.dev/articles/push-notifications-overview)に基づく。すべてのブラウザの配信先を網羅したリストではない。実機が別ホストを返す場合は公式資料と実際の購読を確認して追加する。未知ホストは422 UNSUPPORTED_PUSH_SERVICEとし、アプリ本体は利用可能にする。

endpointのホストが悪意ある末尾一致（fcm.googleapis.com.evil.example等）やIP・localhost・任意ポートにならないことを検証する。DNS・接続先の防御は配信環境の出口制御も含めて検討する。購読鍵の形式が正しいだけでブラウザ由来の証明になるとは扱わない。

## 6. 通知対象と宛先

通知対象：予定追加・取りやめ・日の移動、達成・予約・支払いの追加と取消、精算の完了と取消。

通知しない：通常編集、旅行の作成・開始・終了、精算確認の作成、閲覧、同じ成功操作の再送、購読の登録・解除。通知失敗を埋めるための新たな通知も出さない。

送信前に対象旅行の参加者から操作者を除き、現在利用許可のある相手の有効購読だけを取得する。操作者自身の別端末にも送らない。期限のある購読はexpirationTimeを確認する。停止記録のあるregistration_session_idは除外する。期限切れは登録時の利用者ロック下で無効化してから上限を数える。

## 7. 保存後の送信と時間制限

UseCaseのCOMMIT成功後にだけ、通知用のイベントをメモリ上で渡す。イベントはeventId、action、tripId、targetKind、targetId、occurredAtを含む。eventIdは元の業務操作を識別し、追加と取消は別IDとする。

VercelのNestJS実行境界でwaitUntilに送信処理を渡す案。無保護のvoid send()は使わない。waitUntilもFunctionの寿命を超える保証や永続化は持たない。[Vercel公式](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package)

- COMMITから処理登録までに終了すると通知が欠落し得る。合意した許容範囲とする。
- 永続キュー、Outbox、自動再送は追加しない。購読の登録再試行と、業務通知の再送は別物。
- 通知失敗で保存済みの業務操作を失敗レスポンスへ変えない。同じコマンドの再送で通知だけ送り直さない。
- 初期案は配信先あたり全体3秒、同時に最大3件。全失敗もPromise.allSettledで回収する。HTTP処理をDBロック中に行わない。

web-pushのtimeoutはsocket timeoutであり、処理全体の上限とは異なる。generateRequestDetailsで暗号化・署名済み要求を作り、NodeのHTTPS transportでAbortSignalによる全体期限とリダイレクト禁止を指定する設計とする。単にPromise.raceで待つのをやめて送信を残す実装にはしない。[web-push公式](https://github.com/web-push-libs/web-push)

waitUntil連携が実行境界で成立しない場合は、同じ上限付き処理を応答前にawaitする代替を検証する。いずれも保存の成否と送信の成否を分離する。

## 8. 応答ごとの扱い

| 結果 | 処理 |
|---|---|
| 2xx | 配信サービスが受け付けたと記録。端末表示・既読を保証しない |
| 404／410 | 失効として購読を無効化 |
| 400／401／403 | payload・VAPID・設定を調査するログ。全購読を自動削除しない |
| 429／5xx／通信失敗／期限超過 | 今回は欠落として終了。購読は維持。自動再送なし |

失効無効化は送信時のidとrevisionが現在も一致するときだけ行う。送信中に鍵や購読が更新された場合、新しい購読を古い失敗で無効化しない。無効化のDB更新が失敗しても、元の業務データに影響させない。

ログはeventId、購読ID、結果種別、HTTP status、所要時間まで。endpoint・暗号鍵・Cookie・通知本文・Google情報は記録しない。

## 9. 通知文面とタップ後

初期の文面案：タイトル「旅行アプリ」、本文「予定が追加されました」「支払いの記録が更新されました」「精算の記録が更新されました」など。金額・場所・予定名はロック画面へ出さず、アプリ内で確認する。

payloadはschemaVersion、eventId、action、tripId、targetKind、targetId、occurredAt。最大2KB（UTF-8のJSONサイズ）の案。自由なURL・任意HTMLを含めない。

Service Workerはpushイベントのevent.waitUntilで表示処理を保持する。payloadの形式・許可したフィールドだけであること・actionとtargetKindの対応・UUID・日時を検証し、showNotificationする。不正payloadは詳細リンクを使わず、汎用の「アプリで最新情報をご確認ください」と旅行一覧への固定リンクで表示する。重複eventIdは同じtagを使う。これは厳密な重複配信防止ではない。受信のたびにバックグラウンドで業務APIを読んだり状態を変更したりしない。

タップ先をenumとUUIDから生成する。

- plan：/trips/{tripId}/plans/{targetId}
- achievement／booking／payment：/trips/{tripId}/records?type={kind}&recordId={targetId}
- settlement：/trips/{tripId}/settlements/{targetId}

取消通知は元の記録・精算IDを対象にする。記録一覧APIに任意のrecordId絞り込みを追加し、元記録と取消を取得できるようにする。単に最新ページを開いて過去の記録が見つからない状態を避ける。

notificationclickもevent.waitUntilで保持し、通知を閉じる。既存の同一オリジンウィンドウがあればfocusして遷移し、なければopenWindow。すべての分岐で許可した同一オリジン内のパスに限定する。ログイン期限切れなら再ログイン後に対象を検証する。対象なし・権限なしは説明して旅行一覧へ戻す。

## 10. ログアウト・期限切れ・鍵更新

明示ログアウトでは、認証済みの現在sessionIdについて、利用者行をFOR UPDATEでロックし、closed_push_sessionsへの停止記録と、そのsessionへ紐づく有効購読の無効化を同一トランザクションでCOMMITしてからBetter Authのログアウト処理を行う。購読PUTも同じ利用者行をロックした後に停止記録を確認するため、ログアウト前に認証された遅いPUTでも再登録できない。停止記録はON CONFLICT DO NOTHINGで繰り返せる。無効化が失敗した場合はログアウト完了と表示せず再試行へ。無効化後にログアウト処理が失敗した場合は通知停止済みの状態で再試行できる。

ブラウザのunsubscribeも行う。オフラインではサーバーの通知停止ができないことを示し、通信復帰後に完了させる。別端末の購読を無条件に解除しない。既にセッションが失効して識別できない場合、sign-outの200はCookie消去のみを意味し、サーバーの通知停止完了とは表示しない。ブラウザunsubscribeを試み、失敗した場合は再ログイン後に自分の購読一覧から停止する。新セッションへの登録を強制してから停止する必要はない。

単なるセッション期限切れでは購読を解除しない案。通知は受け取れるが、タップ後の業務データ閲覧には再ログインが必要。利用許可停止は送信先選択でも反映する。

送信中や配信サービスに受け付け済みの通知までは、ログアウト後に取り消せない。新しい配信を止める方針として表示する。

VAPID鍵はデプロイごとに再生成しない。keyIdで管理し、通常の更新は旧鍵を移行期間保持して購読ごとに使い分ける案。秘密鍵漏えい時は旧鍵を停止し、利用者に再登録を案内する。登録時のkeyIdが未知なら409で最新公開鍵の再取得へ進める。

## 11. 実装契約の補足

- notificationは配信の技術モジュールであり、新しい業務境界や業務データの所有者にはしない。UseCaseは成功した新規操作だけを通知ポートへ渡し、購読Repositoryと暗号化・HTTP送信はNestJSのInfrastructureが担う。
- 初期送信設定はaes128gcm、TTL 300秒、urgency normal。配信サービスの保管期限であり、アプリ側の再送ではない。長時間オフラインなら欠落し得る。VAPIDのsubjectは運用者が設定するmailtoまたはHTTPS連絡先。実在する値を実装時に設定し、資料の検証用アドレスを本番に使わない。
- HTTPの3秒期限はDNS・接続・応答の待ちを含めて中断する。DBの宛先取得・失効更新にも有限のstatement/lock timeoutを設定し、例外を回収する。Vercel側の全体期限内に収まる具体的な組み合わせはデプロイ構成で検証する。3xxは追跡せず購読維持・ログ対象とする。
- 設定APIの409はPUSH_ENDPOINT_OWNED_BY_OTHER、PUSH_LIMIT_REACHED、PUSH_KEY_CHANGED、PUSH_SESSION_CLOSED。422はUNSUPPORTED_PUSH_SERVICE、INVALID_PUSH_SUBSCRIPTION。形式・サイズ不正は400。PUT成功200には購読の公開DTOだけを返す。DELETEは自分の対象なし／他人のIDも204として存在を漏らさない。
- 購読PUT・DELETE・ログアウト前処理は同じ利用者行をロックする。別利用者が同一endpointを同時登録する競合はDBのハッシュ一意制約で検出し、トランザクションをロールバック後に409へ変換する。
- recordId指定の記録取得はtype必須、cursor／limit併用不可（400）。planId指定はAND条件。元記録とその取消を最大2件返しnextCursor=null。旅行参加者の認可後、該当なしは200の空配列。精算通知は既存の精算詳細APIを使う。

| targetKind | 許可するaction |
|---|---|
| plan | plan_added / plan_cancelled / plan_moved |
| achievement | achievement_added / achievement_cancelled |
| booking | booking_added / booking_cancelled |
| payment | payment_added / payment_cancelled |
| settlement | settlement_completed / settlement_cancelled |
