# 詳細設計07：4画面の状態・入力・復帰

作成日：2026-09-09
状態：実装前の画面詳細設計。01〜06と既存OpenAPIに合わせた実現案。文言、URL、フォーム初期値、入力保持方法は設計上の選択であり、個々のユーザー承認記録とは区別する。画面実装・実機テストは未実施。

## 1. 範囲と正本

ホーム・しおり・記録・精算と、それらに必要な入力・詳細画面を対象とする。旅行作成／選択・認証・通知設定は接続部分を定義する。配色・完成モックアップ、持ち物・思い出の画面、デプロイ／監視／テスト製品の選定は別の設計で扱う。

業務ルールは合意事項と詳細設計01〜06、送受信のフィールドはOpenAPIを正本とする。本書は既存の成功結果・競合結果をどう表示し、次の操作へつなぐかを定める。ブラウザ側のボタン制御だけで認可や金額を保証しない。

## 2. URLと戻り先

以下は画面URL。APIの/apiとは別。スマートフォンでは4タブを固定し、入力・詳細は幅を使える補助画面とする。主画面の追加タブは作らない。

|---|---|---|
| 旅行一覧 | /trips | listTrips |
| 旅行作成 | /trips/new | 作成はcreateTrip |
| ホーム | /trips/{tripId}/home | getHome |
| しおり | /trips/{tripId}/itinerary?date=YYYY-MM-DD | getItinerary |
| 予定追加 | /trips/{tripId}/plans/new?date=YYYY-MM-DD | getTrip |
| 予定詳細 | /trips/{tripId}/plans/{planId} | getPlan |
| 予定編集 | /trips/{tripId}/plans/{planId}/edit | getPlan |
| 記録 | /trips/{tripId}/records?type=&planId= | listRecords |
| 特定記録 | /trips/{tripId}/records?type={kind}&recordId={recordId} | listRecords（元記録と取消） |
| 支払い追加 | /trips/{tripId}/payments/new?planId= | getTrip、必要ならgetPlan |

| 精算 | /trips/{tripId}/settlements | getBalance、listSettlementPreviews、listSettlements |

空のクエリ値は送らず、未指定としてURLから除去する。画面URLのID／日付／enumを検証してからAPIへ渡す。通知のリンクは06の固定生成規則を維持する。

- 画面上部に選択中の旅行名を表示。タブ切替でtripIdを維持する。
- 戻り先は許可した同一旅行の内部経路と、選択日／フィルター／スクロール位置として保持する。任意の外部returnUrlを受け付けない。
- 通知などで直接開いて戻り先がない場合、予定詳細は予定日のしおり、記録は同種の通常一覧、精算確認／履歴は精算画面へ戻る。
- しおりの日付と記録のフィルターはURLで再現する。追加ページのカーソル・スクロールは現在の画面メモリ内に保持する。再読み込みで全ページの復元は保証しない。
- 未変更フォームはそのまま閉じる。変更済みはアプリ内の戻る／タブ切替で破棄確認。OSによる終了時の確認表示は保証しない。
- 詳細や一覧を開くGETだけで記録・精算確認を作成しない。

## 3. 共通の取得状態

| 状態 | 表示 | 操作 |
|---|---|---|
| 初回読み込み | 対象欄のプレースホルダーと読み込み表示 | 未取得の値を使う更新は不可 |
| 正常・データあり | 最新取得結果 | 条件を満たす操作を表示 |
| 正常・0件 | 画面に対応した空表示 | 追加／条件解除などを案内 |
| 再取得中 | 同じ旅行・同じ条件の前回表示と「更新中」 | 最新性が必要な精算確認は取得後に進む |
| 初回取得失敗 | 「取得できませんでした」 | 明示的な再試行 |
| 再取得失敗 | 前回表示に「更新できていません」と取得時刻 | 再試行。失敗を0件・0円へ変えない |
| 認証切れ | 業務データを隠しログインへの導線 | 再認証後に認可と最新状態を再取得 |
| 403／404 | 対象を開けない旨と旅行一覧への導線 | 他旅行の情報や推測した詳細を表示しない |
| オフライン | 接続できない旨 | 更新不可。オフラインしおりは別途実装した範囲だけ |

前回表示は現在の画面メモリにあるものに限り、APIの汎用永続キャッシュを新設しない。条件や旅行が変わった場合、前のデータを新しい条件の結果として残さない。遅い旧要求は要求ID等で破棄する。

画面表示、手動更新、自分の保存成功、バックグラウンドから表示へ復帰したときに必要なGETを行う。復帰とマウントが重なったGETはまとめる。常時ポーリングはしない。相手の更新が即時に画面へ反映される保証はなく、更新操作ではサーバーで再検証する。

ホームだけは05のsectionごとの失敗を表示できる。他の画面でも別APIで取得する欄は独立して失敗を示すが、1つの失敗したAPIレスポンスから成功部分を捏造しない。

## 4. ホーム

| 領域 | 内容と操作 | 空・失敗時 |
|---|---|---|
| 旅行ヘッダー | 旅行名・期間・状態・切替。手動開始／終了 | 初回旅行取得失敗なら全体を停止 |
| 予定 | 対象日と最大3件、全件表示への導線 | 0件は「この日の予定はまだありません」＋予定追加 |
| 支払い | 「支払いを記録」。関連予定なしで開く | 金額欄の失敗だけでは支払い入力を禁止しない |
| 精算 | 誰から誰へ、金額、対象件数、精算画面へ | 失敗は「精算額を取得できませんでした」。0円にしない |
| 最近の記録 | 最大3件、通常一覧へ | 0件は「記録はまだありません」 |

beforeは「初日の予定」、duringは「今日の予定」。completed／after_datesでschedule.data=nullなら予定抜粋を出さず、しおりへの導線を置く。status=unavailableは失敗、data.items=[]は予定がない日として区別する。

終了前は確認ダイアログに「未精算分があっても、終了後に精算できます」。状態終了後も記録・編集ボタンを一括無効にしない。開始／終了で相手への通知を追加しない。

## 5. しおり・予定詳細

日付選択は旅行期間内。date未指定は日本時間の今日が期間内なら今日、それ以外は初日を初期表示する。明示された期間外日付は勝手に別日へ置換せず「旅行期間外です」と日付選択を表示する。

並び順は04の時刻順・未定末尾・登録日時・ID。ホーム抜粋の未達成優先とは区別する。予定カードには名前、種類、時刻または「時刻未定」、取りやめ・達成・予約の独立した状態を表示する。取りやめ済みも残し、色だけで区別しない。

| 詳細操作 | 条件・表示 | 成功後 |
|---|---|---|
| 編集 | 取りやめ済みも許可。種類はcanChangeKindに従う | 詳細に留まる |
| 日の移動 | 旅行期間から選択 | 詳細に留まり新日付を表示。旧しおりへ戻る場合は旧日を維持し、新日の導線を添える |
| 取りやめ | 未取りやめのみ。確認に名前・日付を表示 | 取りやめ状態。既存記録を残す |
| 達成を記録 | 場所／食べ処／買い物かつ未取りやめ、有効達成なし | 詳細に有効記録を表示 |
| 予約済みを記録 | 食べ処／宿／移動、有効予約なし | 取りやめ済みでも記録可能 |
| 支払いを記録 | 取りやめ状態を問わず可能 | 関連予定を初期選択 |

達成／予約は短い記録操作なので別の確認ダイアログを毎回挟まず、保存中は連打を防ぐ。取りやめ時は「達成・予約・支払いの記録は残ります」。予約記録の追加／取消には「このアプリ上の記録です。実際の予約手続きは行いません」と表示する。

有効な達成／予約がある場合は追加ボタンを状態と記録へのリンクに置き換える。RECORD_ALREADY_ACTIVEなら既存記録へ更新し、再登録を促さない。

## 6. 入力項目と変換

| フォーム | 項目・初期値 | 検証と送信 |
|---|---|---|
| 旅行作成 | 名前、開始日、終了日。日付は未入力 | 名前1〜100文字・空白のみ不可、実在日、開始≦終了。参加者の入力なし |
| 予定追加 | 名前、種類は未選択、日付は選択日、時刻未定、メモ空 | 名前1〜100文字、種類必須、旅行期間内の日付、時刻HH:mm／null、メモ最大2,000文字 |
| 予定編集 | 現在値 | 変更フィールドだけPATCH。時刻・メモの消去はnull。日付は別操作 |
| 日の移動 | 現在日付 | 旅行期間内の実在日。同じ日なら送信不要 |
| 旅行名／期間 | 現在値 | 取りやめ済みを含む予定が新期間外なら拒否される。予定を自動移動しない |
| 支払い | 金額空、支払者は自分、負担は折半、用途空、予定は入口による | 金額1〜999,999,999円、支払者は二人のいずれか、割合合計100、用途任意1〜100文字 |

文字数上限はUnicodeコードポイント数で検証する設計とし、UTF-16の単純なlengthだけで判定しない。名称・用途は前後空白を除去して検証し、メモの改行と内部空白は保持する。空の任意用途はフィールドを省略し、空のメモはnullにする。名称にHTMLを解釈させずテキストとして表示する。

金額は文字列入力と数字キーボードを使い、確定後に円と桁区切りを表示する。全角数字は半角へ変換、前後空白は除去する。小数・負号・指数表記・円記号・カンマ等は黙って数値変換せず理由を示す。先頭0は除去して検証し、0円は拒否する。APIへ桁区切りなしの10進文字列を送る。

負担の分け方は折半／支払者が全額／もう一人が全額／割合指定。割合指定は「自分の負担％」を0〜100の整数で入力し、相手側は100から差し引いて表示する。二人の名前・割合・円額を常に並べる。支払者を変更した場合、割合指定は各人の割合を維持し、全額モードは新しい支払者を基準に再計算する。

支払者以外の負担を支払いごとに切り捨て、残額は支払者へ。表示用計算にもBigIntを使う。保存後はサーバーの確定負担額を表示する。例えば1,001円の折半では支払者501円、相手500円。割合設定を後で変えても保存済みの支払いは変更しない。

関連予定は任意で解除可能。選択UIは旅行内の日付→その日の予定として既存getItineraryを使い、取りやめ状態も表示する。未取得予定を推測して候補にしない。URLから渡したplanIdはgetPlanで同じ旅行への所属を確認し、失敗した場合は勝手に関連なしへ変えて保存せず、再取得または利用者による解除へ進む。

入力エラーは送信前とサーバー応答後の両方で表示する。最初のエラー項目へフォーカスし、入力値を保持する。送信不可のボタンだけを置かず、理由を隣に示す。

## 7. 記録タイムライン・訂正

通常一覧は種類・関連予定で絞り込み、登録日時降順。追加取得失敗は既存カードを残し、末尾で再試行する。条件変更時はカーソルを破棄して最初から取得する。同じID／種類のカードを二重に追加しない。

空表示は未登録なら「記録はまだありません」、フィルター中なら「この条件の記録はありません」＋条件解除。特定recordIdでは元記録と取消だけを表示し、「この記録に絞り込み中」「すべての記録へ」を置く。取得時にtype必須、cursor・limitは送らない。

支払いカード／詳細は用途（未設定なら「支払い」）、金額、支払者、二人の割合と確定負担額、関連予定、登録者・登録時刻、取消状態。達成／予約は種類、元予定、登録者・時刻、取消状態を表示する。取消を元記録の削除で表現しない。

取消ダイアログは対象の名前／金額／時刻を示す。支払いは「取り消すと精算額が変わる場合があります。既に精算した分は次回の調整になります」。過去の送金が返金される表示をしない。

直接編集するボタンは設けない。支払い取消後は「正しい内容で支払いを記録」へ進めるが、取消と新規追加は独立して保存されることを表示する。新規入力を中断しても取消は成立したまま。達成／予約の再登録可否は現在の予定から判断する。

## 8. 精算一覧・確認・履歴

精算画面は現在の受け渡し、対象明細、自分の未完了確認、精算履歴を分ける。独立APIの取得失敗を各欄へ表示し、履歴が失敗しても「履歴なし」と表示しない。

| 残額の状態 | 表示 | 主操作 |
|---|---|---|
| 対象0件 | 「現在、精算する対象はありません」 | 新規確認ボタンなし。過去の未完了確認や履歴は閲覧可 |
| 対象あり・非0円 | 渡す人 → 受け取る人、金額、件数 | 「受け渡しを確認する」 |
| 対象あり・0円 | 「受け渡しは不要です。未処理の対象がN件あります」 | 「受け渡し不要の対象を確認する」 |
| 取得失敗 | 金額不明を明示 | 最新取得を再試行。新規確認へ進めない |

確認作成はボタン操作時のPOSTだけ。明細・金額・作成時刻・確認IDが固定された画面へ遷移する。追加された支払いは次回と表示し、GETや画面復帰で固定金額を書き換えない。未完了確認は自動的に選ばず、日時・方向・金額から本人が選ぶ。

確認画面のGETは表示復帰時にも行う。完了POSTでも再検証されるため、GETの成功を将来の保存保証にしない。

| validation.status | 画面と操作 |
|---|---|
| ready | 非0なら「表示の全額を受け渡しました」の未チェック確認と「受け渡し完了を記録」。0なら「受け渡し不要として精算を記録」 |
| cancelled_items_ack_required | 取消対象を表示。未受け渡しなら最新確認へ。元の非0金額を全額受け渡し済みなら変更明細の了承後に元の確認で記録 |
| target_changed | 元の確認と変更を表示し、通常の完了を停止。再取得・履歴確認へ。新しい確認へ進む前に受け渡し済みかを確認 |
| already_completed | 既存精算へのリンク。もう一度完了ボタンを出さない |
| completed_then_cancelled | 元の完了と取消を表示。元previewは再使用せず、新しい確認への導線 |

非0の完了はcompletionKind=transfer_completed、0はno_transfer_required。通常の了承IDは空配列。取消明細を実際に表示して了承した場合だけ、その全paymentIdを送る。再取得で取消集合が変われば了承チェックを解除する。金額と了承対象をクライアントで追加／変更しない。

0円確認で対象が取消された場合は「既に受け渡した」という例外を使わず、初期UIは最新の対象から再確認する。部分額・追加額の受け渡し入力は設けない。

受け渡し後に対象競合が判明した場合、再送金を促さない。「受け渡しを繰り返さず、精算履歴を確認してください」と元の確認を残す。同じ全対象の既存精算があれば表示する。一部対象の競合などをこのUIで自動解決できない場合、過去の正しい精算を取り消す誘導はせず、未記録の事実を確認して個別に対応する（初期版の機能限界）。

成功後は「今回の精算を記録しました」と履歴リンク。残額の再取得が失敗しても成功を撤回せず、残額は未確認と表示する。新規支払いがある場合は残りを表示し、「すべて精算済み」と断定しない。

履歴詳細の取消はサーバーの取消可能性に従い最新の有効な精算のみ。確認に方向・金額・日時と「実際の返金は行いません」。SETTLEMENT_NOT_LATESTなら履歴を更新し、古い精算を消すために新しい正しい精算を取り消す案内はしない。

## 9. 保存状態と再送

| 状態 | 動作 |
|---|---|
| 編集中 | 入力可能。未送信の下書きは自動永続保存しない |
| 送信中 | 同じ操作の再押下を停止。「保存中」。成功前に一覧・金額を確定表示しない |
| 成功 | 成功レスポンスを表示し、関連GETを更新。通知の成否を成功判定に使わない |
| 入力・業務条件の拒否 | 入力を保持して該当箇所や既存記録を表示 |
| 結果不明 | 「保存されたか確認できません」。入力の変更と新規キーでの再登録を止め、同じ要求の再試行へ |

POST/PATCH等の業務書き込みは、送信する直前にoperation・tripId・resourceId・body・If-Match・Idempotency-Keyを1組として確定する。同じ結果を確かめる再送では、同じ利用者で同じキー・本文・If-Matchを送る。認証やOriginヘッダーの古い値は保持せず、再送時の環境を使う。

入力や了承IDを変更した場合は別の要求になる。元要求が未確定なら先に同じ要求で結果を確かめる。明確にロールバックした入力エラー等を修正した後は新しいキーを使う。IDEMPOTENCY_KEY_REUSEDを単に新しいキーへ変えて自動再送しない。

通信切断・タイムアウト・解釈できない5xxは保存失敗と断定できない。クライアントの中断操作もサーバーのロールバックを意味しない。精算確認IDの完了状態GETは補助として使えるが、一般の一覧に見当たらないことだけでは未保存を証明できない。

### 再読み込み・再ログインへの引き継ぎ

送信済み要求の結果確認用に限り、IndexedDBへ上記の要求組とuserId・作成時刻を送信前に保存する案。未送信の編集内容や画面一覧、Cookie・セッショントークン・Google情報は保存しない。これはオフライン追加／同期キューではなく、オンラインで送信した操作の復帰情報である。

- 同じ操作フォームに未確定要求があれば、先に結果確認を表示する。無関係な旅行・操作を一律停止しない。
- 復帰時は認証とuserId一致を確認してから内容を表示し、本人の再試行操作で送る。自動バックグラウンド送信は行わない。
- 成功／確定した拒否を得たら削除。認証期限切れでは要求を保持し、同じアカウントの再ログイン後に確認する。別アカウントへ要求内容を表示しない。
- 明示ログアウトでは03の方針どおりローカル情報も削除する。未確定要求がある場合は、結果確認情報が消えることと「先に結果を確認する」導線を示す。ログアウトの選択自体は妨げない。
- IndexedDB書き込みが失敗した場合はサーバーへ送る前に停止し、端末の保存領域を利用できない旨を表示する。リロードを跨ぐ重複防止を保証したまま、黙ってメモリのみへ切り替えない。
- OS／利用者のデータ消去・別端末への移動まで復帰を保証しない。要求を失った場合、精算はサーバーの未完了確認／履歴から確認する。支払い等は記録を確認し、同額の既存記録を推測で同一操作と決めない。

同じキーの成功再送は過去時点のDTOの場合がある。成功を確認した後に別GETで現在状態を取得し、後日の取消や相手の編集を上書きしない。

## 10. 競合・エラーの表示

| エラー | 次の動作 |
|---|---|
| VERSION_CONFLICT | 入力を残して最新の予定／旅行を別表示。差分を確認し、本人が修正して新しいETag・キーで保存。自動上書きなし |
| IF_MATCH_REQUIRED／428 | 「画面を更新してからやり直してください」。入力を保持し対象GET。実装不備として記録 |
| PLAN_HAS_RECORD_HISTORY | 種類変更不可の理由。その他の編集は残し、新しい予定の作成を案内 |
| PLAN_CANCELLED／PLAN_KIND_NOT_SUPPORTED | 現在の予定状態を取得し、追加可能な操作へ更新 |
| PLAN_OUTSIDE_TRIP_PERIOD | 日付／期間欄へエラー。旅行期間を再取得 |
| CANCELLED_ITEMS_ACK_REQUIRED | 確認GETを更新し、取消集合に対する了承を取り直す |
| PREVIEW_CHANGED／TARGET_PARTIALLY_SETTLED | 完了を止めて対象と履歴を確認。再送金の指示を出さない |
| TARGET_ALREADY_SETTLED | 同じ対象の既存精算を表示 |
| SETTLEMENT_NOT_LATEST | 履歴を更新し取消不可の理由を表示 |
| 401 | 再認証後に対象の認可と状態を確認。保存要求の無言再送なし |
| 403／404 | 開けない旨。新しいキーでの回避を試みない |
| 503・通信失敗 | GETは再試行。書き込みは確定拒否か結果不明かを分け、未確定なら同じ要求で確認 |

業務エラー名をそのまま利用者向け文面にせず、日本語の理由と実行できる操作を表示する。サーバーのSQLやスタック情報は画面に出さない。

## 11. 更新範囲と操作性

| 保存したもの | 再取得する主な表示 |
|---|---|
| 予定追加／編集／移動／取消 | 対象予定、旧日・新日のしおり、ホーム。記録画面を表示する際は関連予定名も更新 |
| 達成／予約追加・取消 | 対象予定、しおり、記録、ホーム |
| 支払い追加・取消 | 支払い／記録、現在残額、ホーム。開いている精算確認のvalidationを再取得し、固定明細は維持 |
| 精算完了・取消 | 残額、確認一覧と対象確認、履歴、ホーム |
| 旅行名・期間・状態 | 旅行一覧、旅行、ホーム、しおりの日付選択 |

その場で表示している画面を再取得し、非表示画面は古い状態として印を付け次の表示時に取得する。全画面へ無条件に同時GETを投げない。入力中に再取得が発生しても入力欄を受信値で置き換えない。

各入力に可視ラベル、エラーとの関連付け、必須表示を設ける。完了／失敗は読み上げ領域でも通知する。ダイアログはフォーカスを内部へ移し、閉じたら起点へ戻す。取りやめやエラーは色だけに依存しない。スマートフォンのキーボードで保存ボタンが完全に隠れないようスクロール可能にする。

端末幅・文字拡大・キーボード・戻る／復帰・VoiceOver／TalkBackの実動作は実装後に検証する。本書だけでアクセシビリティ適合やiPhone／Androidでの成功を主張しない。
