# 詳細設計09：テスト・監視・CI

作成・公式情報確認日：2026-09-10
状態：実装前の選定・検証方針。アプリのテストコード、CI設定、ログ基盤を今回実装したものではない。製品・閾値は詳細設計上の選択であり、ユーザーの個別承認記録とは区別する。

## 1. 選定するツール

| 用途 | 初期選定 | 適用範囲 |
|---|---|---|
| 単体・統合テスト実行 | Vitest | webとapiで設定を分離し、ランナーは共通化 |
| Reactの操作・表示 | React Testing Library＋user-event＋jsdom | Client Componentのフォーム、エラー、状態表示 |
| NestJSのテスト起動 | @nestjs/testing | 実際のModule／DI構成を組み立てる |
| HTTP API検証 | Supertest | 実NestJSへHTTP要求。認証・入力・レスポンス・ヘッダー |
| 実PostgreSQL | TestcontainersのPostgreSQLモジュール | マイグレーション、行ロック、制約、ロール権限 |
| ブラウザE2E | Playwright | Next＋Nest＋検証DBを通した主要な操作 |
| OpenAPI形式検証 | @apidevtools/swagger-parser | 既存の検証方式を継続。実装レスポンスとの一致は別途確認 |
| CI | GitHub Actions | 標準Linux runnerで検査・ビルド・テスト |
| アプリログ | Pino | 許可した項目だけをJSONで標準出力 |
| 運用状況の確認 | Vercel Runtime Logs／Usage、Neon Console | エラー・実行時間・DB利用量を管理者が確認 |

NestJSの現行公式資料はVitest／Supertestの組合せと、テストランナーに依存しないテスト用Moduleを案内している。古いJestのサンプルを混在させず、採用するNest majorに対応したtransform・ESM・decorator metadataの設定をM0で確認する。[NestJS Testing](https://docs.nestjs.com/fundamentals/testing)

Next.jsの公式資料ではVitest＋React Testing Libraryが案内されている。ただしasync Server Componentは単体テストの対象として無理にmock化せず、実サーバーを起動するPlaywrightで確認する。[Next.js Vitest](https://nextjs.org/docs/app/guides/testing/vitest)、[React Testing Library](https://testing-library.com/docs/react-testing-library/intro/)

Testcontainersはテスト用PostgreSQLを起動・破棄する。実行にはDocker等の対応実行環境が必要であり、起動できない場合にPGliteへ自動置換して合格にしない。[Testcontainers PostgreSQL](https://node.testcontainers.org/modules/postgresql/)

初期はJestの併用、MSW、Testcontainersとは別のCI用常設DB、Sentry／Datadog、ログ転送サービスを追加しない。HTTP障害の画面再現にはPlaywrightのルート制御、単体テストにはポート境界のfakeを使う。ライブラリの正確なバージョンはM0でNode 22.xとの互換性を確認してlockfileに固定し、未検証のlatestを本番へ自動導入しない。

## 2. テストの分担

| 層 | 重点 | 置き換えてよいもの／いけないもの |
|---|---|---|
| 純粋な業務計算 | 端数・割合・符号・対象導出・取消順序 | DBなし。期待値は実装関数の再呼出しで作らない |
| UseCase | 業務条件、成功／拒否、通知をCOMMIT後だけに行うこと | 外部通知等はfake可。排他の保証はここだけで済ませない |
| DB統合 | 同じクライアントのtransaction、FK・CHECK・履歴保護・GRANT・競合 | 本番と同majorの実PostgreSQLと実migration。Repositoryは実装を使う |
| API統合 | 認証・認可・Origin・ETag・再送・入力とDTO | Google／Push外部通信を隔離。認証Guardを一律無効にしない |
| コンポーネント | 入力保持、可否理由、読み上げ、空／取得失敗 | 必要な取得ポートのfake可。大きいsnapshotの一致だけを合格条件にしない |
| E2E | 画面→API→DBの保存、戻る、再読込、二人操作 | 本体APIの成功を全件mockしない。例外の表示だけを試すケースは別ラベルにする |
| 実環境・実機 | Google callback、rewrite、Neon pooled接続、Web Push、復元 | CIの代用不可。08のOPSチェックを実行 |

PGliteや既存finance_model_check.pyは設計の検算資料として保持する。本番コードが同じ保証を持つことや、Neonの複数接続で安全なことの証明とはしない。

## 4. 競合テストを成立させる条件

二つの独立したDB接続を使用し、backend PIDが異なることを確認する。同じtransaction内のPromise.allを同時利用者の再現としない。テスト用barrierで先行処理のロック獲得後に後続処理を開始し、任意のsleepだけに順序を任せない。

先行COMMITと先行ROLLBACKの両方を試し、後続結果と全表の整合性を確認する。金融と予定の別旅行同時操作が不要に全体停止しないことも確認する。競合待ちにはテスト自体の上限時間を設け、ハングを合格にしない。

fixtureの初期化は管理ロール、検証対象の操作はapp_runtime。テスト全体を1つの外側transactionで包むと独立接続から見えなくなるため、隔離DBの再作成／明示的なresetを使う。履歴保護を外した状態でテスト対象を書き換えない。管理resetはテスト用DBにだけ許可する。

空DBから全migration適用に加え、直前版schema＋検証データからの更新を試す。Better Auth標準表、custom trigger／VIEW、GRANTを含める。SQLの構文確認だけで移行成功としない。

## 5. 認証・外部通信の扱い

通常CIはGoogleへ実ログインせず、許可二人と第三者を検証DBへseedし、採用Better Authのテスト専用fixtureから正規の署名Cookie／DB sessionを作る。テスト用session発行処理はテストプロセス側に置き、本番のログイン裏口や環境変数だけで有効になる公開ルートにしない。

Cookie署名、DB session失効、利用許可、旅行参加者、Originは実処理を通す。Google state／callbackの実統合は固定結合検証環境で別途実施する。テスト用Cookieが通ったことをGoogle OAuthの成功と報告しない。

PushはCIでは送らず、暗号化要求生成・HTTP transportの失敗・中断をfake／ローカルテストサーバーで検証。テスト専用transportは本番のendpoint許可条件を緩めず、依存注入で分離する。response消失のE2EはAPIへ要求を通してCOMMITを確認した後、ブラウザへの応答だけを破棄する。APIへ一度も到達しないmock失敗とは区別する。

## 6. CIの実行内容

| ジョブ | 内容 | 初期時間上限案 |
|---|---|---|
| quality | 依存固定インストール、型検査、ESLint、OpenAPI形式、単体／コンポーネント | 10分 |
| api-db | Testcontainers、全migration、API・DB・競合・ロール検証 | 15分 |
| build | web／apiの本番build。実環境の秘密情報なし | 10分 |
| e2e | 成功したbuildを起動し、主要フローを実API／DBで確認 | 20分 |

quality／api-db／buildは独立可能。e2eはそれらの成功後に起動する。実装が未到達のジョブを空のテストで成功扱いにせず、段階ごとに有効化し、公開時は必要ジョブを全て通す。

PRとmain更新で実行、同じPRの古い実行はキャンセルして消費を抑える。本番リリース・migrationは08の管理者手動手順とし、CIのキャンセル対象に含めない。[GitHub Actions concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

初期は各ジョブのworkerを小さくし、DB競合ケースは専用suiteを直列に実行。PRはChromiumで主要E2E、main／公開前はChromium＋WebKitで同じ重要フローを確認する。モバイルviewportとタッチ設定も使うが、iPhoneのホーム画面PWA／Androidの通知受信の代わりではない。[Playwright CI](https://playwright.dev/docs/ci-intro)、[Emulation](https://playwright.dev/docs/emulation)

CIの自動リトライは初期0回。調査目的で再実行して成功しても初回失敗を記録し、不安定な金銭・認証テストを無視して公開しない。Playwrightのretry設定とflaky分類を使う場合は後で明示的に方針変更する。[Playwright retries](https://playwright.dev/docs/test-retries)

失敗時だけtrace／スクリーンショット／必要ログをartifactに残し、保持3日を初期値にする。合計50MBを目安に上限を設け、大量動画は保存しない。storageStateやCookie、OAuth応答、実データはartifactから除外する。架空の認証情報を含むtraceにもアクセス制限が必要。

workflow権限は原則contents:read、外部actionは検証したcommit SHAで固定する案。forkのコードへsecretsを渡す運用や、pull_request_targetで未信頼コードを実行する構成は採用しない。予算設定は08に従う。

## 7. 合格条件と既存チェックの関係

T-01〜18の実装済み対象が成功し、金額・履歴・認証の既知の重大不具合がないことを公開条件にする。カバレッジは測るが、全体80％のような数字だけを合格条件にしない。重要分岐の不足をレビューで確認し、見た目だけの変更に無関係なテストを量産しない。

画面受入シナリオUI-01〜32は維持。入力・状態表示は単体／コンポーネントで広く確認し、UI-16〜28を含む精算・競合・復帰はE2EとDB状態の照合を優先する。全32件を全部のブラウザでPRごとに重複実行する必要はないが、公開前に未確認の項目を残した場合は理由・代替根拠を明記する。

OPS-01〜18は08の実環境・公開チェック。TやCIの成功で自動的に合格へ置き換えない。認証・金銭整合性・環境分離・復元の未確認は公開前に解消する。

## 8. 監視とログ

初期はVercel Runtime LogsとUsage、Neon Consoleを監視の確認先とし、PinoでアプリのJSONログを整える。Pinoは収集／保存サービスではない。Nestのlogger adapterから使用し、request／responseオブジェクト全体をそのまま出さない。

許可する項目：時刻、level、requestId、operation、HTTP status、durationMs、errorCode、release SHA、通知用eventId／subscriptionIdなど必要最小限の不透明ID。requestIdはサーバー側で生成し、過大／不正な外部値をそのまま信用しない。エラー応答には照会用requestIdをヘッダーで返す案とし、本文の既存OpenAPIを破壊しない。

出さない項目：Cookie、Authorization、Google code／token／sub、DB URL、SQLパラメーター、body全体、氏名、メモ、金額、通知endpoint／鍵、キーを含む例外文字列。ログschemaのallowlistに加えてPinoのredactを防御として使う。例外のmessage／stackに秘密が含まれ得るため、既知の安全なcodeへ整形する。[Pino redaction](https://github.com/pinojs/pino/blob/main/docs/redaction.md)

| 観測するもの | 判断・対応 |
|---|---|
| 保存処理5xx／timeout、DB pool待ち | 利用者の結果不明を優先確認。同じ要求の再試行を案内し、新規送金を促さない |
| 金額・履歴・占有の不整合 | 一件でも更新停止と調査。自動修正や履歴削除をしない |
| 401／403 | 期限切れと未許可を区別。単発を直ちに障害扱いしない |
| VERSION_CONFLICT等の409 | 正常に起こり得る業務結果。全てをerrorログにしない |
| 通知404／410 | 06のrevision条件付き停止。配信成功率を端末到達率と呼ばない |
| VAPID設定不正の401／403 | 通知設定を確認。業務保存は維持 |
| 使用枠70％／90％ | 08の調査／検証縮小。自動課金しない |

Vercel HobbyのRuntime Logsは公式掲載で保持1時間。週1回の確認では過去エラーを遡れない。利用時に問題が出たら早めにrequestIdと発生時刻を控え、必要な安全化済みログを管理者が保全する。長期傾向の分析・常時の障害検知はこの初期構成では提供しない。[Vercel Runtime Logs](https://vercel.com/docs/logs/runtime)

Pinoの制御対象はアプリが出すログ。Vercel等が独自に記録するURL／メタデータまで同じredactが効くとは扱わず、Google callback等の管理画面ログを公開前に点検する。ログ共有は管理者に限定する。

ブラウザ内だけで起きる例外はサーバーのログへ自動収集されない。初期は画面のエラー表示と手動再現・実機検証で確認する。ブラウザ例外の遠隔収集や1時間超の保持が必要になった時点で、Sentry等の無料枠・データ除去・超過停止を再評価する。今回は導入・アカウント作成を行わない。

## 9. 検証状態

製品の公式資料と既存設計の対象・公開条件を照合した。新しいアプリテストやCIを実行したわけではない。VitestのNest metadata、Better Auth fixture、Testcontainers、Playwright、Pinoは実装初期に互換性を確認する。検証結果の記録は実行済み／未実行を分ける。
