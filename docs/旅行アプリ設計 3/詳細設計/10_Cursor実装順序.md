## 1. 引き継ぐ範囲

二人限定のGoogleログイン、旅行・ホーム・しおり・記録・精算、Web Pushを初期リリース対象とする。既存の基本設計と詳細設計01〜09を維持する。持ち物・思い出の業務領域は削除された扱いにせず、今回の4画面に暗黙に実装範囲を増やさない。オフラインしおり、海外通貨、第三者デモは後続。

資料は参照仕様。sql/00は最小検証用、Better Auth標準表は未生成、各OpenAPIはまだ分割されている。参照SQLをそのまま本番migrationとして実行しない。検算スクリプトをアプリの実装へコピーしただけで完了としない。

テストとログは各機能と同時に追加する。全実装が終わるまで待ってからまとめて付けない。M3を先に十分確認するのは金銭記録の整合性がUIの土台になるため。M2時点でも達成／予約履歴が存在し得るschemaと種類変更条件を用意し、M4で検証を完成させる。

M6の公開経路に不確実性があるため、M1の後に小さな結合検証を前倒ししてよい。その場合も本番データ・課金サービスを使わず、未完成機能を一般公開しない。前倒しした接続検証とM6全体の合格を区別する。

## 3. 最初に決める実装上の細部

| 項目 | 初期方針 |
|---|---|
| フレームワーク／依存の版 | 対応Node 22.xと相互依存を確認し固定。未検証の版番号は資料だけで断定しない |
| 入力検証の実装ライブラリ | M0〜M1で既存OpenAPIとの対応を確認して選定。Zod等を採る場合もDBの制約の代替にしない |
| フォーム／取得状態のライブラリ | M2の1画面で必要性を確認して選定。単に資料に名前がないため機能設計を再開しない |
| OpenAPIの統合 | 重複GET tripを一つに統合。既存JSONを根拠に生成結果との差分を確認。schemaだけで業務意味の一致を保証しない |
| 本番migration／GRANT | 認証生成表と全領域を統合し、空DBと直前版から検証 |
| 品質の記録 | T／UI／OPSのIDをPRや検証結果へ紐付ける |

この表は通常の実装判断をCursorへ委ねる範囲。フレームワークやDBの全面変更、二人制限の解除、精算ルールの変更、有料化は別の方針決定として扱う。

## 4. 各段階で提出するもの

- 変更した機能と、利用者から見た動作。
- 対応設計とT／UI／OPSのID。
- 実行した検証と結果、未検証の範囲。
- migration／設定変更の有無と、前の版との互換性。
- 次段階に必要なもの。設計矛盾は場所と影響を示し、都合のよい規則へ無言で変更しない。

一度にアプリ全体を生成してレビューするのではなく、上の段階を動作する単位で区切る。変更と関係のない機能や依存をついでに追加しない。

## 5. Cursorへ最初に渡す依頼文

このフォルダのCursor引き継ぎ.mdと詳細設計01〜11とM-1の決定内容を読み、旅行Webアプリの実装をM0から開始してください。対象リポジトリのAGENTS.mdと既存コードを先に確認し、設計資料の業務ルールを維持してください。まずNext.js・NestJS・TypeScriptの基盤、Node 22.xでの依存互換性、VitestとTestcontainersによる検証環境、CIの骨組みを作成してください。sql/00_validation_prerequisites.sqlは本番migrationではありません。既存の検算成功を実アプリの検証成功とは扱わないでください。実施結果・変更内容・未検証事項を報告し、その後にM1へ進める状態を整えてください。外部サービスの公開、本番データ操作、有料プランへの変更は、この最初の依頼には含みません。
