## 実施条件

許可された二人A・B、予定期間3日以上の旅行、未終了／終了旅行を検証用に用意する。AとBは異なるブラウザセッションを使う。金額や氏名は検証用とし、実送金は行わずテスト上の完了操作で確認する。通信の遅延・応答消失は検証環境で制御する。

主要な画面操作はiPhoneとAndroidで行う。通知の受信は06の別の実機確認も必要。自動テスト・手動確認の担当分けと採用ツールは後続のテスト設計で決める。

## 通常表示と入力

| ID | 条件・操作 | 期待結果 |
|---|---|---|
| UI-01 | 前回旅行を保持して起動、次にアクセス不可のIDで起動 | 有効ならホーム、不可なら情報を漏らさず旅行一覧。保存IDだけで認可しない |
| UI-02 | 期間前／期間内／終了後のホームを表示 | 初日／今日／終了後の表示を区別。日付だけで旅行状態を変更しない |
| UI-03 | ホームの予定0件、予定section=null、section失敗をそれぞれ返す | 空表示・予定抜粋なし・取得失敗を別表示。残額失敗を0円にしない |
| UI-04 | しおりで23:59と時刻未定の予定を追加 | 時刻順で未定末尾。未定を00:00として表示・保存しない |
| UI-05 | 予定フォームに空白のみの名前、期間外日、上限超のメモ | 対象項目に理由を表示し入力保持。修正して保存可能 |
| UI-06 | メモ／時刻を消去して編集、日付を移動 | 消去はnull、PATCHへ日付を混ぜない。移動後の詳細と戻り先の日付が一致する設計どおりに動く |
| UI-07 | 達成履歴を取消後に種類変更を試す。別予定には支払い履歴だけを作る | 達成履歴ありは変更不可、支払いだけなら変更可 |
| UI-08 | 取りやめ済み食べ処の詳細を開く | 達成追加不可。予約記録・支払い可能。既存達成を自動取消しない |

| UI-10 | 金額に全角数字、0、小数、指数表記を入力 | 全角数字だけ半角へ正規化。0・小数・指数表記は拒否。桁区切りなし整数文字列で送信 |
| UI-11 | Aが1,001円の折半を2件支払い、さらに割合70:30の入力を試す | 各件A501円／B500円。2件のB→Aは1,000円。割合変更で既存支払いを再計算しない |
| UI-12 | 支払者を変更し、全額モードと割合指定を比較 | 全額モードは新支払者に追随、割合指定は各人の割合を維持。負担和が支払額と一致 |
| UI-13 | 記録のフィルター変更中に古いGETが遅れて返る | 新しい条件へ古い結果を混ぜない。追加取得失敗は既存カードを維持 |
| UI-14 | 取消された古い記録を通知URLのrecordIdで開く | 元記録と取消を表示。最新ページにないために見失わない。通常一覧への導線あり |
| UI-15 | 支払いを取消後、入れ直しフォームを中断 | 取消は残る。直接編集や取消の巻き戻しは発生しない |

## 精算と同時操作

| ID | 条件・操作 | 期待結果 |
|---|---|---|

| UI-19 | 取消了承後、完了前に別の対象も取消 | 了承集合が一致せず再確認。新しい取消を自動了承しない |

| UI-21 | 最新有効精算と古い精算を開き、表示後にも相手が精算 | 最新のみ取消操作。競合時は履歴更新し、正しい新しい精算を取消す案内をしない |
| UI-22 | 保存成功後に残額GETだけ失敗 | 今回の保存成功を維持し、残額は未確認と表示。再送・二重記録なし |
| UI-23 | 旅行を終了し、支払い・訂正・精算を行う | 既存制約内で操作可能。未精算の自動消去、終了取消UIなし |
