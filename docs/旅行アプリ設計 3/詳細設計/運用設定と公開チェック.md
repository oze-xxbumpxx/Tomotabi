## 1. 環境変数の配置

名前はアプリ設定の設計案。Better AuthやVercelがすべて自動認識する名前ではないため、実装で設定オブジェクトへ明示的に渡す。秘密情報の実値をこの表やGitへ記入しない。

| 設定名 | 配置 | 秘密 | 内容と検証 |
|---|---|---|---|
| APP_ENV | web／api | いいえ | local／staging／production。Vercel環境区分と区別 |
| PUBLIC_APP_ORIGIN | web／api | いいえ | 固定HTTPS origin。localだけlocalhostの開発URL |
| API_ORIGIN | webのみ | いいえ | 対応環境の固定API origin。rewriteに使用 |
| DATABASE_URL | apiのみ | はい | app_runtime、Neon pooled接続、TLS。test／productionを分離 |
| MIGRATION_DATABASE_URL | 管理者端末のみ | はい | migratorのdirect接続。web／api／通常CIに配布しない |
| BACKUP_DATABASE_URL | 管理者端末のみ | はい | 全対象をdumpできる管理用direct接続。runtimeと分離 |
| BETTER_AUTH_SECRET | apiのみ | はい | 環境ごとに生成した十分な乱数。安定して保持 |
| GOOGLE_CLIENT_ID | apiのみ | いいえ | 環境ごとのOAuth client |
| GOOGLE_CLIENT_SECRET | apiのみ | はい | OAuth secret。本番と開発で共有しない |
| VAPID_KEY_ID | apiのみ | いいえ | 使用中の鍵識別子。06の登録契約と一致 |
| VAPID_PUBLIC_KEY | apiのみ・公開鍵APIから配布 | いいえ | 対応するP-256公開鍵 |
| VAPID_PRIVATE_KEY | apiのみ | はい | 公開鍵と対になる秘密鍵。毎回生成しない |
| VAPID_SUBJECT | apiのみ | いいえ | 管理者の連絡先mailto／HTTPS。検証用仮値を本番にしない |
| PUSH_ENABLED | apiのみ | いいえ | 本番は実機検証後にtrue。通常の検証・復元環境はfalse |
| APP_MAINTENANCE_MODE | api／web | いいえ | 通常／更新停止等の実装設定。DB管理による停止の代替ではない |
| RELEASE_SHA | web／api | いいえ | 公開commit。ログに版の識別として使う |

APP_MAINTENANCE_MODEは環境変数変更だけで旧deploymentへ即時反映されるとは扱わない。完全停止には08のDB接続／権限管理を含める。新規サインインとOAuth callback、ログアウト、閲覧、業務書き込み、通知のどこを止めるかを区別する。通常メンテナンスではログアウトを可能にし、復元中の完全遮断ではサーバー失効未完了の表示を維持する。

認証baseURL=PUBLIC_APP_ORIGIN、basePath=/api/auth、trustedOrigins=[PUBLIC_APP_ORIGIN]を設定する。NEXT_PUBLIC_*へ秘密値を移さない。PR PreviewではAPI_ORIGIN等を本番へフォールバックさせず、外部API接続のない画面確認モードを明示する。

将来VAPID複数鍵の移行を実装する際は、現在鍵だけの表からkeyId→鍵組の設定へ拡張し、旧購読との対応を確認する。今回は単一の初期鍵を前提とする。

## 2. 管理画面で記録するもの

実値の秘密を含めず、次の管理情報を別の管理者用台帳へ記録する。

- 本番／結合検証それぞれのweb・apiプロジェクトID、固定URL、Gitのroot directory。
- NeonプロジェクトID、branch ID、DB名、PostgreSQL major、リージョン、プラン名。
- Node major、lockfile、web/apiのcommit、適用済みmigration ID。
- OAuth clientの環境対応、登録redirect URI。secret本体は台帳へ書かない。
- 二人の初期登録の完了有無。Google subや個人情報は公開資料へ掲載しない。
- 最終dump日時、復元確認日時、暗号化保存先の管理参照、次回確認日。

PostgreSQL majorはNeonで作成したものとlocal／CIを揃え、pg_dumpはサーバーと互換性のあるバージョンを使用する。DBダンプにはクラスタのロール設定等が全て入るとは限らないため、migrator／app_runtimeの作成とGRANTをマイグレーション／管理手順として別管理する。

## 5. 障害時に最初に残す情報

発生時刻、画面操作、requestId、保存成功／結果不明の区分、web/apiの版、サービスの障害情報、DBの最新復元可能時点を記録する。支払い・受け渡しの事実とアプリ上の記録を区別する。認証トークンや通知endpointをスクリーンショットや共有issueへ貼らない。

通知のみの失敗、アプリの不具合、DBのデータ損失を切り分ける。通知だけの失敗で業務データを復元せず、結果不明の送金を再実行しない。二人への連絡が必要な場合は管理者が行い、設計作業中に自動送信する設定は作成しない。
