## 調査範囲と読み方

日本のWebプロダクト企業への転職を想定し、大手・成長企業・スタートアップの企業公式求人（企業が掲載するHRMOS・HERP・Greenhouseを含む）と公式エンジニア採用サイトを確認した。下表は8社の採用ページから得た定性的な比較であり、求人件数・シェア・年収の統計ではない。大手SIer、組み込み、データサイエンス、海外市場の網羅調査は含まない。

ユーザーはReact、Node.js、TypeScriptの経験があり、Web系エンジニアを志望する。将来はアーキテクチャ設計、バックエンド、インフラを見られるテックリードを目指す。この経験と目標を選定の前提とする。実務年数とインフラ経験の程度は未確認。使用技術の掲載と、その技術の実務経験が応募条件になっていることを区別する。確認日は求人の掲載・更新日を意味しない。

## 分析

### 言語だけで選ばない

このサンプルでは、JVM系、Go系、TypeScript系それぞれに採用上の接点がある。Java / Kotlin + Spring Bootは大手とベンチャーの双方に具体例があり、「モダンな技術を扱いたい」という希望と両立する。RubyやPythonも公式採用ページに掲載されており、企業・プロダクト・職種を絞らず一つの言語が優位だとは結論できない。

LINEヤフー、マネーフォワードケッサイ、HERPなどの求人には、設計・テスト・運用や業務理解が明示されている。したがって、この旅行アプリでは使用技術名に加え、整合性、訂正、認可、障害時の扱いを説明できる成果物にすることを推奨する。この推奨は求人記載からの分析であり、採用結果の保証ではない。

### 三つの候補

| 候補 | 優先する条件 | 旅行アプリで示せること | 学習・実装上の代償 |
|---|---|---|---|
| Kotlin + Spring Boot | 大手のJava / Kotlin系とベンチャーの双方を視野に入れる | 型による業務ルール、文脈の分離、トランザクションと認証・認可 | Kotlinに加えJVM・Springの理解が必要。Javaを読む力も身につける |
| Go | Goを使うプロダクト企業のバックエンドが主な志望先 | API・SQL・トランザクション・パッケージ境界を自分で設計する力 | ライブラリ選定とアプリ構造を明示的に決める必要。Goの個人開発は他言語の必須実務経験を代替しない |
| TypeScript + NestJS | フルスタック志向、またはTypeScriptの既存経験を活かしたい | フロント・APIを通した実装、モジュール構成、境界とテスト | 型の共有だけでAPI入力の検証やDB整合性は保証されない。JVM特化の求人には別の学習が要る |

KotlinはJavaの技術基盤と相互運用でき、Springによるバックエンド開発を公式に案内している。[Kotlin公式](https://kotlinlang.org/docs/server-overview.html)

NestJSは機能単位のモジュールと、公開する依存の制御を提供する。今回の5文脈を表現する候補になるが、フレームワークのモジュールだけでドメインの分離が自動的に守られるわけではない。[NestJS公式](https://docs.nestjs.com/modules)

## ユーザーの経験と目標を踏まえた推奨構成

第一候補は TypeScript + NestJS とする。React・Node.js・TypeScriptの既存経験を活かし、新しい学習を業務のモデル化、DB整合性、テスト、クラウド運用へ集中できると判断する。NestJSの採用例としてOPTEMOとレバレジーズの求人があり、Node.jsを使ってバックエンドやリード職を目指す経路は確認できる。ただし、市場全体で最も求人数が多いという結論ではない。

Kotlin + Spring Bootは、JVM系の企業を主な志望先とする場合の有力な代替案として残す。Goも、志望求人がGo中心になった時点で優先順位を上げる。

| 領域 | 候補 | 選定理由 |
|---|---|---|
| バックエンド | TypeScript + NestJS（Node.js） | 既存経験を活かし、5文脈の分離と業務ロジック・認可・テストの設計を深める |
| フロントエンド | Next.js（App Router）+ React + TypeScript | React経験を活かし、ユーザーの希望するフレームワーク学習を含める。Next.jsは複数の確認先に掲載 |
| フロントの構成 | Next.jsを第一候補とし、従来のVite構成案を置き換える提案 | 学習対象はルーティング・レイアウト・Server / Client Components・データ取得。業務処理はNestJSに置き、RESTの方針を維持 |
| DB | PostgreSQL | 支払い・精算に必要なトランザクション、制約、SQLの設計を示す。市場シェアでMySQLより優位と判断したわけではない |
| API | REST + OpenAPI | 既存ADRを維持。クライアントとの契約と変更管理を示す |
| 環境・配信 | Docker + GitHub Actions | 環境の再現とテスト・デプロイの自動化を成果物として示す |
| 本番ホスティング | Vercel Hobby + Neon Free（採用済み） | 月額0円の制約を優先。AWSは別段階の学習候補 |
| インフラのコード管理 | Terraformは別段階の学習候補 | 本番必須ではない。AWS等の検証環境に取り組む場合に再検討 |

ユーザーのフレームワーク学習の希望を受け、Next.jsを第一候補へ変更した。App Router、Server / Client Components、データ取得・更新後の表示を学習する。精算等の業務処理はNestJSに置く構成とする。[Next.js公式](https://nextjs.org/docs/app)

PostgreSQLのトランザクションを利用しても、精算の二重実行を自動的に防げるわけではない。対象の確定、制約、同時操作の扱いは詳細設計で定める。[PostgreSQL公式](https://www.postgresql.org/docs/current/tutorial-transactions.html)

## ポートフォリオで優先する証拠

以下はこのアプリに合わせた提案であり、追加の大規模システムを作る要件ではない。

1. 5文脈に分けた理由と、一方向の問い合わせをコードでどう守ったか。
2. 精算の二重計上を防ぐ設計と、同時実行・取り消しを扱うテスト。
3. Googleの本人確認、二人限定の利用許可、旅行参加者の認可の責務分担。
4. 通知が失敗しても業務データが残ること、履歴から状態を確認できること。
5. CIでの自動検証、デプロイ手順、ログから不具合を調べて改善した記録。
6. Cursorが生成したコードについて、自分が確認した判断・見つけた問題・修正理由を説明できること。
7. インフラの構成図、権限と秘密情報の管理方針、月額費用の根拠、バックアップからの復元とデプロイを戻す手順。

これらはテックリードとしての基礎能力を示す材料になる。チームでの合意形成、他者の設計レビュー、育成、事業上の優先順位づけは、個人開発だけで経験したと主張せず、実務でも積み上げる。

企業求人に現れるKubernetes、マイクロサービス、AI機能等は、今回の要件と採用済みADRに照らして必要性を判断する。現段階で一式を追加する理由はない。

個人開発は設計力と学習成果の補強になるが、求人にある実務年数・チーム経験の代替とは限らない。特に、Kotlinで作っただけでJava実務経験の要件を満たすとは扱わない。

## 推奨が変わる条件

- 現在のReact / Node.js / TypeScript経験を土台にバックエンド・インフラへ広げる：NestJSを第一候補にする（今回の推奨）。
- 志望求人がGo中心：Goを第一候補にする。
- 志望求人がJava実務を強く要求：Java + Spring BootもKotlinと同列で比較する。
- Ruby / Railsなどの既存経験や具体的な志望先がある：今回の3候補に固定せず、その経験からの最短経路を再評価する。

次に技術選定案を検討し、採用する場合はADRに理由を残す。クラウドの具体的なサービス構成を決める前に、月額予算と既存のAWS / Google Cloud経験を確認する。この文書は提案であり、技術スタックを採用済みに変更していない。
